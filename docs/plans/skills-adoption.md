# Skills adoption — which outside skills the harness takes, and which it does not

**Status:** proposed by the main thread on 2026-10-11 at the user's ask, not
built. It records the verdicts on five Claude Code skills the user named and
on the roles of replica-skill (github.com/Jakeschincariol/replica-skill).
Its items carry priorities 2, 4 and 5 of the 2026-10-11 list
(`server-deployment.md`, *The order across the plans*).

## The test

A skill is taken when it serves projects in general and fits the
harness's rules:

- one surface per task (`token-economy.md` P4);
- no role pushes or deploys (C-5);
- no phase widens its own permissions (`command-requests.md`);
- every phase goes through the dispatcher and its quota discipline.

## Verdicts on the Claude Code skills

| Skill | What it is | Verdict |
|---|---|---|
| `/run-skill-generator` | Bundled (CLI ≥ 2.1.145). Brings a project up from a clean checkout and records how to build and run it as `.claude/skills/run-<name>/` | **Take it. Priority 2.** See *1* below |
| `/fewer-permission-prompts` | Bundled. Reads past transcripts and adds an allowlist of read-only calls to `.claude/settings.json` | **Not in a phase**: a phase granting itself permissions. Its idea is taken: a report over `permission_denials` that *suggests* entries for a person to approve (`command-requests.md`, steps 1 and 5) |
| `/batch` | Bundled. Plans a large change and runs it across 5 to 30 worktree agents in parallel | **No.** It goes around the dispatcher: quota, one surface per task, review before merge. The harness's own form is the epic and its split (`task-split.md`) |
| `/loop` | Runs a prompt on an interval in an interactive session | **No, for phases.** The dispatcher is the loop. It stays a tool for the operator's own session |
| `skill-doctor` | No public documentation found on 2026-10-11. It appears to be the report of `claude plugin eval` | **Verify first.** If it is what it seems, it serves the operator: auditing the harness's own `skills/`, not running in a phase |

### 1. run-skill-generator in mapping

The gates and the implementador guess how to build and run a project today.
For a project that is not the harness, that guess is where a phase loses
turns.

- The cartografo's mapping phase (`mapping_enabled`) runs the generator once
  per project and commits `.claude/skills/run-<name>/` to the project.
- The gates read their commands from it when the project's config names
  none.
- It is regenerated by a task, never by a phase on its own.
- **To verify:** the CLI version in the agent image (≥ 2.1.145), and that
  bringing a project up inside the agent's dind works under `-p`.

**Built 2026-10-17** by T-068 (`docs/decisions.md` ADR 115). The mapper runs
the generator first and stages the skill under `docs/run-skill/`; the
dispatcher moves it to `.claude/skills/` under the mapping commit's lock. The
gates still read only the index frontmatter, which the mapper fills from what
the generator verified: ADR 115 narrows the second bullet above. The CLI
version holds (2.1.296); bringing a project up in the dind is not verified yet.

## What replica-skill offers

replica-skill is eleven chained skills that map an existing app from
public sources, rebuild it, and launch it under a new brand. Its Python
tools are stdlib-only and use no network. Against the harness:

| replica | In the harness | Verdict |
|---|---|---|
| recon | the cartografo maps a repo, not the web | **The idea is taken** as the research role (`research-role.md`) |
| architect, build, backend | arquitecto, implementador | already there |
| test: test plan, Playwright E2E, bugs by severity | gates and revisor, no E2E | **Take it as a skill and a gate. Priority 4.** See *2* below |
| design: tokens from screenshots, WCAG contrast check | nothing | **Take it as a skill. Priority 5.** See *3* below |
| diff: visual parity with the original | — | No: only meaningful when cloning |
| entrepreneur, brand, launch | — | No: product marketing, and brand's sweep removes the traces of the original app, which the harness does not do |
| deploy | — | No: C-5 |

### 2. An E2E test skill and gate

For any project with a UI:

- A skill the implementador loads when a task touches a screen: write or
  update a Playwright test for the flow the task changes.
- A gate that runs the project's E2E suite in the agent's dind, with no
  model in the loop, like the other gates. Its failures, sorted by
  severity, go to the revisor.
- The browser image goes into the registry mirror, so the gate does not
  pull it on every run.

**Prerequisite, noted 2026-10-17.** The gate needs the dind, and this host
has no `sysbox-runc`, so `dind-cuenta1` cannot start. Sysbox is installed
before step 3 below starts. That is the decision under `docs/ROADMAP.md`
stage 1, *Sysbox for the dind sidecars*.

### 3. A design skill

For projects with a front:

- Design tokens (colour, type, spacing) written once per project and read
  by the implementador.
- A contrast check as a stdlib script, run as a gate on the token file.
- The prompt names the styles to avoid, as the Opus 5.5 guide advises for
  front work (`models-5-5.md`, *Decisions*, 4).
- Whether this becomes a role of its own is decided after the skill has run
  on a few tasks.

## How it would be built

Each a single surface:

1. run-skill-generator in the mapping phase, and the gates reading its
   recipe.
2. The E2E skill for the implementador.
3. The E2E gate and the browser image in the mirror.
4. The design skill and its contrast gate.
5. The denials report that suggests allowlist entries, inside
   `command-requests.md` step 5.
