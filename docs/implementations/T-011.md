# T-011 — the api's share of tier 1 of the front plan

What this task built, why it is shaped this way, and what it deliberately did
not touch. The spec is `docs/plans/front.md` *The api's share*, over the two
entries it points at: `docs/decisions.md` ADR 17 (three fields the harness has
and the routes omit) and ADR 18 (three configured thresholds on
`/api/accounts`). The two shapes those entries left open are decided in
`docs/decisions.md` ADR 20 and ADR 21, which this file does not restate — read
them for the *why*; this file is the *what*.

No front-end code: `front/` is untracked and stays untracked, and nothing under
it was created or changed. The console half of tier 1 — the `current_task` to
`current_task_id` rename, the four deleted constants in `types.ts`, the debt-id
split — is a separate task.

## What was built

Six fields, in two routes and one shared helper. No new module, no new route, no
new config key, no new data source: every value was already on the `Config` or
the `TaskFile` the service holds.

- `observability/api/app.py`, the `/api/accounts` view: the row built before the
  `try` grows `is_primary`, `quota_threshold_pct`, `reserve_pct` and
  `quota_cooldown_seconds`. `is_primary` is `AccountConfig.is_primary`, which
  `load_config` sets from the top-level `primary_account`; the three thresholds
  come off the `cfg` `create_app` loaded. `data` is still a list of rows and the
  envelope is still exactly `data` and `warnings` — ADR 20 on why a sibling of
  the list was not available.
- `observability/api/app.py`, `_task`: grows `depends_on`, which
  `context_transfer.TaskFile` already parses as a `list[str]`. Both task routes
  answer it, because the console reads the list on the detail screen and a count
  on the index.
- `observability/api/app.py`, the `/api/tasks/<task_id>` view: `row["body"]`
  after the `_task` call and before `app.json.dumps`, inside the existing guard.
  `/api/tasks` does not grow it — ADR 21.

So `/api/accounts` answers nine keys per row, `/api/tasks` ten, and
`/api/tasks/<task_id>` those ten plus `body`.

One doc outside `docs/decisions.md` changed, because this task made its text
false rather than incomplete: `docs/plans/front.md` opened with "Status: nothing
here is built" and *The api's share* described the six fields as work to do. Both
now say the api's share is served and name the two ADRs that closed its open
shapes. That is `T-008-D3`'s lesson applied without being asked — a plan's Status
paragraph that denies finished work is the exact failure that row records, and
the index says the first task allowed to edit the plan owns it.

## Why outside the `try`, and why inside the other one

The two placements are opposite and both are deliberate.

On `/api/accounts` the four new keys are set **before** the `try`, with `name`
and `container`. They come from the config, which was loaded once at startup and
cannot fail per request; the `try` exists for the state file. An unreadable state
file nulls `state`, `current_task` and `rate_limited_at` and must not null what
the config says — an account the operator named primary does not stop being
primary because the record of what it is doing is truncated.
`tests/observability/test_api.py:test_an_unreadable_state_file_keeps_the_config_half_of_the_row`
pins that.

On `/api/tasks/<task_id>` the `body` assignment is **inside** the `try`, with the
shaping and the `app.json.dumps` round, because that is the module's rule: the
guard wraps the use of parsed values, not only the parse
(`docs/learnings/a-never-500-read-wraps-the-use-not-the-parse.md`). It cannot
fire on this field — `read_task_file` builds `body` by splitting the file's text,
so it is always a `str` and always serialises — and the placement is held anyway,
because the next field added there may not be. ADR 21 says this too, so a reader
does not go looking for the test that would prove it.

## What the tests pin

`tests/observability/test_api.py`, which builds its fixtures through the
dispatcher's own writers (its module docstring says why, and that property is
unchanged):

- `_harness` grows four optional keys — `primary_account`,
  `quota_threshold_pct`, `reserve_pct`, `quota_cooldown_seconds` — written into
  the fixture config only when passed, so every existing case still exercises
  `dispatcher/config.py`'s own defaults. `_task` lets a case pass `depends_on`.
- `test_tasks_reports_the_fields_the_task_file_carries` and
  `test_a_harness_with_no_board_is_not_an_error` assert a list row whole, now ten
  keys. The first writes a non-empty `body` into the fixture, so the whole-dict
  assertion is what fails if `body` is ever moved into `_task`.
- `test_accounts_reports_the_pool_from_the_state_directory` asserts the whole
  list, now nine keys per row, against the config defaults.
- `test_the_primary_account_is_marked_and_the_rest_are_not`: a fixture that
  writes `primary_account`, asserting the marked account `true` and the other
  `false`. Without it `is_primary` would only ever be asserted false, since no
  other case writes the key.
- `test_the_thresholds_on_a_row_are_the_configured_ones`: all three set away from
  their defaults, with `reserve_pct` at 70 — above the 60 the default bends to —
  so a route holding literals, or re-deriving the default, fails.
- `test_one_task_by_id_carries_the_running_body_and_the_list_route_does_not`:
  both halves of ADR 21's asymmetry over one task file, including that the
  record did not travel on some other key.

The two envelope-invariant tests were not edited and pass unchanged, which is
the check on ADR 20's shape from one side. `tests/observability/test_board.py`
was not edited and passes unchanged, which is the check from the other: the
board's `_envelope_problem` checks rows by subset, so a row may grow keys, and
`data` stayed a list.

## Declared debt — nothing bounds the body on the detail route

Introduced by this task. `/api/tasks/<task_id>` serves `body` whole, and
`handoff()` only ever appends to it, so the response grows with the task id for
as long as that id lives. The largest card here is 55 KB today and nothing
shrinks it.

**Where it bites:** a card under `.hive/tasks/` past a few hundred KB, or a
client that polls the detail route rather than reading it once per screen view.

**Why it stays:** ADR 17 admits the body whole and ADR 21 only moved it off the
list route. A cap is a decision nobody has made — a truncated running record
needs a rule for which end survives and how the caller is told, which is a
`warnings` contract change under ADR 5, not a line in a view.

**Cost:** one detail response carries a task's whole history, with no warning
and no parameter to ask for less, and it is the largest thing this service
answers.

**Fix:** either a `MAX_BODY_BYTES` truncation naming itself in `warnings`, on
the model of `MAX_EVENT_LIMIT` under ADR 11, or a `?body=` parameter. Either way
it is an ADR narrowing ADR 21, and it belongs with the console task that renders
the detail screen and knows what that screen needs.

## What was not done, and is not debt

- `usage_pct`: ADR 18 keeps it unserved until something persists the `/usage`
  probe and when it ran. Persisting it is a task of its own.
- `rank`: ADR 17 drops it — nothing in the harness ranks accounts.
- The account `heartbeat` the console asks for: ADR 17 rules that neither side
  moves until the object is named, and nothing has named it.
- `observability/board/` and its templates: not one line. `docs/charter.md` C-8
  keeps the Jinja board the tie-breaking reference until the console serves
  parity, so it had to keep working, and its suite is how that was checked.
- `docs/ui.md`: `docs/plans/front.md` binds its creation to the first tier-1
  task that touches a screen. This task touches no screen, and speculative
  vocabulary for screens nobody is building is what that plan says the file must
  not become.
- `docs/plans/board.md` *The shapes*: left as written. It is Phase 1's
  specification and the record of what grew past it is ADR 20 and ADR 21 —
  `docs/learnings/a-toolchain-ruling-can-outlive-a-specs-state-list.md` on why
  rewriting a spec section to match later code is the wrong edit. Now also
  `docs/learnings/board-md-the-shapes-is-not-the-current-key-list.md`, so a reader
  arriving at that list from a trigger learns it is three ADRs behind.

## Filed by the auditor

Nothing in the api changed in this phase; the suite was re-run whole and is
unchanged at 1168 passed, 10 skipped. What it added is the record.

Two debt entries, both `card` `none` because this harness has no board —
`docs/debt/README.md`'s closing paragraphs say why, and for `T-011-D2` there is a
second structural reason recorded there:

- [`T-011-D1`](../debt/T-011-D1.md) — the unbounded `body`, declared by the
  implementador and accepted by the revisor. *Declared debt* above is its long
  form.
- [`T-011-D2`](../debt/T-011-D2.md) — `docs/plans/front.md` *Decisions this tier's
  tasks make* binds two items to the first tier-1 task, which was this one, and
  does not say neither fired. Raised by the revisor as its own proposal and
  therefore ruled on here: `dispatcher/debt.py:accepted` filters the
  *implementador's* declarations by the revisor's rulings, so a revisor's own
  proposal has no route to a card. Accepted, because the fix is an edit to a
  section the plan binds to the console task and the reasoning for not firing
  either item is only reachable from *What was not done, and is not debt* above.
