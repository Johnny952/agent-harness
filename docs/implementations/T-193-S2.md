# T-193-S2 — the console forwards `/api/session`

Decision: `docs/decisions.md` ADR 522 (on ADR 324 and ADR 381).

One file of code, `front/src/lib/api/forward.ts`, and its tests in
`front/src/lib/api/forward.test.ts`. `front/src/server.ts` is not touched:
the address comes from the request's own headers (ADR 522, 5).

## What

1. **`const SESSION = "/api/session";`** beside `PUSH_SETTINGS`, with a
   JSDoc naming ADR 324 and ADR 522.
2. **The CSRF helper.** Move `forwardBoard`'s three checks (415, then the
   `Sec-Fetch-Site` 403, then the `Origin` 403) into
   `function csrfRefusal(request: Request, url: URL): Response | null`, same
   order and same messages. `forwardBoard` calls it and returns its answer
   when not null. Its JSDoc's *On CSRF* paragraph stays on `forwardBoard`
   and the helper's says "`forwardBoard`'s checks, also `forwardSession`'s".
   No existing test may change.
3. **`function clientAddress(request: Request): string | null`**: the
   incoming `x-forwarded-for` split on `,`, the last entry trimmed, returned
   when it matches `/^[0-9A-Fa-f.:]{1,45}$/`, else null (no header, empty,
   or not shaped like an address).
4. **`function sessionCookie(request: Request): string | null`**: the value
   of the `harness_session` cookie in the browser's `cookie` header (split
   on `;`, each part trimmed, the first whose name before `=` is exactly
   `harness_session`), or null. The value is not decoded or checked.
5. **`async function forwardSession(request: Request, url: URL)`**, in this
   order:
   - `url.search !== ""` → 400 `{"error": "/api/session takes no query string."}`;
   - `POST` or `DELETE`: `csrfRefusal` → its answer;
   - headers `{ Accept: "application/json" }`; when present add `Cookie:
     harness_session=<value>`, `X-CSRF-Token` (the browser's
     `x-csrf-token` unchanged) and `X-Forwarded-For` (`clientAddress`);
   - `POST` only: `Content-Type: application/json` and the body from
     `readBounded(request, MAX_BOARD_BODY_BYTES)`, null → 413 with the
     board writes' message; `GET` and `DELETE` send no body;
   - `fetch(`${BOARD_SERVICE_URL}${SESSION}`, { method, headers, body?,
     signal: AbortSignal.timeout(BOARD_SERVICE_TIMEOUT_MS) })`, the catch
     exactly `forwardBoardRead`'s (log the address, 504 on timeout, else 502);
   - answer: `new Headers()`, `content-type` when upstream sent one, then
     `append("set-cookie", c)` for each `upstream.headers.getSetCookie()`;
     `new Response(await upstream.arrayBuffer(), { status, headers })`.
   - Nothing is logged but the failure line; never the body, cookie, token
     or address.
6. **Dispatch** in `forwardApiRequest`, after the two push reads and before
   `boardTarget`: `if (url.pathname === SESSION && (method is GET, POST or
   DELETE)) return forwardSession(request, url);`. `PUT`/`PATCH` fall to the
   405; `/api/session/x` to the 405 or the whitelist's 404 as today.
7. **Prose.** The file header gets a paragraph after *Three more…
   credentials*: "**Three more go to the board-service for sign-in** (ADR
   324, ADR 522)", the three pairs, that they alone carry the
   `harness_session` cookie, `X-CSRF-Token` and `X-Forwarded-For` (the last
   hop received) and pass `Set-Cookie` back, the two writes with the CSRF
   checks, a query refused. Update the push paragraph's "(twenty-seven with
   the three below)" to "(twenty-seven with the three credentials below,
   twenty-nine with the session's two)". `boardTarget`'s and
   `forwardBoard`'s "twenty-seven" and the dispatch comment stay: those
   functions still hold twenty-seven pairs.

## Tests (`forward.test.ts`, new `describe("the session routes (ADR 522)")`)

A Set-Cookie stub: `vi.spyOn(globalThis, "fetch").mockImplementation(async
() => new Response(body, { status, headers: [["content-type",
"application/json"], ["set-cookie", "harness_session=s; Path=/; HttpOnly"]] }))`.

1. `POST` with same-origin headers, a browser `Origin`, `Authorization`, a
   `Cookie: other=1; harness_session=abc`, `X-CSRF-Token: t` and
   `X-Forwarded-For: 6.6.6.6, 203.0.113.7`: target `${BOARD}/api/session`,
   method POST, headers exactly `{Accept, Content-Type, Cookie:
   "harness_session=abc", "X-CSRF-Token": "t", "X-Forwarded-For":
   "203.0.113.7"}` (so no Origin, no Authorization, no `other`), body bytes
   unchanged.
2. The answer of 1: status 200, JSON body, `getSetCookie()` equal to the
   stub's.
3. `GET` with the cookie and no CSRF headers at all (and with
   `sec-fetch-site: cross-site`): forwarded, no body, `Set-Cookie` back; a
   401 stub passes back 401 with its `Set-Cookie`.
4. `DELETE` with the cookie and the token: forwarded, 204 passed back
   with an empty body and the clearing `Set-Cookie`.
5. `X-Forwarded-For` absent → no `X-Forwarded-For` upstream; `garbage` or
   `1.2.3.4, ` (empty last hop) → none; a single `::1` → `::1`.
6. No cookie → no `Cookie` key upstream; no token → no `X-CSRF-Token` key.
7. A query (`?x=1`) on each of the three methods → 400, fetch not called.
8. `POST` and `DELETE` as `text/plain` → 415; `sec-fetch-site: cross-site`
   → 403; `origin: http://evil.test` → 403; fetch not called.
9. `POST` over 64 KiB → 413, fetch not called.
10. Unreachable → 502, timeout (`DOMException("…", "TimeoutError")`, as the
    existing timeout tests do) → 504; neither body contains `board.test`.
11. `PUT /api/session` → 405 and `/api/session/x` `GET` → 404, fetch not
    called.
12. Another board write (e.g. `POST /api/backlog`) sent with a cookie, an
    `X-CSRF-Token` and an `X-Forwarded-For` still sends exactly its old
    headers, and a `Set-Cookie` from its stub is not passed back.

Run `cd front && bun install` if `node_modules` is missing, then
`bun run typecheck`, `bun run test`, `bun run lint`.

## As built

All seven *What* steps and the twelve tests (grouped into eleven `it`s) are in.
One deviation: `forwardSession` answers a 204, 205 or 304 with a `null` body.
`new Response(await upstream.arrayBuffer(), { status: 204 })` throws `Invalid
response status code 204` even for an empty buffer, and the close is a 204.
Typecheck, the whole `bun run test` and lint pass.

## Ruled out

See ADR 522 *Ruled out*: the socket peer, the first hop, folding into
`forwardBoard`, the whole `Cookie` header.
