# T-140 — the worker runs one project's starts in parallel

Decision: `docs/decisions.md` ADR 306 (narrows ADR 200 for the worker).

## What was built

- `dispatcher/config.py`: `Config.project_parallel` (slug to ceiling), loaded by
  `_load_project_parallel`, which refuses non-integers, bools, values under 1 and
  values over the pool's phase slots (the sum of `max_concurrent_phases`), the
  same bound `queue --parallel` has in `cli.py`. `Config.parallel_for(slug)` reads
  it, default 1, capped by the slots. Read-only in `CONFIG_KEYS` (ADR 106).
- `dispatcher/queue.py`: `_Scheduler` became `WriteScheduler(cfg, project, label,
  cond, order=())`, with `enlist(task_id)` for callers that learn the order as
  starts join. `_run_parallel` builds it as before; nothing else moved.
- `dispatcher/actions.py`: the `start` serial key is `start:<project>:<task>`,
  so the same task cannot run twice but one project's starts no longer exclude
  each other by key.
- `dispatcher/worker.py`: `_StartGroup` (lock, scheduler, member action ids) per
  project in `Worker._groups`. `_join_project` takes the `ProjectLock` for the
  first start and adds later ones up to `parallel_for`; `_leave_project` releases
  the lock when the last member leaves. `_consider` reserves the place before the
  account, pool and claim checks and gives it back at each refusal. The scheduler
  exists only under a ceiling above 1 and is passed to `run_task_cycle(scheduler=)`
  by `_start`, which already does the single mapping, write window and stale-plan
  note.

## Why this way

- Reuse `run_task_cycle(scheduler=)`: the worker only has to hand it a scheduler.
- A ceiling of 1 builds no scheduler and holds the lock exactly as before, so
  every existing worker test passes unchanged.
- Other `project:` kinds (verdict, clone, init, request_changes) still take their
  own `ProjectLock`; a held group makes them wait as `project`, and a held verdict
  makes a start wait, through the flock.

## Ruled out

- Raising the ceiling per action rather than per project: needs no config, but
  gives the owner no way to keep today's behaviour.
- A per-start lock: breaks "a `run-task` stays out while any start runs".
- Duplicating the window code in the worker: `WriteScheduler` is shared.

## Known limits

- The `ProjectLock` holder record names only the group's first start.
- Within a group the write order is the order starts joined, not an epic's order.

## Tests

`tests/dispatcher/test_worker_parallel.py` (windows at once on disjoint surfaces,
never on overlap, lock held until the last start leaves, third start waits,
ceiling 1 has no scheduler, refusal gives the place back); `test_config.py`
(ceiling parsing and slot bound); `test_actions.py` (serial key).
