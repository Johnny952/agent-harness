# T-014 — the drop waits for the auditor's section in the task card

What this task built, why it is shaped this way, and what it deliberately did
not reach. The spec is the second paragraph of *Fix* in
[`docs/debt/T-012-D1.md`](../debt/T-012-D1.md); the decision is
[`docs/decisions.md`](../decisions.md) **ADR 34**, which narrows **ADR 33**. This
file does not restate the argument — ADR 34 is six arguments in order, and it is
the thing to read for the *why* of any one of them. This file is the *what*, the
shape, and the two places a later task will trip.

The code is about twenty-five lines across three files. The ADR is the
deliverable, and the row this closes had been open on exactly the point the ADR
settles: which local file stands in for "the promoting role ran".

## What was built

Three symbols, no config key, no flag, no verb.

- `dispatcher/context_transfer.py:has_phase_section(hive_dir, task_id, role)` —
  the evidence reader. `read_task_file(task_file_path(...)).body` and one
  anchored regex, `^## <role>( \(round \d+\))?$` under `re.MULTILINE` with
  `re.escape` on the role. It lives here because this module owns the card and
  already holds every other path into it, and because both `drop_promoted` call
  sites already pass `cfg.hive_tasks_dir`, so the check costs one `open` and no
  new argument. `(OSError, ValueError, KeyError, yaml.YAMLError)` — the four
  `read_task_file` raises — answer `False`.
- `dispatcher/learnings.py:droppable(hive_dir, task_id) -> list[Entry]` — the
  filter that was inline in `drop_promoted`, lifted verbatim: not `reviewed`,
  `scope == SCOPE_PROJECT`, `task_id in (entry.task, entry.carried_by)`. No
  condition was added or removed in the lift.
- `dispatcher/learnings.py:PROMOTING_ROLE = "auditor"` — the role named once.
  The gate and the line `merge-task` prints both read it. `duties`' own
  `role == "auditor"` branch is left alone; ADR 34's last paragraph says why,
  and a reviewer should read that rather than file it as a duplicate.

`drop_promoted` keeps its name, its signature and its `list[str]` of
inbox-relative refs — ADR 33 froze all three — and gained four lines: select
through `droppable`, and if the selection is non-empty and the card carries no
section for `PROMOTING_ROLE`, log what stayed and return `[]`. The move loop
below it is untouched, `_free_path` included.

`dispatcher/cli.py`'s `merge-task` arm gained the `else` branch: when nothing
was dropped it re-selects through `droppable`, and if that is non-empty prints
how many entries stayed, that they stayed in `inbox/`, the card it looked in,
the missing `## auditor` heading, and the refs. Exit 0. Everything above the
call — `cleanup_container`, `read_owner`, the `try/finally`, the
`outcome.refused` exit 1, `print(outcome.detail)` — is unchanged, and so is
`close_resolved_debt` below it.

`dispatcher/dispatcher.py` has **no** change. The gate is a no-op on the
automatic path and the test is what says so.

### Why `entries and` comes first

The gate reads the card only when there is something to drop. A merge of a task
that filed nothing — the ordinary case, most merges — takes the same path it
took before this task and logs nothing. The ordering is not an optimisation of
one `open`; it keeps the log quiet, because a line about a missing auditor
section on every merge that had no entries anyway is a line operators learn to
skip.

## Why the card body, and not `handoffs/`

ADR 34 argues this at length; the operational short version is that
`list_handoff_roles` reads a directory that does not exist for a task predating
`save_handoff` or for one no phase has finished, while those cards still carry
their `## <role>` sections. A gate on the directory would answer "no auditor"
for ever for the oldest tasks in the hive and keep their entries in the inbox
permanently — unbounded prompt cost, which is the cost the drop exists to pay
off. It is a different bug in the same place, not a safer default.

The heading, not the role's name: a role writes prose into its `**Detail**` and
that prose lands inside somebody's section, so a substring search for `auditor`
would read a risk line saying *the auditor never ran* as proof that it did. The
parsed body, not the file's text: a card's frontmatter carries the task
description, and a description is free to quote the heading it is asking for —
T-014's own card does.

## What a later task will trip on

**Two existing tests in each of two files went red the moment the gate landed,
and that was the gate working.** `tests/dispatcher/test_learnings.py:_entry` and
`tests/dispatcher/test_cli.py:_learning` build the learnings root and never the
task card, so `drop_promoted` found no evidence and moved nothing:

- `test_drop_promoted_moves_only_what_the_merged_branch_filed`
- `test_drop_promoted_does_not_overwrite_an_earlier_dropped_entry`
- `test_cli_merge_task_drops_the_entries_the_merged_branch_filed`
- `test_cli_merge_task_keeps_the_entries_another_task_is_carrying`

Each now writes a card first, through a `_card` helper added beside the entry
helper in both files, and each docstring says the card is what admits the drop.
A phase that reads that failure as unrelated breakage will loosen the gate
instead of writing the card. The general shape is filed as a trap in the shared
inbox: a precondition added to a `dispatcher/` function that reads
`.hive/tasks/<id>.md` turns red every existing test of that function.

`tests/dispatcher/test_learnings.py:test_drop_promoted_keeps_the_entries_when_the_card_cannot_be_read`
has to `mkdir` the hive directory before writing a damaged card into it: the
learnings root is a *sibling* of `hive_tasks_dir`, so `ensure_dirs` never
creates the directory the card lives in.

## Tests, and what each one pins

Seven new, in three files; `python3 -m pytest` goes 1106 → 1113 passed, 10
skipped.

`tests/dispatcher/test_learnings.py` — a cycle whose card has only
`## implementador` and `## revisor` keeps everything and does not even create
`dropped/`; `## auditor (round 2)` admits the drop, because `run-phase --round`
labels a hand-resumed phase that way; a missing card and a card with no
frontmatter both keep the entries and neither raises; a card whose only mention
of the role is a prose line and a `### auditor` keeps them; and `droppable`'s
refs equal what `drop_promoted` returns on a card that has the section, which is
the only state in which the two lists can be compared at all.

`tests/dispatcher/test_dispatcher.py:test_run_task_cycle_still_drops_the_entries_its_auditor_filed`
— the automatic path end to end, with a real project-scope entry in the inbox
before the run. It asserts the card got its `## auditor` section and that the
file left `inbox/` for `dropped/`. ADR 34's claim that the gate is a no-op there
is a claim about control flow, so a refactor that reorders the auditor and the
drop fails this test instead of surviving a comment.

`tests/dispatcher/test_cli.py:test_cli_merge_task_says_what_it_kept_when_no_auditor_ever_ran`
— exit zero (asserted by *not* expecting `SystemExit`, the way the other
merge-task tests do), the entry still in `inbox/`, and the line carrying
`kept 1`, `inbox/`, `## auditor` and the ref.

## What was ruled out

- **An override flag, a config key or a new verb.** A switch for forcing the
  drop past the gate is a switch for losing the entries again, which is the
  whole content of the row. Nothing needs one: when the gate fires the entries
  stay in the inbox, where the next task sees them and where the table a phase
  is handed is capped at `MAX_ROWS` anyway. The operator who really must clear
  one has `dispatch learnings --drop <ref>`, which takes one ref at a time, with
  the entry in front of them, and means "this entry was wrong".
- **The gate at the `merge-task` call site.** Two callers today and a third
  named in [`docs/plans/board.md`](../plans/board.md) — Phase 4's action queue.
  "Do not move an entry unless the role that files it ran" is the function's
  promise about the files it moves, not one caller's good manners.
- **`list_handoff_roles` as the evidence.** Above, and ADR 34.
- **The exact test — checking each ref against the merged tree.** That is a
  second `docker exec` into the project checkout on every merge, to catch a case
  no run has yet produced. **It is accepted as a residual in ADR 34's
  Consequences and is deliberately not a row in
  [`docs/debt/README.md`](../debt/README.md)**: the cost is refused on the
  merits, not deferred for capacity, and a row nobody intends to take reads as
  pending work for ever. If the case fires, that paragraph is the thing to
  supersede, and the ref list the merge printed is the evidence that it did.
- **Anything that enumerates `dropped/`.** `read_inbox`, `read_harness` and
  `read_all` are unchanged, no prompt fragment mentions the directory, and
  neither amended `README.md` passage says anyone looks there. ADR 33's move is
  free only because no reader walks it.
- **Rewriting [`docs/debt/T-012-D1.md`](../debt/T-012-D1.md).** Its blockquote
  of the old docstring is the record of what the premise said at filing time.
  One line of it changes, the `**Status:**` line, and the auditor writes it
  along with the row — the indexes are that phase's to write.

## The limit of the proxy, beyond the residual ADR 34 accepts

A section is evidence that a phase *returned*, not that it filed anything, and
the section is rendered from whatever the phase came back with. When a phase
returns a structured handoff, every line of the role's own text lands behind a
`- ` bullet or a `**Bold**` label, so a role cannot write a column-zero `## `
heading into the card. When no schema comes back, `dispatcher/handoff.py:body`
falls back to the phase's raw prose, and prose starting `## auditor` at column
zero would be indistinguishable from a section. No run has produced that, a
`final=True` phase that does not return at all leaves no section either way, and
closing it means changing what the fallback renders rather than what the gate
reads. It is written down here because it is the next thing to know if the gate
is ever seen to pass on a cycle whose auditor did not run.
