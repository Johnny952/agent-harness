# T-138 — `mark_orphaned` and `drop_promoted` take the carry lock

Implements ADR 300 (extends ADR 294, decision 1); closes `docs/debt/T-136-D1.md`.

## What

`dispatcher/learnings.py`:

- `mark_orphaned` does an unlocked first read to find the projects of the
  entries it would touch, then for each project (sorted) takes
  `_carry_lock` and runs `_release` — a fresh read of inbox and harness,
  a fresh `seen` map, and the old loop restricted to that project.
- `drop_promoted` keeps the `droppable` selection and the `has_phase_section`
  gate outside any lock, then per project takes the lock and runs
  `_move_dropped` (a fresh `droppable`, filtered by project).
- Entries whose project is not one path component (`_lockable`) are handled
  in a final unlocked pass (`project=None`): `carry` refuses such a project,
  so nothing can race them, and raising would strand the dying task's other
  entries.
- Signatures, return types and log lines are unchanged; no caller changes.

## Tests

`tests/dispatcher/test_learnings.py`: each function waits on a held lock;
another project's held lock does not block; the `mark_orphaned` vs `carry`
race (slowed `_write`) keeps both `carried_by` and the demoted status; invalid
project slugs are still released and dropped. 587 tests in
`test_learnings.py` + `test_dispatcher.py` pass.

## Ruled out

- One lock per learnings root: would make every project's carry wait on
  unrelated writers (ADR 300 decision 1).
- Holding all needed project locks at once: needs a lock order; one at a
  time cannot deadlock.
- Locking `stamp`, `reconcile`, `promote`, `set_status`, `delete`: none races
  `carry` on `carried_by` today (ADR 300 Consequences).
- The race test cannot prove the lock absent of races, only show the lost
  update without it.
