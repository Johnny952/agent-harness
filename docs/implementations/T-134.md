# T-134 — one public resolve-under-lock function

## What

- `dispatcher/dispatcher.py` `resolve_conflict_locked(cfg, task_id, slug) ->
  (outcome, detail)`, after `_back_in_review`: cleanup container, the
  `resolve-conflict` base lock, `read_owner`/`restore_owner` around
  `resolve_conflict`. It is the worker's former `_resolve_locked`, moved.
- `dispatcher/worker.py`: `_resolve_locked` deleted; the handler calls
  `core.resolve_conflict_locked`. No `core._base_lock` left there.
- `dispatcher/cli.py` `resolve-conflict`: one call; `resolved` prints the
  detail, `not_resolved` prints it to stderr (exit 1), `not_run` prints
  `task <id>: not resolved: <detail>` to stderr (exit 1).
- Debt `T-133-S1-D1` marked resolved in its entry and in `docs/debt/README.md`.

## Why this way

ADR 291. The worker's body already returned the outcomes both callers need,
so it moved verbatim and the CLI maps them. `resolve_conflict` and
`_base_lock` are looked up as module globals, so monkeypatches still reach them.

## Ruled out

A raising function and a container parameter (ADR 291 *Ruled out*).

## Behaviour change

CLI edges only (ADR 291): no container is exit 1 (was exit 2 with usage), and
an exception is a one-line exit 1 (was a traceback).

## Verified

`python3 -m pytest` (see handoff). The six helper tests now call
`core.resolve_conflict_locked`; the handler fake patches it; the CLI test
patches `dispatcher_mod` names; two new CLI tests cover `resolved` and `not_run`.
