# T-052 — the collector's `/events` take a read token and per-agent write tokens

Decision: `docs/decisions.md` ADR 72. This note is how it was built.

## What was done

- `observability/collector/server.py`
  - New pieces: `ConfigError`, `parse_write_tokens` and `load_config(environ)`.
    The last returns `(read_token, {source_app: token})` or raises with a
    message naming the variable.
  - `_source_app_for` does a full constant-time scan with `check_token`.
  - `_unauthorized` returns a 401 with `WWW-Authenticate: Bearer`.
  - `create_app(db_path, read_token, write_tokens)` changes the routes:
    - `POST` authenticates before it parses the body and stores the bound
      source_app.
    - `GET` requires the read token.
  - `main(environ=None)` prints `collector: refusing to start: …` and exits 2.
    Otherwise it builds the app; `__main__` calls `main().run(...)`.
- `hooks/emit_event.py`
  - It sends `Authorization: Bearer $COLLECTOR_TOKEN` when the variable is set.
  - A non-2xx response is one stderr line with the status. Unreachable is
    unchanged, and nothing raises.
- Compose files
  - In all three, each agent got `COLLECTOR_TOKEN=${COLLECTOR_WRITE_TOKEN_<N>}`.
  - The collector got `COLLECTOR_READ_TOKEN` and the
    `COLLECTOR_WRITE_TOKENS` map, in `docker-compose.yml` and
    `docker-compose.coolify.yml`.
  - The Coolify header lists the three keys as required.
- `scripts/configure.sh`
  - `write_token_var` maps an account name to its key.
  - The `.env` it writes gains `COLLECTOR_READ_TOKEN` and one write token per
    entered account, all from `gen_token`.
  - The custom-accounts note names the two compose edits.
- README
  - The wizard, `compose up` and Coolify sections name the keys.
  - The section 6 row is now marked built.
- Tests
  - `tests/observability/test_collector.py` covers:
    - GET with no token, a wrong token, Basic auth, a write token, and the read
      token;
    - POST with no token, a wrong token, and the read token;
    - A's token claiming B is stored as A;
    - startup with each variable unset, empty or whitespace;
    - every map refusal.
  - `tests/hooks/test_emit_event.py` covers the header, no header without a
    token, and a 401 being one line that does not raise.
  - `tests/integration/test_hook_to_collector.py` runs over a real socket with
    tokens, plus spoofing and refusal cases.
  - `tests/integration/test_compose_invariants.py` has five per-deployment
    checks: the read token only in the collector, the agent-to-map binding,
    each write variable's holders, and bare spelling.

## Why this way

- The map is assembled in compose rather than discovered from the env, so the
  binding sits next to each agent's `SOURCE_APP`.
- The compose test can then check, on the files alone, that the binding and
  the agent agree.
- Each account keeps its own `.env` key so `configure.sh` can generate it the
  way it generates `API_TOKEN`.
- The collector checks configuration in `main()`, not `create_app()`, so tests
  and the integration server can build an app directly.
- A `create_app` given nothing still accepts nothing: an empty map or an empty
  read token can never match, because `check_token` refuses an empty expected
  value.
- Compose invariants are per deployment because the split stack is two files.
  A service in one file holding the read token is as bad as one in the other.

## Ruled out

- One shared token. An agent could read every other agent's events, and
  `source_app` would stay a claim in the body.
- A prefix scan of `COLLECTOR_WRITE_TOKEN_*` env vars. The mapping would be
  implicit, and a missing account would be undetectable.
- A default or empty fallback in compose. It is a known token or a hole, and
  the collector refuses empty anyway.
- Giving the dispatcher a token. It has a `collector_url` in config but no
  HTTP client for the collector.
