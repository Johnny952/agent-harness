# T-016 — `/api/learnings`, and the console's two learnings surfaces

Tier 2's second and last route. The decisions are `docs/decisions.md` **ADR 41**
(the route and its row, field by field) and **ADR 42** (the console's half, which
narrows ADR 18 and ADR 27), both appended by this task's arquitecto; the build
order was `/data/.hive/tasks/T-016/plan.md`, which is outside the repo and goes
with the task. This file is what was actually built, why that way, and what was
ruled out.

Before: `front/src/lib/api/client.ts:listLearnings` returned `mockLearnings()`
with `L-01` ids that exist nowhere in this harness; the Learnings screen drew
that fixture, sorted it with a comparator of its own and measured it against a
`LEARNING_TABLE_CAP = 40` literal in `types.ts`; the task detail's learnings
region was an `EmptyState` naming `/api/learnings` as the route it waited for;
and `front/src/lib/api/forward.ts` refused that path as not one of the six it
carried.

## What a learning row is, in one paragraph

An entry is a file — `<hive>/learnings/{inbox,harness}/<slug>.md`, written by the
phase that hit the trap, parsed by `dispatcher/learnings.py` into `Entry` as
frontmatter-as-read plus the body's four sections. The route serves **ten keys**:
`ref`, `task`, `carried_by`, `scope`, `status`, `when`, `rule`, `stale`,
`in_phase_table`, `phase_table_cap`. ADR 41 part 5 has the table with a reason
per key and a second list of what is left out — `body`, `path`, `project`,
`reviewed`, `harness`, `refutes`, `refuted_by`, `fingerprint`,
`orphaned_from` — each with its own reason. Three of those are worth repeating
here because a later task will reach for them: **the body is not served** (the
`rule` line is what the dispatcher's own table shows and the file the `ref` names
is the document), **`refutes` and `refuted_by` are real and unrendered** (they
are the next thing this route grows, for a screen that explains *why* a row is
refuted), and **`docs/learnings/` is a different object** from the hive inbox and
is not in this read at all.

## What was built — four functions in `dispatcher/learnings.py`

No behaviour change, and no second parser: each of the first three is code that
already existed inside `table()` or `duties()`, lifted so the api asks the same
question the dispatcher does and neither side can drift.

- `eligible(entries, project)` — `applicable()` minus the refuted, which is the
  cut `duties` makes before `table` orders anything. `duties()` now calls it in
  place of its inline comprehension.
- `ordered(entries, harness)` — the sort `table()` did: confirmed first, refuted
  last, fresh before stale inside each band, `ref` as the tie-break.
- `handed(entries, harness)` — `ordered(...)[:MAX_ROWS]`, exactly the rows a
  phase's prompt carries.
- `unreadable(path)` — the `.md` files in one directory `read_dir` skipped.

`table()` is rewritten to take its rows from `handed` and to decide its "N more
are in the directory" footer by `len(entries) > len(shown)` rather than by
`MAX_ROWS` directly. It renders the same bytes: the existing tests in
`tests/dispatcher/test_learnings.py` are the check and none of them needed
editing, which the arquitecto predicted from reading the function and this phase
measured.

One comment was corrected while being moved. The sort comment inside `table()`
said "stale before fresh within each band"; the key is `e.stale(harness)`
ascending, so it is fresh before stale, and `ordered`'s docstring says that.

`unreadable` is the `LocalBoardClient.unreadable()` shape (ADR 3, ADR 4,
`docs/debt/T-008-D2.md`) and exists for the same reason: a reader that silently
drops what it cannot parse leaves the one caller whose whole contract is "report
the damage" nothing to report. It **re-reads** the directory through
`_read_entry` rather than widening `read_dir`'s return, because `read_dir` has
four callers inside the dispatcher that want entries and nothing else. It passes
the directory as `_read_entry`'s `root`, which is sound only because the entry is
discarded — the `ref` it would have built is never read, and the comment on the
call says so. It raises `OSError` from `os.listdir` the way `read_dir` does: the
caller guards, this module does not widen.

## What was built — the route

`GET /api/learnings` in `observability/api/app.py`, beside `/api/phases`, behind
the same `requires_auth`, over the hive the api already mounts `:ro`. No compose
change: `../../.hive:/data/.hive:ro` is already both compose files' mount, and the
route needs no environment key.

`?project=` is the only parameter, on `/api/debt`'s rule — optional with one
checkout, required with several, 404 for a slug `projects_root` does not hold,
through `_project` unchanged. The filter is `learnings.applicable`, which is what
a phase of that project is shown: everything a human promoted into `harness/`
plus everything this project discovered itself.

Three warnings and no 500, per directory:

- a `.md` file `read_dir` skipped, named on `_read_cards`' wording;
- a directory that exists and will not list, named, with the *other* directory
  still read — `read_dir` guards with `os.path.isdir` and then calls `os.listdir`,
  which still raises, and this route lists two
  (`docs/learnings/a-per-item-listing-in-a-never-500-read-needs-its-own-guard.md`
  one level up);
- a missing learnings root, which is `[]` plus one warning naming it, because
  `ensure_dirs` runs on every `run-task` and an absent tree means no run has
  happened here. A root that exists with nothing in it is empty and silent.

There is **no per-row `try` and no `app.json.dumps` round**, unlike `/api/tasks`
and `/api/phases`, and the comment on the view carries the reason and the
condition that reopens it: every value comes through `Entry`'s own accessors,
which coerce with `str()`, or is a `bool` or `MAX_ROWS`, so no file content
reaches the envelope un-coerced — and a later field read straight off `meta`
takes the guard and the serialisation round with it.

`MAX_LEARNINGS = 500` bounds the answer on `MAX_PHASES`' model with the clamp
named in `warnings`. The harness fingerprint is computed **once in `create_app`**
from `cfg.permission_mode`, `cfg.allowed_tools` and `docker_exec.WRITER_ROLES` —
the same three `dispatcher/dispatcher.py` passes — off the one `Config` that
function loaded and never from a second `load_config` in a view
(`docs/learnings/a-new-field-on-an-api-row-has-two-questions.md`).
`dispatcher/docker_exec.py` becomes an explicit import of this module for that
one frozenset and is still never called, which is the sentence the module
docstring already carried and now says.

**Tests:** `/api/learnings` joined `ROUTES` in `tests/observability/test_api.py`,
which buys the 401, the unknown-parameter 400, the envelope shape, the bearer
cases and `test_no_route_accepts_a_write`. Then thirteen cases in the file's
idiom, written through a `_learning` helper that writes the frontmatter and the
`## Rule` section by hand the way a phase does — there is no public writer for
these, so a test going through one would exercise a path nothing on this harness
takes. `_harness` now also returns its `config_path`, so `_fingerprint` reads the
two permission defaults off the same `config.yaml` the app was created from
rather than spelling them out: a literal would stop pinning anything the day
`dispatcher/config.py`'s defaults move.

## What was built — the console half

`LearningEntry` in `front/src/lib/api/types.ts` becomes ADR 41's ten keys under
the api's own names; `id`, `trigger`, `body` and `retired` are gone. `scope` and
`status` are widened with `| string` because the api derives both with `str()`
from a file's own frontmatter, which makes the union an annotation
(`docs/learnings/a-console-type-over-a-served-value-is-an-annotation.md`).
`LEARNING_TABLE_CAP` is **deleted**, with the comment block above it naming ADR
42 the way the `HEARTBEAT_STALE_S` note does: it was never a layout number, it is
`dispatcher/learnings.py:MAX_ROWS`, and it arrives per row as `phase_table_cap`.
`HandoffPayload.learnings`' comment and the `Phase` docstring's clause about the
join were both false — that field is free prose, not refs — and say so now.

`listLearnings` is `readEnvelope<LearningEntry[]>("/api/learnings")` in the wired
block, with no mapping and no sort: the api answers in the order a phase sees and
reordering at the boundary would be the console contradicting the route. The
forward admits `"/api/learnings": []` and its `?project=` line became a
`PROJECT_SCOPED` set rather than `path === "/api/debt"`, because two routes now
take the slug from `CONSOLE_PROJECT`. Three counts moved from six to seven: the
forward's docstring, its rejection message (pinned in `forward.test.ts`) and
`client.ts`'s.

`mockLearnings` is **kept and conformed**, which is ADR 25 and
`docs/learnings/narrowing-a-served-type-is-also-a-fixture-edit.md`: a fixture
typed against the served interface is what makes a typecheck catch a type that
drifts from the route. Its paragraph in
`front/src/lib/api/mock/fixtures.ts` moved from the
fixtures that still back a screen to the ones that back nothing.

`front/src/components/console/learnings.tsx` is new and **exports components
only**: `LearningStatus` (the status pill with `stale` as a qualifier beside it,
an unknown status verbatim and muted) and `InPhaseTable` (the two falses told
apart — refuted, or past the cap the row itself carries). It is a components
module and not a route file for ADR 30's reason: a test cannot reach a component
under `src/routes/`, because the TanStack generator tries to make a route out of
every file there. A non-component export here would have cost a tenth
`react-refresh` warning and this task's bar is the nine the console already
carries (`docs/debt/T-015-D1.md`), so there is none.

`front/src/routes/learnings.tsx` renders the served rows: no `statusRank`, no
sort, the filter all that stands between the rows and the table; the `useMemo`'s
dependency is the envelope object and not the unwrapped `?? []`
(`docs/learnings/a-query-default-feeding-a-usememo-dep-depends-on-the-data-object.md`);
`WarningBanner` above the content; the cap read off a row's `phase_table_cap`;
the over-cap banner counting rows that are neither refuted nor `in_phase_table`;
`Absent` for an empty `when` or `rule`; and an empty state that names the harness
fact — no phase has written an entry — rather than a route.

`front/src/routes/tasks.$taskId.tsx` gains `learningsQuery`, its warnings
concatenated into the one banner, and the region changes subject: the rows whose
`task` or `carried_by` is this task id — the last of `learnings.droppable`'s
four conditions, without its inbox, `reviewed` and `scope: project` ones, so
`merge-task` drops a subset of what the region shows (ADR 42) — with a `carried` marker on a row another task found. Its copy says the
handed table is recomputed per dispatch and recorded nowhere, which is
`docs/ui.md` *A region with no route says which route, and when*'s third
sentence; an `ErrorState` inside the region on a failed read, like the debt
region beside it.

**Tests:** `front/src/components/console/learnings.test.tsx` in
`payload.test.tsx`'s
idiom, eight renders — a known status, an unknown one, a served `stale`, a fresh
row, `in table`, a cap read off the row, a refuted row, and a refuted row whose
`in_phase_table` is somehow `true`. Two edits in
`front/src/lib/api/forward.test.ts`:
`/api/learnings` forwards with the console's own `?project=`, and the "not one of
the …" case is retargeted at `/api/threads`, which ADR 19 says is never coming.

## What ships unexecuted, and why

V0.6e has a `NOT RUN` results row. Every one of its steps needs a browser against
a running console and no phase can open one; it inherits V0.6c's reason. What a
phase *can* run, and this one did, is the suite behind it:

- `cd front && bun install --frozen-lockfile` — 512 installs across 549 packages,
  no changes.
- `cd front && bun run typecheck` — exit 0.
- `cd front && bun run test` — 60 passed in 5 files (was 51 in 4).
- `cd front && bun run lint` — 0 errors, 9 warnings, the same nine
  `react-refresh/only-export-components` the console carried before.
- `python3 -m pytest` — 1200 passed, 10 skipped (was 1179 and 10).

That covers the route's shape, the forward's allowlist and both served judgements
as units. It covers nothing about what an operator sees, which is what V0.6e is
for.

## What was not done, and is not debt

- **No `docs/learnings/README.md` parser and no route for the filed index.** ADR
  41 part 3: a different object, a different lifecycle, and the only option that
  needs a second parser, which this module's docstring refuses. A later task that
  wants it serves it under its own route with its parser in `dispatcher/`.
- **No reader of `dropped/` or `archive/`.** ADR 33 made `dropped/`'s
  invisibility the property that keeps a wrong drop recoverable for free, and
  `docs/debt/T-012-D1.md` names teaching a reader to enumerate it as what that
  depends on.
- **No `body`, `refutes` or `refuted_by` on the row.** Named above; the reasons
  are in ADR 41 part 5.
- **No byte cap on the answer.** `MAX_LEARNINGS` bounds a count, which is enough
  while `rule` and `when` are one line each. A row that ever carries the entry
  body is a different bound, and the constant's comment says so.
- **No screen-side sort anywhere.** The task detail's `byCycle` remains the one
  screen-side sort in the console, with its reason written on it.

One thing was declared as debt rather than fixed: the Learnings screen's empty
state is one state, so a filter matching nothing reads as an empty inbox. That is
a cross-screen wording gap — `debt.tsx` has it too — and fixing it means an entry
in `docs/ui.md` that binds every filtered screen in the console, while this task
touches one of them. ADR 42's last paragraph is the reasoning.
