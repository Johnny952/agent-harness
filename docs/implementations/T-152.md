# T-152 — `run-queue --resume` takes a new `--limit` and `--parallel`

Decision: `docs/decisions.md` ADR 336 (amends ADR 79, 5 and ADR 333, 3).

## What was built

- `dispatcher/queue.py`: `Queue.changes` (list of `{at, limit?, parallel?}`);
  `resume` split into `reopen` (loads, settles `running` to `interrupted`,
  checks a new limit against `queue.spent`, records the change, requeues
  `limit_reached` entries while spend is below the limit; writes nothing) and
  `resume` (`reopen` + `save`). `usage_offset` is set only when `None` in
  `_run_serial` and `_run_parallel.start`, so a requeued entry's spend counts
  from its first start. `confirmation` prints a "Changed on resume" list.
- `dispatcher/cli.py`: `--parallel` default `None` (a given value is told from
  an absent one; a new queue uses 1). Resume refuses `--project`, `--task-id`,
  `--ready` naming what it takes, holds `--limit` to the floor (helper
  `check_floor`, shared with the new-queue path), and asks the yes
  (`confirm`, shared) only when `reopen` appended a change. A no saves nothing.
- Tests in `tests/dispatcher/test_queue.py` (higher limit runs on, finished
  task not re-run, limit not above spend refused, floor, forbidden arguments,
  parallelism recorded and used, no-answer saves nothing, plain resume, old
  file loads). `_cli` takes `config_of` to give a test a different pool.
- Docs: `docs/cli.md` run-queue, README section 5.

## Why this way

`reopen` raises before touching the file so a refused limit leaves the queue
byte-identical. The change is detected by comparing `changes` lengths in the
CLI rather than a return flag, to keep `reopen` returning a `Queue`.

## Ruled out

- Resuming a `limit_reached` task from its saved phase: no cycle entry at a
  later phase exists and `dispatcher/dispatcher.py` is outside the Surface; it
  re-runs from the arquitecto (ADR 336, 5; proposed as debt).
- Resetting `usage_offset` on requeue: the queue's spend would drop.
