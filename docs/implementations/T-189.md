# T-189 — the queue waits for a pending merge instead of ending

Implements `docs/decisions.md` ADR 498 (amends ADR 79 decisions 4 and 7).

## What was built

- `dispatcher/queue.py`: `_end_status` (done / waiting / stalled) replaces the
  loops' old `left` test; `run` now loops `take project → loop → release →
  _wait_for_merges`, so the project lock is free during the wait (the merge's
  `backup.before_merge` refuses on a held lock, and a request for changes
  needs it). `_wait_for_merges` re-reads finished entries' task files every
  `MERGE_POLL_SECONDS`, maps merged / dropped (or file gone) / blocked, and
  ends `wait_expired` or `cancelled` (KeyboardInterrupt in the sleep). New
  `Queue.max_wait_hours` and `Queue.waiting`, `DROPPED` in `FAILED`, `_now()`
  for tests. `reopen` clears `waiting` for expired/cancelled queues and keeps
  it for a `waiting` one. Confirmation and summary lines per ADR 498 (8).
- `dispatcher/cli.py`: `--max-wait HOURS` (refused with `--resume`, below 0 is
  a usage error); exit 1 for stalled / wait_expired / cancelled.
- `docs/cli.md`: argument row, wait paragraph, exits line.
- Tests in `tests/dispatcher/test_queue.py` (a fake clock and a sleep that
  merges); three older tests now use `max_wait_hours = 0`.

## Why this way

The merge needs no hook: `mark_merged` already writes where `_is_merged`
reads. The wait lives in `run`, not in the loops, so both loops stay as they
were and only the lock handoff is new. A stale `waiting` clock after a loop
that ran cycles is cleared by comparing entry states before and after the loop.

## Ruled out

Waking from the merge paths, holding the lock while waiting, a config key for
the maximum, waiting on dependencies outside the queue (see ADR 498).

## Not done

No CLI-level test of the `--max-wait` flag or the exit codes.
