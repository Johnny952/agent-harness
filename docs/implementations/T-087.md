# T-087 — The queue picks from the board's Ready order

Decisions: `docs/decisions.md` ADR 132. It covers:
- `run-queue --ready N`, which adds the first N ready tasks after the listed
  ones and keeps the listed order;
- ready tasks the checks would refuse, which are passed over and shown;
- the pick, which is read once at plan time and never on resume.

## What was built

- `dispatcher/queue.py`:
  - `Entry.from_ready` and `Queue.passed_over`, both with defaults, so old
    queue files load.
  - `plan(..., ready=0)`: the listed entries, then `_pick_ready`'s. It
    refuses a negative count and a queue with no task.
  - `_entry`: the per-task checks `plan` already made (a description, in
    sections, and `dispatch_problems`), pulled out to be shared.
  - `_pick_ready`: walks `tasks.ready_order(tasks.read_all_tasks(...))`,
    skips listed ids, passes over refused tasks with their reason, and stops
    at the count.
  - `confirmation`: `[from Ready]` on picked lines, and a "Passed over from
    the Ready order" section.
- `dispatcher/cli.py`: `run-queue --ready N`. `--task-id` is optional
  when `--ready` is given. A negative N is refused, and so is `--ready` with
  `--resume`.
- Tests, in `tests/dispatcher/test_queue.py`, 12 new:
  - the pick by bucket, then rank (unranked first), then id;
  - a dependency lifted by what waits on it;
  - merged, blocked, backlog and non-pending tasks not picked;
  - the listed order kept, with picked tasks after it and no repeats;
  - a listed task waiting on a picked one;
  - a refused ready task passed over and shown, while a listed one still
    refuses the queue;
  - the empty and negative errors;
  - a run in picked order;
  - the saved fields, and a queue file from before them;
  - the CLI `--ready` and its usage errors.
  No existing test asserted an order this changes.
- Full suite: 3033 passed, 10 skipped.

## Why this way

- The operator's list is what C-4 confirms, so the Ready order only fills
  in after it.
- The pick runs once, before the screen, so what runs is what was shown. A
  resume runs the saved entries.
- A task the operator did not list should not block the queue. It is
  skipped, and the screen says why.
- The scheduler and its safety rules work off the entries' order, so they
  needed no change.

## Pending

- The front does not start queues. A "run the next N" button on the board
  would call the same `plan`.
- A task that becomes ready mid-queue waits for the next queue.

## Compose

No change.

## Ruled out

- Reordering the listed tasks, picking again on resume or at runtime,
  refusing the queue for one bad ready task, and picking tasks that become
  ready mid-queue (ADR 132).
