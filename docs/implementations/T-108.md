# T-108 — compose: the `worker` service, the actions mount, `BOARD_ACTIONS_TOKEN`

ADR 142 step 5, decided in `docs/decisions.md` ADR 166.

## What changed

- `docker/compose/docker-compose.yml` and `docker-compose.coolify.yml`:
  - `worker`, built from `docker/dispatcher/Dockerfile`, `command:
    ["--config", "/app/config.yaml", "worker"]`, `profiles: ["worker"]`,
    `restart: unless-stopped`, `ia_harness_net` only, no `ports`, the
    dispatcher's `depends_on` (`collector`). No `environment`: the dispatcher
    has none. In the Coolify file it sits after `dispatcher` and before
    `agent-cuenta1`, so `render_coolify_compose` (which copies the head to the
    first `  agent-` line) still reproduces the shipped file byte for byte.
  - `board-service` gains the volume `../../dispatcher_state/actions:/state/actions`
    (read-write, fourth entry) and `BOARD_ACTIONS_TOKEN=${BOARD_ACTIONS_TOKEN:-}`.
  - `console` gains `BOARD_ACTIONS_TOKEN=${BOARD_ACTIONS_TOKEN:-}`.
- `scripts/configure.sh` writes `BOARD_ACTIONS_TOKEN=$(gen_token)` after
  `CONFIG_WRITER_TOKEN`, commented with its readers and the restart on rotation.
- `tests/integration/test_compose_invariants.py`: socket only in `worker` and
  `dispatcher`; the worker's shape; the board service's four volumes, no `/state`
  mount, environment only the token; the token's holders; the optional-default
  parametrize list; `configure.sh` writes it. `tests/scripts/test_configure.py`
  `_assert_tokens` counts the new token (64 hex, distinct).
- `README.md` (step 4, *Deploying with Coolify*) and `docs/README.md` (Modules
  rows for `dispatcher/actions.py` and `dispatcher/worker.py`).

## Mounts chosen

- `worker`: the dispatcher's seven entries, same strings, same order: docker
  socket, `dispatcher_state:/state`, `.hive`, `claude_shared`, the project deploy
  keys, `config.yaml:ro`, `config.d:ro`. Copied, not anchored, so each file stays
  readable; a test asserts equality with the dispatcher's.
- `board-service`: `.hive`, `config.yaml:ro`, `config.d:ro` and
  `dispatcher_state/actions:/state/actions`. Never the whole `dispatcher_state`.

## Ruled out

- A YAML anchor shared by `dispatcher` and `worker`: the compose files carry no
  anchors elsewhere.
- Mounting `dispatcher_state` into the board service: it would hand it the
  account state and locks it must not touch.

## Notes for the operator

- `dispatcher_state/actions` does not exist on the host. Docker creates it on
  first mount, root-owned, which is what both services run as. This task does
  not create it.
- No stack was brought up and `.env` was not touched: an existing `.env` lacks
  `BOARD_ACTIONS_TOKEN`, so Start and Cancel answer 503 until it is added and
  `board-service` and `console` are restarted.
- The compose files were checked statically (YAML-parsing tests), not with
  `docker compose config`.
