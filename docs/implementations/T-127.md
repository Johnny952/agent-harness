# T-127 — push the task branch after each committing phase, per project, off by default

Builds `docs/plans/review.md` step 5 and the task-branch half of *Decisions*,
4. ADR 271.

## What

- `dispatcher/config.py`: a `push_task_branch` key, a mapping of project slug
  to a real boolean (`_load_push_task_branch`, parsed and refused as
  `_load_auto_approve` is), a `Config.push_task_branch` field and
  `Config.pushes_task_branch(slug)`, `False` for an unlisted project. Its
  `CONFIG_KEYS` row is read-only: it writes to the remote with the
  dispatcher's credential.
- `dispatcher/docker_exec.py`: `push_task_branch(container, projects_root,
  slug, task_id, ...)` pushes
  `refs/heads/agent/task/<id>:refs/heads/agent/task/<id>` to the remote the
  base tracks, with `_remote_access`'s credential as `push_base` uses it. No
  `--force`, no `+` refspec, no other ref. It returns a `PushOutcome` whose
  target is the task branch: `pushed`, `no_upstream` or `push_refused`.
- `dispatcher/dispatcher.py`:
  - `dispatch_phase` reads the branch's tip (`_task_branch_tip`, through
    `docker_exec.resolve_commit`) once the worktree exists. After the commit
    and `_record_left_behind`, still inside the owner window, it calls
    `_push_task_branch`, which reads the tip again and pushes only when it
    moved. Both happen only when the phase is not at the base and the project
    has the key on.
  - `DispatchResult.branch_push` carries the one-line note for a push that
    did not land. `run_phase` appends it to the handoff under
    `## Task-branch push`.
- `tests/dispatcher/test_push_task_branch.py`:
  - Real-git tests of the push, built on `test_push_base.py`'s bare-remote
    setup. They check that the branch lands under its own name, that the base
    is never pushed with it, that a branch the remote moved is refused and
    kept, that a base with no remote pushes nothing, and that no command is
    forced.
  - Hook tests check that the push is off by default and off for `false`. On,
    a committing phase pushes, inside the owner window. Nothing is pushed for
    an unmoved tip or at the base. A refused or raising push still lets the
    phase succeed, with the note. An unreadable tip never fails the phase.
    The note reaches the handoff.
- `tests/dispatcher/test_config.py`: the key is off by default, read per
  project, and refused unless it is a real boolean. The key table test counts
  19 read-only keys.

## Why this way

- The push goes to the base's tracking remote, not to `origin` by name, so
  both pushes ADR 78's credential makes go to the same place.
- It compares the tip before and after the phase rather than asking whether
  `commit_worktree` made a commit. That catches whatever landed on the branch
  during the phase, and it costs only two `rev-parse` reads, and only for a
  project with the key on.
- A tip that cannot be read before the phase still lets the push run when the
  branch exists after it. A non-forced push of a branch the remote already
  has is a no-op.
- The note goes on `DispatchResult` and into the handoff, as the gate report
  does. The phase's own outcome is unchanged.

## Ruled out

- `--force-with-lease`: C-5 says never forced.
- Failing the phase on a refused push: the commit is already safe locally,
  and the next committing phase tries again.
- One loader shared with `auto_approve`: kept apart so each key's error names
  itself, and so the change stays local next to T-128's.
