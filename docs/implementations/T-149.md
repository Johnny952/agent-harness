# T-149 — per-address failed sign-in counter

Spec: `docs/decisions.md` ADR 381. Resolves `docs/debt/T-146-D1.md`.

## What was built

`board_service/signin.py`:
- `MAX_ADDRESS_FAILURES = 20`, `ADDRESS_WINDOW = LOCK_SECONDS`.
- `_forwarded_for()` returns the first `X-Forwarded-For` hop or None; `audit`
  uses it instead of its inline split (same output).
- `addresses.json` (via `_addresses_path`, the existing `_read`/`_write`/
  `_locked`, so 0600 and atomic). `_count_address` adds one failure, restarts
  the window when `since` is older than `ADDRESS_WINDOW`, locks at the limit,
  and writes the file pruned by `_address_live`.
- `session_create`: after the body check, inside the lock, a locked address
  gets 429 (`address_locked` audit line, no scrypt). Every failure path
  (`unknown_user`, user `locked`, `wrong_password`, `wrong_code`,
  `replayed_code`) counts through a local `count` helper. A good sign-in does
  not touch the entry. No header: nothing is read, checked or written.

`tests/board_service/test_signin.py`: `sign_in` takes `headers`; a section of
tests covers lock by unknown names, mixed users, other address / no header,
first hop, lock expiry, window, no reset on success, equal 429 bodies, store
mode and content, pruning.

`docs/plans/server-deployment.md` step 1: one sentence naming ADR 381.

## Why this way

Counting by `remote_addr` would lock everyone together (all requests come
from the console), so the code is inert without the header. The address lock
check comes before the user lookup so a locked address spends no scrypt and
cannot tell known from unknown names.

## Ruled out

- Resetting the address on a good sign-in (a sprayer with one account would
  clear its own count).
- A separate lock file or store for addresses: the one `.lock` already
  serialises everything.
- Counting `address_locked` refusals: a lock would never end under retries.

## Not verified

The header is trusted as sent; step 2 must overwrite it (ADR 381
Consequences).
