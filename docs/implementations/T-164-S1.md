# T-164-S1 — the `follow_up` debt ruling

Decisions: `docs/decisions.md` ADR 393 (the plan's) and ADR 394 (how it is
filed).

## What was built

- `dispatcher/debt.py`: `FOLLOW_UP`, added to `RULINGS`; `follow_ups`
  (declarations the revisor ruled `follow_up`, declared order);
  `follow_up_item` (title `<task_id> follow-up: <what>`, description built
  like `backlog_item`'s). `accepted` is unchanged: its
  `ruled.get(fp, ACCEPTED) == ACCEPTED` already drops a follow_up, so it gets
  no id, no filing-note line and no index row.
- `dispatcher/tasks.py`: `follow_up` in `SOURCES`.
- `dispatcher/handoff.py`: the ruling enum follows `debt.RULINGS`; the
  description gains the `follow_up` clause.
- `dispatcher/dispatcher.py`: `_file_follow_ups`, called after
  `_mirror_filed_debt` in `run_task_cycle` and in `run_single_phase` under
  `final`. It files through `tasks.propose` (source `follow_up`, normal,
  `depends_on=[task_id]`) and logs a `BoardWriteError`/`OSError` instead of
  failing the cycle. Nothing is added to `filed`, so the note and the
  automatic approve never see it.

## Why this way

Idempotency reuses `tasks.propose`'s own title match rather than a new
`follow_up_of` field (ADR 394, ruled out). Tests: `test_debt.py` (all four
rulings side by side), `test_handoff.py`, `test_dispatcher.py` (one item, no
debt item, note lists only the accepted entry, re-run, refused propose).

## Ruled out / not done

- The `TaskSource` union in `front/` and the role prompts (S3), `blocked_by`
  (S2).
- A dedicated `run_single_phase(final=True)` test: the call is the same
  helper; the cycle path is tested end to end.
