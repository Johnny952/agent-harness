# T-078 — `GET /api/command-requests` (command-requests step 6, the data half)

Decisions: `docs/decisions.md` ADR 122. It covers the path and its filters,
which rows a block makes and in what state, the verdict with no output and no
email, the CLI lines to copy, and refused requests listed apart.

## What was built

- `observability/api/app.py`:
  - The `GET /api/command-requests` route, with `?project=` and `?state=`.
  - `COMMAND_REQUEST_STATES` and `MAX_COMMAND_REQUEST_TASKS` (2000, with a
    warning like the roadmap's).
  - The helpers `_command_requests`, `_current_block`, `_block_rows`,
    `_accepted_row`, `_request_row`, `_verdict`, `_relative_log`,
    `_commands`, `_refused_row` and `_command_request_order`.
  - Which block is live and whether it awaits a resume are
    `command_run._check_blocked`, `_filed_block`, `_block_verdict` and
    `awaits_resume`. `command_run` is now among the module's imports and its
    docstring's list of readers.
- Tests: `tests/observability/test_command_requests.py` covers:
  - `pending`, with a row per request and *allow* only for kind `agent`;
  - `awaiting_resume` for a *run* and for a *deny*;
  - `resumed` and `denied`;
  - a verdict whose envelope is gone;
  - an undecided block left out once the task moved on;
  - the order;
  - refused requests apart, live block only, malformed ones included;
  - both filters, with a 400 and a 404;
  - unreadable task files, envelopes and verdict entries as warnings;
  - the cap;
  - no output, session, account, email or absolute path in the body;
  - nothing written.
  The route is added to `ROUTES` in `tests/observability/test_api.py`, so
  auth, the unknown parameter and the envelope are checked as for every
  route.
- Docs: ADR 122, and a *Built 2026-10-18, in part* note under step 6 of
  `docs/plans/command-requests.md`.

## Why this way

- Hive-wide, like `/api/roadmap`, because requests belong to tasks.
- `command_run`'s own checks, so the board and the CLI never disagree on
  which block is live or what `command-resume` would take. `_recheck` is not
  used, since it calls docker.
- One row per verdict, because one verdict covers the block. Verdicts
  outlive envelopes, so history survives a later phase.
- Refused requests are apart and live-only, so a block of only refusals is
  visible without offering verdicts the CLI refuses.
- The log only by its relative path, and `by` dropped when it looks like an
  email.

## Pending

- **T-079, the Approvals card.** It reads this response, inside the usual
  envelope `{"data": ..., "warnings": [...]}`:

  ```json
  {
    "requests": [
      {
        "task_id": "T-1",
        "project": "ia-harness",
        "title": null,
        "role": "implementador",
        "filed_at": "2026-10-18T09:00:00.123456+00:00",
        "n": 1,
        "argv": ["pytest", "-q"],
        "target": {"kind": "agent", "container": "agent-cuenta1", "service": null, "cwd": "/workspace"},
        "agent_reason": "to check the suite",
        "state": "pending",
        "verdict": null,
        "commands": {
          "run": "dispatch command-verdict T-1 1 run --project ia-harness",
          "allow": "dispatch command-verdict T-1 1 allow --project ia-harness",
          "deny": "dispatch command-verdict T-1 1 deny --project ia-harness",
          "resume": null
        }
      }
    ],
    "refused": [
      {
        "task_id": "T-2",
        "project": "ia-harness",
        "title": null,
        "role": "cartografo",
        "filed_at": "2026-10-18T09:30:00+00:00",
        "argv": ["sudo", "x"],
        "target": {"kind": "host", "service": null},
        "agent_reason": "need root",
        "refused_reason": "..."
      }
    ]
  }
  ```

  The fields the card needs to handle:
  - `state` is one of `pending`, `awaiting_resume`, `resumed`, `denied`.
  - `verdict` is null or `{verdict: "run"|"allow"|"deny", by, at, comment,
    allowed, resumed_at, ran}`. `by` is null if it looked like an email, and
    `allowed` is the `Bash(...)` pattern on an *allow*.
  - `ran` is null or `{exit_code, timed_out, truncated, log}`, where `log`
    is `commands/<n>.log` relative to the task.
  - `commands` has four keys. Only `run`/`deny` (and `allow` for kind
    `agent`) are set when `pending`, only `resume` when `awaiting_resume`,
    and all are null otherwise.
  - These can be null on a history row whose envelope is gone: `argv`,
    `agent_reason` and `target`, and `project` when unknown. When the
    project is unknown, `commands` carry `--project <project>`.
  - `requests` is ordered pending first, then by `filed_at`.
  - `?state=` and `?project=` filter it.
- A verdict from the board is not built. It is a write and a docker exec, so
  it needs its own ask.
- A history row has no argv once a later phase overwrote its envelope. Fixing
  that means keeping the argv on the verdict record, a dispatcher change.
- An undecided block the task moved on from is not shown.

## Ruled out

- Serving any part of a log.
- Mixing refused requests into `requests`.
- A per-project route.
- Re-checking targets from the API.
