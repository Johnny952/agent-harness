# T-008 — `LocalBoardClient`, Phase 0 of the board plan

What this task built, why it is shaped this way, and what it did not build.
The spec is `docs/plans/board.md` "Phase 0 — `LocalBoardClient`" and is
unchanged by this task. The decisions that a later task could undo without
knowing they were decisions are `docs/decisions.md` ADR 1 and ADR 2; this file
is the build log and does not restate them.

## What was built

A board that is a directory, behind the seam that was already there.

- `dispatcher/vibe_kanban_client.py`: `LocalBoardClient`, plus `CARD_FIELDS`
  (what a card holds and therefore the only keys `list_issues` filters on),
  `INITIAL_CARD_STATUS`, and `_card_issue` (one stored document → one
  `KanbanIssue`). The `KanbanClient` union now names all three clients.
  `KanbanIssue` is untouched.
- `dispatcher/config.py`: `LocalBoardConfig`, `_load_local_board` (the shape of
  `_load_vibe_kanban`, same style of `ValueError`), and `_load_boards`, which
  loads both optional blocks and refuses the pair.
- `dispatcher/cli.py`: `_kanban()` is a three-way choice — `vibe_kanban`,
  then `local_board`, then `NullKanbanClient`. `_seed_kanban_issue_id` accepts
  `--kanban-issue-id` for either board.
- `config.example.yaml`: the commented `local_board:` block beside
  `vibe_kanban:`, saying that the two are alternatives and that `dir` wants a
  mounted volume.
- Tests: 17 local-board cases in `tests/dispatcher/test_vibe_kanban_client.py`,
  the parity test parametrized over `NullKanbanClient` and `LocalBoardClient`,
  a second parity test that the local board adds nothing to the shared surface,
  and the config/CLI wiring in `tests/dispatcher/test_config.py` and
  `tests/dispatcher/test_cli.py`.
- Docs: `docs/decisions.md` (new file, ADR 1 and ADR 2), `docs/README.md`, and
  the three places in the root `README.md` that described a board as
  necessarily Vibe Kanban's.

`dispatcher/dispatcher.py`, `observability/`, and `docs/plans/board.md` are
untouched, as the spec's "Out of scope for Phase 0" requires.

## Why this way

**One file per issue, no index.** A card is `<issue_id>.json` in
`local_board.dir` and nothing aggregates them. An index file would be a second
document to keep consistent with the first, and the only read that would get
faster is `list_issues`, which walks a directory that has one entry per task
this harness has ever run. `_cards()` sorts by `(created_at, issue_id)` so a
reader gets a stable order out of random ids.

**Atomicity copied, not invented.** `_write_card` is
`tempfile.NamedTemporaryFile(dir=...)` then `os.replace`, which is what
`dispatcher/state_machine.py` does for account state — including what it does
not do, which is `fsync`. Matching the existing writer was the point: two
different durability stories in one repo is a thing a later reader has to
explain to themselves. The temp file is named `.card-*.tmp` so a write
interrupted before the replace leaves something `_cards()` skips rather than a
card nobody created.

**`set_status` is read-modify-write.** It reads the card, raises `LookupError`
if there is none, and writes the whole document back with the new status. Not a
partial update: the document is small, and rewriting it whole keeps the atomic
write the only write path.

**An id is treated as untrusted text.** `issue_id` reaches this client from a
task file's frontmatter, so it is a YAML scalar some phase wrote, not something
the client minted. `_card_path` returns `None` when `<issue_id>.json` is not its
own basename, so an id with a separator in it cannot name a file outside the
board directory. That case answers like any other unknown id: `None` from
`get_issue`, `LookupError` from `set_status`.

**`get_issue` really never raises.** The first version caught
`(OSError, json.JSONDecodeError)`, which left one hole: an id carrying a NUL —
reachable from a double-quoted YAML scalar — makes `Path.read_text` raise
`ValueError: embedded null byte`, and `json.JSONDecodeError` is a subclass of
`ValueError` rather than the other way round. The catch is `(OSError,
ValueError)`, which closes the hole and replaces two names with one.
`test_local_board_get_issue_does_not_raise_on_an_id_no_path_can_hold` is the
regression.

**A corrupt card is logged and skipped, not raised.** Writes here are atomic,
so a document that will not parse came from outside this client. `get_issue`
is documented as a lookup, and `list_issues` returning the readable cards is
more useful to a Phase 1 reader than a board that cannot be listed at all.
This is a deliberate asymmetry with `set_status`: a *missing* card is a bug
worth raising about, an *unreadable* one is someone else's edit.

**Both blocks configured fails at load, not at the call.** `_load_boards`
raises, so `_kanban()` never has to encode a precedence rule and the operator
learns at startup. ADR 2 has the reasoning.

## What was ruled out

- **Short display ids** (`VK-7`-style, or `board-1`). `dispatcher/cli.py`
  rejects a `--kanban-issue-id` that does not parse as a uuid; minting short
  ids would mean relaxing that check, which is a second change wearing the
  first one's clothes. `simple_id` stays `None` and the UI can number by
  `created_at`.
- **A `status_map` for the local board.** There is no column here to rename.
  Mapping would throw away the role in `in_progress:<role>`, which
  `docs/plans/board.md` "Why not adopt one" names as the one dimension a
  generic board cannot model.
- **A lock around the read-modify-write.** One writer today, and the write
  itself is atomic, so a race can lose a status but cannot corrupt a card.
  Carried as debt rather than built, because a lock file with no concurrent
  writer is a mechanism whose first real test would be its first use.
- **SQLite, one file for the whole board.** `observability/collector/` already
  owns the project's only database, and a board that is a directory of JSON is
  readable with `ls` and `cat` before any of Phases 1–3 exist. The plan says
  "SQLite is enough until it is not" about the *events* table; this is the same
  argument one notch lower.
- **Deleting `VibeKanbanClient`**, or flipping the local board on by default.
  Both are explicitly out of scope: the default flips in Phase 2, "because that
  is when there is something to look at".
- **A `delete_issue` or any fifth method.** The seam is four methods, and a
  public method only one implementation has is one `dispatcher/dispatcher.py`
  cannot call, because it does not know which implementation it got.
  `test_the_local_board_adds_nothing_to_the_shared_surface` holds that line.

## Verified

- `python3 -m pytest` from the repository root: **784 passed, 10 skipped**. The
  skips are `tests/integration/test_agent_entrypoint.py`, which wants a built
  agent image and docker on `PATH`; they predate this task.
- The suite is the whole of the evidence. No real `dispatch` run has used
  `local_board`, and the live `config.yaml` is on the host, outside every
  clone — so the operator-facing claim this task can make is "the client does
  what its tests say", not "the board has been watched moving".
