# T-028 — the board seam is removed

This task builds step 2 of `docs/plans/board-service.md`, *How it would be
built*. The client module, its three clients, the client factory in the CLI,
both config blocks and `kanban_issue_id` are gone. The decision is
`docs/decisions.md` ADR 59, appended by this task's arquitecto; it supersedes
ADR 1 to ADR 4. Nothing in the tree opens, moves or mirrors a card any more.

## Verified first-hand, not taken from the card

| Card's claim | Where | Verdict |
|---|---|---|
| The client module holds `KanbanClient`, `NullKanbanClient`, `VibeKanbanClient`, `LocalBoardClient` | the deleted module | true (and `KanbanIssue`) |
| `_kanban()` picks the client, `_seed_kanban_issue_id` seeds the id | `dispatcher/cli.py` | true |
| `open_cycle` opens a card | `dispatcher/dispatcher.py`, through `_open_kanban_issue` | true |
| `_update_task_status` moves the card **and updates the task file** | `dispatcher/dispatcher.py` | **half false**, see below |
| `tasks.set_kanban_issue_id`; `TaskFile.kanban_issue_id` | `dispatcher/tasks.py`, `dispatcher/context_transfer.py` | true, plus `read_kanban_issue_id` |
| The debt filing creates a card per entry | `_file_accepted_debt` | true |
| The api serves `card` and `kanban_issue_id` | `observability/api/app.py`, `_task` and `_read_cards` | true |
| No live task file has a `kanban_issue_id:` line | the live hive tasks dir | true: `grep -rln "^kanban_issue_id:"` over it printed nothing (read-only) |
| `config.yaml` configures neither board | the live config | **not verifiable from a phase**: the file is outside the directories a phase may read |

Different from the card:

1. **`_update_task_status` never wrote the task file.** Its whole body was
   `kanban.set_status`. A task file's `status` is written by `tasks.handoff`
   and `tasks.acquire_lock`. So the card's "keeps updating the task file and
   stops at that" has nothing to keep: the function and its eleven call sites
   are deleted, and the task file behaves exactly as before. A cycle that
   stops blocked still writes no `blocked` anywhere; its record is the log
   line and the exit code (ADR 52). Declared as found debt.
2. **Two more card movers the card does not name.** `close_resolved_debt`
   (called by the cycle after a merge and by `merge-task`) and
   `debt.card_ids` closed the cards of resolved debt. Both are deleted;
   `merge-task` prints nothing about debt now.
3. **`vibe_kanban_mcp_url`** was already a refused key. It stays refused,
   under the same message as the two blocks.
4. `docs/README.md` had a Modules row for the deleted module. The card does
   not name the file; it is edited because it is a present doc.

## What changed

- **Deleted:** the client module and its test file.
- **`dispatcher/config.py`:** `VibeKanbanConfig`, `LocalBoardConfig`, the
  status map and the three loaders are gone, with the two `Config` fields.
  `_refuse_board_keys` raises `ValueError` for any of `REMOVED_BOARD_KEYS`
  present in the file, naming the key and ADR 59. Presence, not truthiness:
  `local_board:` left empty is still an operator expecting a board.
- **`dispatcher/context_transfer.py`:** `TaskFile` loses the field, the
  reader and the serializer lose their lines, `read_kanban_issue_id` goes.
- **`dispatcher/tasks.py`:** `set_kanban_issue_id` goes.
- **`dispatcher/dispatcher.py`:** `_issue_title`, `_open_kanban_issue`,
  `_update_task_status`, `close_resolved_debt`, `CycleContext.kanban` and
  `.issue_id`, and the client argument of `open_cycle`, `run_task_cycle`,
  `run_single_phase` and `_file_accepted_debt` go. Every log line that sat
  beside a removed call stays. `_file_accepted_debt` returns
  `list[tuple[str, debt.Declaration]]`.
- **`dispatcher/cli.py`:** `_kanban`, `_seed_kanban_issue_id`, the
  `--kanban-issue-id` flag and the card-closing block of `merge-task` go.
- **`dispatcher/debt.py`:** `card_title`, `card_description`, `card_ids`,
  `LABEL` and `TITLE_MAX` go (no other caller). `COLUMNS`, `index_rows` and
  the `card` key it returns are untouched. `filing_note` takes the two-item
  tuples and tells the auditor to write `none` in the `card` column.
- **`observability/api/app.py`:** `_read_cards` and the remote-board warning
  go; `_task` returns eight keys (nine with `body` on the detail route).
- **Config surfaces:** `config.example.yaml` and `scripts/configure.sh` no
  longer offer a board.
- **Compose:** the `vibe-kanban` service, its `kanban` profile, the
  `vibe_kanban_data` declaration and the two "Not vibe-kanban" comments are
  gone from both files.

## Decisions taken while building

- **One message for three keys.** A per-key message would be three strings
  saying the same thing. The test pins the key's name, the phrase "the board
  seam was removed" and "ADR 59".
- **The key drop is silent, on purpose.** `read_task_file` ignores a
  `kanban_issue_id` it finds, and the next writer drops it. This is the trap
  `docs/learnings/dropping-a-key-from-read-task-file-deletes-it-on-the-next-write.md`
  names, taken deliberately: the value has no reader left, so there is
  nothing to move first. A malformed value under the key (a mapping) used to
  cost the task its api row; it now costs nothing, and a test holds that.
- **The filing note says `none` once, not per entry.** The old per-entry
  "(no card (this project has no board))" was prose an auditor copied into
  the column (inbox entry
  `T-024-the-filing-notes-no-card-phrase-is-prose-not-an-id`). The note now
  gives the literal value to write.
- **Tests keep their evidence.** About fifty dispatcher tests used the fake
  board's status list as the only proof of how a cycle ended. Each such
  assertion became the cycle's own return (`CycleOutcome.FINISHED`,
  `BLOCKED`, `HELD`), or, for `run_single_phase`, its result plus the task
  file's status. None was deleted without a replacement. Tests whose only
  subject was a card were dropped: opening, reusing or being refused one,
  the title, a client that raises, a card per debt, closing on merge.
- **The two malformed-`kanban_issue_id` api tests.** The list route still
  has `test_frontmatter_json_cannot_serialise_is_a_warning_and_not_a_500`
  for "a value that fails at the use costs one row a warning". The detail
  route had no other, so its test was retargeted to an unserialisable
  `owner` rather than dropped.

## Ruled out

- **Making `_update_task_status` write `blocked` to the task file.** It
  would satisfy the card's sentence and change lock and re-run behaviour
  nobody asked for. The plan's sections 4 and 6 own that write.
- **Ignoring a leftover config block with a warning.** An operator would
  keep watching a board no run moves (ADR 2's argument, which survives).
- **Removing the index's `card` column.** The api and the console read it;
  step 5 of the plan puts a backlog item's id there.
- **Striking ADR 1 to ADR 4's headings.** The card forbids editing an
  earlier entry; ADR 59's status line is the pointer.

## What an operator should know

- A `config.yaml` that still has `vibe_kanban`, `local_board` or
  `vibe_kanban_mcp_url` stops the dispatcher and the api at startup, with
  the key named. Delete the key.
- **Removing the `vibe_kanban_data` declaration deletes no volume.** A host
  that ever ran the `kanban` profile keeps the volume until someone removes
  it by hand.
- `run-task --kanban-issue-id` is now a usage error.

## Left undone, declared as debt

- `front/` still declares `KanbanIssue`, `card` and `kanban_issue_id` on a
  task, and its fixtures return them (out of scope by the card).
- The root `README.md` still describes the optional board, the flag, both
  config blocks and the compose service; `pyproject.toml` and
  `docker/agent/Dockerfile` still install `mcp`, and the Dockerfile's
  comment names the deleted module.
- Nothing writes `blocked` to a task file (found, not introduced).

For the auditor: `docs/learnings/the-kanban-seam-is-a-closed-surface.md`
describes a surface that no longer exists, and the paragraph after the table
in `docs/debt/README.md` still speaks of a board's card id. Those are its
indexes.

## Round 2: the prompt text the first round missed

The revisor found that round 1 grepped for the module's name and so missed
prose the dispatcher hands to agents. Fixed:

- `dispatcher/project_docs.py` `_AUDITOR` told the auditor that filed
  debt's "cards are already on the board", in the same prompt where
  `debt.filing_note` says to write `none` in the `card` column. It now gives
  the real reason the auditor files only what it is handed: the dispatcher
  assigns the ids so a re-run names the same entry the same way.
- `dispatcher/project_docs.py` `_IMPLEMENTADOR` said `resolved_debt` closes
  "the entry, and its card". It now says what happens: the ids are recorded
  in the task file (`tasks.set_resolved_debt`) and the auditor marks each row
  resolved.
- `dispatcher/handoff.py`, the `ruling` description under `debt_rulings`:
  "filed and put on the board" is now "filed in the debt index". The module
  docstring's "debt card" is "debt entry".
- `docs/business.md`, first rule under "Reading the harness's state": it
  described `card` and `kanban_issue_id` in the present tense and cited ADR 3.
  Rewritten against ADR 59. Round 1 left it to the auditor, wrongly: the
  auditor owns the two indexes, and this is a doc whose contract this task
  changed.

The tests assert the phrases ("on the board", "its card", "their cards") and
not the word, because these prompts also call the task file a card.
