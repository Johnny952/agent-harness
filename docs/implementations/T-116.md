# T-116 — one cycle per project

Decisions are ADR 200 in `docs/decisions.md`; this is how it was built.

## What changed

- `dispatcher/project_lock.py` (new): `ProjectLock.take` / `release`,
  `ProjectBusy`, `project_lock_path`. A non-blocking `flock` on
  `<state_dir>/project-locks/<slug>.lock`; the holder writes one JSON line so a
  refused start can name it. `release` truncates before closing so it cannot
  wipe the next holder's record; the file is never removed.
- `dispatcher/dispatcher.py`: `open_cycle(project_lock=, via=)` takes the lock
  after its last refusal and before it writes the description;
  `CycleContext` carries it and `owns_project_lock`; `close_cycle` releases in
  a `finally` around the old body (now `_close_cycle`), so the foreign-lock
  early return releases too. `run_task_cycle` and `run_single_phase` thread
  `project_lock` and `via`.
- `dispatcher/command_run.py`: `run_command_request` / `resume_command_verdict`
  open through the same seam; a busy project refuses before the verdict is
  recorded.
- `dispatcher/worker.py`: `_consider` takes the lock for a `project:` serial
  key, waits as `project` when busy, releases on an account wait or a lost
  claim; the lock rides on `Running` to the handler, which passes it to the
  cycle and releases it in `_run_handler`'s `finally`.
- `dispatcher/queue.py`: `run` polls for the lock, holds it for the whole run
  and passes it to every cycle in both the serial and the parallel path.
- `dispatcher/cli.py`: the four cycle verbs print
  `<ProjectBusy>; <task> was not started` and exit `EXIT_HELD` (75).

## Why this way

- One seam (`open_cycle`) rather than a lock in each verb: a library caller
  cannot skip the rule. A caller that already holds the lock passes it and the
  cycle neither takes nor releases it, which is how the worker and a parallel
  queue share one lock between several cycles without deadlock (ADR 83 write
  windows are untouched).
- The CLI exits instead of waiting (ADR 200, 5); the queue polls, as it already
  does for accounts.

## Ruled out

A presence-means-busy file or a heartbeat lock (needs a reaper after a crash);
a blocking `flock` (a thread would sleep in the kernel); one lock per cycle in
a parallel queue (the queue would serialise itself).

## Tests

`tests/dispatcher/test_project_lock.py` (lock, dead process via a real
subprocess killed with SIGKILL, cycle open/close, revision round, CLI exit 75,
queue `--parallel 1` and `2` with a barrier proving two cycles run at once),
plus two cases in `tests/dispatcher/test_worker.py`. The existing fakes of
`run_task_cycle`/`open_cycle` in the queue and worker tests gained a
`project_lock` parameter.

Not run in a container: nothing here touches docker.
