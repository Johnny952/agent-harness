# T-142 — filtered learnings

Decision: `docs/decisions.md` ADR 315. This is how it was built.

## What was built
- `dispatcher/learnings.py`: `TaskContext` (frozen, `paths` and `tags`,
  `usable`), `NO_CONTEXT`, `task_context`, `select`; `table(..., filtered=)`
  and `duties(..., context=NO_CONTEXT)`.
- `dispatcher/dispatcher.py`: the one `learnings.duties` call in
  `_role_prompt` passes `context=learnings.task_context(...)`.
- `tests/dispatcher/test_learnings.py`: path, directory and basename match,
  tag whole-word match, harness/reviewed rows kept, no match, only-a-kept-row
  match, no context, trailer wording, `task_context` reads.
- Root `README.md` Future work item 1 bullet flipped to built.

## Why this way
- `select` is pure and falls back to `list(entries)` for an unusable context
  or when no non-kept row matches, so the worst case is today's table.
- Filter, then cap: `table` still orders and cuts, and counts the two
  separately in the trailer. With `filtered=0` the trailer is the old line.
- `task_context` never raises: it runs inside `_role_prompt`, and a bad card
  or handoff must cost a filter, not a dispatch. Paths come from the
  description (`surface.parse`) and the arquitecto handoff's `paths`; tags
  from the card.
- "Profile" is the project, which `eligible` already applies.

## `/api/learnings`
Untouched. `in_phase_table` is `handed(eligible(...))`, i.e. the unfiltered
table, which is what a no-context or no-match phase gets (ADR 315 decision
5). A filtered phase gets a subset. Per-task answer is debt (`?task=`).

## Ruled out
- Tags/paths in entry frontmatter (format out of scope; old entries match
  nothing).
- The role as a profile (always "usable", role names are prose everywhere).
- Making the api select per task (it has no task).
