# T-067 — the Settings screen's controls: save and reset with the revision (console-config task 3, second half)

Decisions: `docs/decisions.md` ADR 114 (the writers, one write at a time and
the refetch, the controls by key and kind, where a refusal is shown).

## What was built

- `front/src/lib/api/client.ts`: `readEnvelope` takes an optional
  `{method, body}` and sends it as JSON; `putSetting(key, value, revision)`
  (PUT `{value, revision}`) and `resetSetting(key, revision)` (DELETE
  `{revision}`), the key one encoded segment.
- `front/src/lib/api/types.ts`: `Settings.base`, `overrides` and `revision` are
  nullable, as the writer serves them.
- `front/src/lib/api/queries.ts`: comment only; `settingsQuery` still has no
  poll and is invalidated after every write.
- `front/src/routes/models.tsx`: one page-wide mutation; every control disabled
  while it is pending or the read is fetching. Per editable row a control by
  key (`role_model`, `role_effort`, `fallback_roles`, `primary_account`) or by
  `kind` (`bool`, `effort`, `positive_int`, `non_negative_int`, `string`),
  *Save*, and *Reset* when the source is `override`. The 409 banner with its
  refetch and the drafts dropped; any other refusal quoted on a
  `<tr data-refusal>` under its row with the value kept; the broken-config
  banner's *Reset* per overridden key, none when `overrides` is `null`.
- `front/src/test/render-route.tsx`: answers keyed `"<METHOD> <path>"` before
  the bare path, a list answered in order with the last repeating, and `sent`
  (method, path, parsed body) returned with the render.
- `front/src/routes/-models.test.tsx`: rewritten on real `CONFIG_KEYS` rows and
  kinds, 32 cases: the read-only ones kept, plus every *Done when* test
  (banner *Reset*, save with the revision and `revision: null`, 422 under its
  row, 409 banner and refetch, Reset as DELETE and its refetch, *(default)*
  taken out of `role_model` with the whole map sent, disabled while in flight,
  no control on read-only, credential or unreachable).
- Docs: ADR 114; *Built* note on task 3 of `docs/plans/console-config.md`;
  `front/AGENTS.md` and `front/README.md` no longer say read-only.

## Why this way

- One write at a time, with the page disabled, means a write always carries
  the revision of the table on screen; a second write never races the first's
  refetch.
- The refetch is a read rather than the write's envelope, so what is shown is
  always what `GET /api/settings` serves.
- Ranges and values are left to the writer's 422, quoted verbatim: the front
  only refuses an empty or non-whole number, which it cannot even serialize as
  the kind asks.
- Native `<select>`, because the Tail, Index and Sessions screens already use
  it and it is testable with `fireEvent.change`.
- An input with a `datalist` is a `combobox` to assistive tech, not a textbox;
  the tests query it so.

## Pending for the follow-up

Nothing on task 3. `MODEL_OPTIONS` and `initialRoleModels` (with their types
`ModelOption` and `RoleModelConfig`) remain unused in
`front/src/lib/api/mock/ops-fixtures.ts` and `front/src/lib/api/ops-types.ts`,

## Ruled out

- Radix Select: a second select idiom in the console, and harder to drive in
  jsdom, for no gain over the native one.
- Setting the query data from the write's answer: it would show a table no
  read served.
- Restating `CONFIG_KEYS`' ranges in the front: two sources of truth that can
  drift; the writer's 422 is the one.
- A per-row mutation: concurrent writes on one revision would turn every one
  but the first into a 409.
