# T-056 — two phases at once on one Max account

The verdict is in `docs/decisions.md` ADR 84. This entry records how it was
measured and what was measured.

## What

- Account: cuenta1 (Max x5), the only configured account, measured on
  2026-10-17. The owner authorized the quota.
- Method: the owner chose a controlled run over dispatched phases, since the
  dispatcher refuses a second phase on a `BUSY` account. Each run was
  `docker exec -w /data/projects/ia-harness agent-cuenta1 timeout
  --kill-after=30 1500 claude --model claude-opus-5-5 --max-turns 80
  --allowed-tools Read Grep Glob -p PROMPT --output-format json`. That is the
  command line `dispatcher/docker_exec.py` builds, with the tools restricted
  to reads. Every run used the same prompt: read `dispatcher/dispatcher.py`,
  `queue.py`, `state_machine.py` and `tasks.py` in full, then describe each
  top-level function and its callers, list every path that leaves an account
  `BUSY` or a task locked, and give counts. Each run lasts about six minutes.
- Order: the probe, then three rounds of one solo run, the probe, a
  concurrent pair (both runs started together, `&` and `wait`), and the
  probe. Solo and pair runs alternate, so drift in the service's speed over
  the hour reaches both.
- Figures come from each run's JSON result (`duration_ms`, `num_turns`,
  `usage`, `is_error`, `api_error_status`). There is no
  `.hive/tasks/<id>/usage/calls.jsonl` here, because no phase was dispatched.
  The `/usage` percentages come from `status --probe`.

## Results (round 2, the one the verdict uses)

| run | wall s | turns | output tokens | cache read | s per 1k out | error |
|---|---|---|---|---|---|---|
| solo-1 | 356.6 | 29 | 41,792 | 2.94M | 8.53 | none |
| solo-2 | 454.8 | 29 | 48,821 | 2.59M | 9.32 | none |
| solo-3 | 349.8 | 30 | 41,943 | 2.76M | 8.34 | none |
| pair1-a | 427.8 | 34 | 47,623 | 2.86M | 8.98 | none |
| pair1-b | 377.2 | 26 | 38,437 | 2.38M | 9.81 | none |
| pair2-a | 358.9 | 27 | 42,800 | 1.83M | 8.39 | none |
| pair2-b | 513.9 | 31 | 61,343 | 2.56M | 8.38 | none |
| pair3-a | 401.8 | 32 | 47,440 | 2.82M | 8.47 | none |
| pair3-b | 392.9 | 29 | 41,740 | 1.97M | 9.41 | none |

- Median wall time: 356.6 s solo, 397.4 s concurrent, so **+11.4%**.
- Normalized by output (s per 1k output tokens): 8.53 solo, 8.73 concurrent,
  so +2.3%. Most of the wall-time difference comes from runs that wrote
  more, such as pair2-b with 61k tokens, not from running beside another
  session.
- Throughput: a pair finished both runs in 429.7, 515.8 and 403.8 s of wall
  clock (median 429.7). Two solo runs back to back take about 715 s, so a
  pair does the same work in about 60% of the time, roughly 1.66×.
- Refusals: none. Every run exited 0, with `is_error` false,
  `api_error_status` null and an empty stderr. No 429 and no rate-limit
  retry was seen.
- `/usage`, session window: 20 → 22 (solo-1) → 27 (pair 1) → 30 (solo-2) →
  36 (pair 2) → 39 (solo-3) → 45 (pair 3). A solo run costs 2–3 points and
  a pair 5–6, so two at once costs the same as two in a row. Concurrency
  saves wall time and spends no less quota.
- `/usage`, week: 3 → 4%. The weekly window reset between the pair-2 and
  solo-3 probes, so it read 0% from there on.

## Round 1 (inconclusive, kept for the record)

A shorter prompt, one baseline and one pair: baseline 39.9 s with 10 turns;
the pair ran 58.0 s (+45%) and 37.3 s (−7%). Runs this short with a single
sample are mostly noise, so round 2 repeated the measurement with longer
runs and three of each.

## Limits

- Read-only work, with no tests, builds or git. A real implementador spends
  part of its time on local commands, which share the container's CPU and
  not the API, so its slowdown may differ either way.
- Three solo runs and six concurrent ones on one afternoon. That is enough
  to tell +11% from +50%, not +11% from +5%.
- One Max x5 account. A Pro account was out of scope (the plan gives this
  measurement no value there).
