# T-109 — thread records and thread models

Contract: `docs/decisions.md` ADR 169 (config) and ADR 170 (store, routes).

## What was built

- `dispatcher/config.py`: `AccountConfig.models`, `Config.thread_models`,
  `Config.thread_models_for`, one `_check_models` for both keys, and an
  editable `list` row for `thread_models` in `CONFIG_KEYS`.
  `config.example.yaml` documents both keys.
- `dispatcher/threads.py`: `create`, `read_thread`, `read_threads`, `update`.
  Writes use `context_transfer._write_atomic` under
  `tasks.task_lock(hive_dir, "_thread-<id>")`.
- `board_service/app.py`: `POST /api/threads` and `PATCH /api/threads/<id>`
  through `_thread_http`, which keeps `_http`'s three guards and order and adds
  the field-name and JSON-type checks. No bearer: they spend no quota.
- Tests: `tests/dispatcher/test_config.py` (extended), `test_threads.py`,
  `tests/board_service/test_threads_routes.py`.

## The main-thread choice

The main thread is the record with the id `main`; no field marks it. A second
one cannot exist because there is one file name for it, and the existence
check and the write are one step under the `_thread-main` lock. It is made on
request (`create(main=True)`), never at boot or by a reader: neither service
writes the hive on start, and the read api cannot write. Its `task` and
`project` are null and refused if given; it cannot be archived.

Ruled out: a `main: true` field (settable on two files); creating it at boot or
on first read (a write nobody asked for).

## Choices worth knowing

- An account change refuses a model not in the new account's list instead of
  repicking: the person chooses model and quota together.
- The model list is validated at load only; nothing is probed.
- Ordinary ids are `th-<UTC timestamp>-<6 hex>`; any other path id is a 404,
  so no path component is built from an id the module did not make.
- Statuses are `open` and `archived`; steps 3 and 4 may want more.
