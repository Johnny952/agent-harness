# T-136 — serialize the learnings carry

Decision: `docs/decisions.md` ADR 294.

## What

`dispatcher/learnings.py`:
- `_carry_lock(hive_dir, project)`: flock on `<learnings root>/.carry-<project>.lock`,
  a fresh descriptor per acquisition (as `adr_numbers._locked`), so threads of one
  `run-queue` exclude each other. A slug that is not one path component raises
  `ValueError`. The dot prefix keeps the file out of `read_dir`.
- `carry` runs its read and every claim under that lock.
- `_carrier_is_live` + `_LIVE_CARRIER_STATUSES`: an entry stamped by a task whose card
  has an owner, or is `awaiting_review`/`conflict`, is left alone. A lock alone would
  not stop a double filing, since `carry` overwrites a foreign `carried_by` on purpose.

## Tests (`tests/dispatcher/test_learnings.py`)

Two threads on a barrier carry six entries with a slowed `_write`; the lists are
disjoint and cover all entries. Verified the test fails (twelve claims) with the lock
swapped for `nullcontext`. Plus live/dead carrier cases, a pin of the status literals
to `tasks` constants, and the bad-slug case.

## Ruled out

- Reusing ADR 200's project lock: the queue holds it for all parallel cycles.
- Importing `tasks` for the constants: the module imports only `context_transfer`.
- Locking `mark_orphaned`/`drop_promoted`: out of surface (debt proposed).
