## What the code says, for each wording

Each README sentence below is written from these, not from the
implementation docs. The implementador re-reads the symbol before writing
the sentence.

- **Exit codes.** `main` in `dispatcher/cli.py`, the `run-task` branch:
  `CycleOutcome.HELD` exits `EXIT_HELD`, `BLOCKED` exits `EXIT_BLOCKED`
  after `task <id> is blocked; the log above says why` on stderr, `SPLIT`
  prints `_epic_line` to stdout and exits `EXIT_SPLIT`, anything else
  falls through to 0.
- **`_epic_line`** prints `task <id> is now an epic: <ids>; run them in that
  order`, the ids being the task file's `split_into`.
- **What `open_cycle` refuses** (`dispatcher/dispatcher.py`), each returning
  None so `run_task_cycle` returns BLOCKED with nothing written: a task
  whose file says `status: epic` (`task <id> is an epic, split into <ids>:
  run its sub-tasks, not the epic`), and one with reasons from
  `tasks.unmet_dependencies` or `tasks.epic_problems` (`task <id> cannot
  start: <reasons>`). `run_single_phase` goes through `open_cycle` too.
- **A split that could not be filed.** `_file_split` returns BLOCKED after
  `task <id>: the split cannot be filed: <problems>`; `run_task_cycle`
  then returns `blocked()`, which marks.
- **Which stops write `status: blocked`.** `_mark_blocked`: only when a
  phase of this run took the lock (`ctx.took_lock`), no foreign lock was
  met, the task file exists and has no owner. The table in
  `docs/implementations/T-030.md`, *Blocked: which return points mark, and
  why*, matches `run_task_cycle` as read today, plus the unfiled split.
- **The merged record.** `record_merge` in `dispatcher/dispatcher.py`,
  called by the cycle's merge and by the `merge-task` branch of `main`
  when the outcome was not refused. It returns the lines `task <id>:
  recorded as merged into <target>` and, when `tasks.close_epic` closed a
  parent, `epic <id>: every sub-task is merged, so it is done`. `merge-task`
  prints them to stdout, a problem to stderr, and still exits 0. An
  up-to-date branch writes the block only when the file has none.
- **`run-phase --role arquitecto`.** `_print_proposed_split` in
  `dispatcher/cli.py`: `phase arquitecto proposes splitting task <id> into
  <n> sub-tasks; nothing was filed:`, the numbered entries, then the
  `file-split` command to run. Exit stays 0.
- **`file-split`.** The `file-split` branch of `main` and
  `file_saved_split`: reads the saved arquitecto handoff, runs no model,
  prints the epic line and exits 0 when it filed; prints `task <id>: the
  split was not filed; the log above says why` to stderr and exits
  `EXIT_BLOCKED` when it refused. What it refuses is in the parser's help
  text and in `_file_split`.
- **A board key in `config.yaml`.** `_refuse_board_keys` in
  `dispatcher/config.py`: `vibe_kanban`, `local_board` and
  `vibe_kanban_mcp_url` (`REMOVED_BOARD_KEYS`) each raise at load, naming
  the key and ADR 59.
- **`--kanban-issue-id`.** Not an argument of any parser, so argparse exits
  2; `test_cli_run_task_no_longer_takes_a_kanban_issue_id` in
  `tests/dispatcher/test_cli.py` holds it.

### Exit codes and the new verbs

Under "`run-task`'s exit code says how the cycle ended", cite ADR 52 and
ADR 60 and make the table:

| Code | The cycle | What to do |
|---|---|---|
| 0 | as it is | as it is |
| 75 | as it is | as it is |
| 3 | split: the arquitecto split the task and the split was filed. The task file says `status: epic`, and stdout has `task <id> is now an epic: <ids>; run them in that order` | run each sub-task with `run-task`, in that order; nothing runs them for you |
| 1 | blocked: what it lists today, plus a split that could not be filed, and a task refused before it started: one whose `depends_on` names a task that is not merged or that is a child of a malformed epic (`task <id> cannot start: <reasons>` in the log), or one whose file says `status: epic` | read the log; a person decides |
| 2 | as it is | as it is |

Replace "The card is blocked either way, so it is the code and the log, not
the board, that tell held from blocked" with the `blocked` rule: a cycle
that stops blocked after one of its phases took the task's lock writes
`status: blocked`, with no owner, to the task file (a failed phase, the
arquitecto's block, the rounds running out, the revisor's block, the auditor
failing, an unfiled split). A held cycle, a task refused before it started,
a diverged project branch, another run's lock and a task with no file leave
the file as it was, and so does `run-phase`. So `blocked` there means a
cycle ran and stopped, not every exit 1.

`merge-task` passage, after "A branch already merged is reported as up to
date": a merge that lands is recorded on the task file as a `merged` block,
which is what another task's `depends_on` waits for (`done` is not enough);
`merge-task` prints `task <id>: recorded as merged into <branch>`; merging
an epic's last sub-task sets the epic `done` and prints `epic <id>: every
sub-task is merged, so it is done`; an up-to-date re-run writes the block
only where there is none, which is how a task merged before the record
existed gets one; a record that could not be written goes to stderr and the
exit is still 0. In the `merge_on_done` paragraph, one clause: the cycle's
own merge records the same thing.

`run-phase` passage: "the account and card locks" becomes the account and
task locks; "`status: done` in the task file and on the board" loses the
board; "exits non-zero and blocks the card" becomes exits non-zero, with
the task file not written `blocked`. Add: the same refusals as `run-task`
apply (an epic, an unmet dependency), and `run-phase --role arquitecto`
prints a split the phase proposed and files nothing, naming `file-split`.

**The block, before anything is written.**: "the card goes `blocked`"
becomes the task file. After it, a new paragraph, **The split, when the
task is more than one.**: a non-empty `split` in the arquitecto's handoff,
two to four sub-tasks; a block wins over a split; the dispatcher files one
`<task-id>-S<n>` task per entry with its own description, `depends_on` and
`epic`, sets the parent to `status: epic` with `split_into`, and stops
before the implementador with exit 3; nothing is dispatched for you; a split
that cannot be filed blocks the task. Then the verb, in a code block like
its neighbours:

```bash
python -m dispatcher.cli --config config.yaml file-split \
  --task-id T-001 --project my-project
```

It files the split of the saved arquitecto handoff without running a model,
prints the same epic line and exits 0; it exits 1 when it refuses: no saved
handoff, a blocked one, no split or an invalid one, a task that is `done`,
already an epic or still locked by a live run. Point at ADR 60.
