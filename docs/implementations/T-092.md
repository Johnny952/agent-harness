# T-092 — The api's task rows carry the epic fields, `merged` and a title

Decisions: `docs/decisions.md` ADR 137. It covers:
- `epic`, `split_into`, `merged` and `title` on `_task`, so on both task
  routes;
- one title rule, `dispatcher/tasks.py:display_title`, shared with the
  board-service;
- a non-list `split_into` served verbatim, with no api warning.

## What was built

- `dispatcher/tasks.py`: `DISPLAY_TITLE_CHARS` (100) and
  `display_title(title, description)`, moved from
  `board_service/app.py:_title`. It takes the raw frontmatter `title`,
  which is what `TaskFile.title` holds.
- `board_service/app.py`: `_title` is now a call to `display_title`, and
  `TITLE_CHARS` is `task_store.DISPLAY_TITLE_CHARS`. Both names still work.
- `observability/api/app.py:_task`: `epic`, `split_into`, `merged`
  (`bool(task.merged)`) and `title`, each with its source and ADR. The
  docstring names the two derived ones.
- `docs/README.md`: the api row names the new task fields.
- Tests, `tests/observability/test_api.py`: the two whole-row tests carry
  the four keys; an epic's `split_into` and a sub-task's `epic` on both
  routes; `merged` true for a merged task and false otherwise; the title
  from frontmatter (stripped), from the Goal, cut at
  `DISPLAY_TITLE_CHARS`, and null with no description or a description
  not in sections; the api and the board-service give the same title; a
  non-list `split_into` served as written with no warning.
- The whole suite passes: 3091 passed, 10 skipped.

## Why this way

- `dispatcher/` is copied into both the api and the board-service images,
  so a rule there needs no Dockerfile change.
- `TaskFile.title` is the frontmatter value, so the api reads no second
  frontmatter.
- `field_problems` feeds `dispatch_problems`. A `split_into` check there
  would change what the dispatcher refuses; `epic_problems` already names
  it.
