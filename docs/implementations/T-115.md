# T-115 — The slots in the dock and in the *Start development* confirmation

Design: `docs/decisions.md` ADR 198. This note is how it was built.

## What was built

- `front/src/lib/slots.ts`: `deriveSlots(accounts, tasks, queue)`, `standingLine`,
  `waitingText`, `resetText`. Pure; the only place a slot is decided.
- `front/src/components/console/slots.tsx`: `SlotsPanel`, read-only, from the
  three shared queries; mounted in `chat-panel.tsx` right under the selector row.
- `front/src/routes/index.tsx`: `BoardPage` derives `standing` once and passes it
  to `StartControl`, which draws it between the description and the note.
- Tests: `front/src/lib/slots.test.ts` (derivation and every `standingLine` arm),
  the "slots region" block in `front/src/components/console/chat-panel.test.tsx`,
  three cases in `front/src/routes/-index.test.tsx`.
- Plans: `projects.md` step 6 and `main-thread.md` step 7 marked built;
  *Waiting for the project* named open.

## Choices

- A slot's emptiness is `state === "IDLE"` and its task is read only on `BUSY`.
  A BUSY account with no `current_task` is a busy slot with "task not recorded",
  not a free one: the first draft counted it free and a test caught it.
- The primary's reset for a parked slot is the probe's raw clause, never parsed;
  *Waiting for an account* compares only epoch resets (provider cooldowns).
- The queue is guarded as `unknown`, as `front/src/lib/thread.ts` does; a failed read is
  passed as `null`, so "not known" is a state of its own, never an empty list.

## Ruled out

- A backend route, re-deciding "under threshold" from `last_probe`, and parsing
  reset clauses (ADR 198, *Ruled out*).
- A second copy of the derivation in the Board: the page calls `deriveSlots`.

## Test-fixture trap

The api serves `current_task`; `client.ts` maps it to `current_task_id`. A stub
that serves `current_task_id` is silently read as no task.
