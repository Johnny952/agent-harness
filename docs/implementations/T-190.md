# T-190 — a dependency on a split task clears once its sub-tasks merge

Resolves debt `T-188-D1`. Decision: `docs/decisions.md` ADR 504.

## What I did

- `dispatcher/tasks.py` `_split_waits_on(dependency, is_merged)`: pure; `None`
  when the dependency is not a split parent (`split_into` non-empty list and
  `epic` unset), else the `split_into` ids not merged, in order.
- `unmet_dependencies`: a non-merged dependency that is a split parent is met
  when `_split_waits_on` is empty (sub-task files read with `_read_for_check`;
  a missing or unreadable one counts as not merged). Otherwise the line is
  `<dep> is split; <ids> not merged yet`. Other messages are unchanged.
- `ready_order`: same rule over the in-memory `tasks` dict, via the same helper.
- Tests: `tests/dispatcher/test_tasks.py` (unmet lines, partial merge, all
  merged then `close_epic`, dropped sub-task, empty `split_into`) and
  `tests/dispatcher/test_board_order.py` (ready order).
- Docs: `docs/README.md` row, the learning
  `docs/learnings/a-dependency-on-a-split-task-never-clears.md`.

## Why this way

One helper for both readers so the file-reading gate and the Ready column
cannot disagree. A dropped sub-task holds the dependent (ADR 504): the owner
re-points it by hand.

## Ruled out

- Writing `merged` on the parent in `close_epic`: ADR 495 ruled it out; a
  parent never merges.
- Changing `dispatcher/queue.py`: its re-pointing and ADR 498 wait stay.
