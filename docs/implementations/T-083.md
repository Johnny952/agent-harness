# T-083 — Each phase gets its config (board-service step 7)

Decisions: `docs/decisions.md` ADR 128. It covers where the role table
lives (in the dispatcher, with the service importing it), which phases get
the board's `--mcp-config` (only a role with tools), how the tools are
allowed, and the `board_mcp_url` config key.

## What was built

- `dispatcher/board_mcp.py` (new). It imports nothing from the package.
  - `ROLE_TOOLS` and `OPERATOR`, moved from `board_service/app.py`.
  - `SERVER_NAME` is `board`, and `DEFAULT_URL` is
    `http://board-service:8792/mcp`.
  - `allowed_tools(role)` gives the `mcp__board__<tool>` names, or none.
  - `mcp_config(url, role)` gives compact JSON: one `http` server named
    `board` at `<url>?role=<role>`, with the role URL-encoded.
- `board_service/app.py`: it now imports `OPERATOR` and `ROLE_TOOLS` from
  `dispatcher.board_mcp`. Nothing else changes.
- `dispatcher/config.py`:
  - `board_mcp_url` in `Config`, `DEFAULT_URL` by default;
  - a read-only row for it in `CONFIG_KEYS`;
  - `_load_board_mcp_url`. An absent key gives the default, and `null`,
    `""` or whitespace gives `None` (off). The value is stripped. A
    non-string, a URL that is not http or https, and a URL with a query or
    a fragment are refused.
- `dispatcher/docker_exec.py`: `exec_claude(..., mcp_config=None)` emits
  `--mcp-config <json>` after `--json-schema` and before `--add-dir`, ahead
  of `-p`. Nothing is emitted for `None` or `""`.
- `dispatcher/dispatcher.py`: when `board_mcp_url` is set and the role has
  board tools, `_phase_permission_flags` adds `mcp_config`. It also
  appends the board names to `allowed_tools` after the configured list and
  the project allowlist, with no repeats. The dict is already splatted
  into every phase call and every resume, so nothing else changes.
- `config.example.yaml`: a commented `board_mcp_url` after `collector_url`.
- Tests:
  - `tests/dispatcher/test_board_mcp.py` (new, 18 tests):
    - the service and the dispatcher hold one table (`is`), and the
      default URL uses the service's `PORT`;
    - the tool names, the JSON's shape, and the role's quoting;
    - the URL written is one the service's own handler accepts
      (`tools/list` through its test client);
    - the arquitecto gets the server and both names;
    - every other phase role gets neither, and its flags equal those of a
      config with the URL off;
    - turned off (`None`, `""`), the arquitecto gets neither;
    - a configured URL is the one written;
    - the names follow the project allowlist with no repeat;
    - a dispatched arquitecto phase, fresh and resumed, carries the
      config, and a revisor phase does not.
  - `tests/dispatcher/test_config.py`:
    - the default;
    - null, empty and whitespace turn it off;
    - the value is stripped;
    - refusals for an int, a list, no scheme, a query and a fragment;
    - the row is read-only;
    - the key-coverage test includes the key.
  - `tests/dispatcher/test_docker_exec.py`:
    - the value goes as one argument before `-p`;
    - nothing is emitted for `None` or `""`;
    - it stays apart from `--add-dir` and `--allowed-tools`.

## Why this way

- **The table in the dispatcher.** The service imports `dispatcher`, so
  the reverse import would be a cycle. With one copy, the dispatcher can
  never write a config for a role the service would serve no tools, or
  the other way round.
- **Only a role with tools gets the server.** Any other role would see an
  empty `tools/list`, which is a connection made for nothing. Keeping their
  command lines unchanged also keeps this step out of every other phase.
- **Inline JSON, not a file.** `--mcp-config` takes JSON, and a file would
  have to exist inside the agent container at the path the CLI reads.
- **The names in `--allowed-tools`.** Under `-p` an ask with nobody to
  answer it is a denial, so a server without its names would be no use.
- **A read-only key, on by default.** The URL is a service address and a
  grant, like `collector_url`, so it is not something the console sets.
  The default is the compose name, which is what every install has.
  `null` turns it off for a host without the service.
- **The name `board_mcp_url`.** `vibe_kanban_mcp_url` is refused by
  `_refuse_board_keys` (ADR 59).
- **A query is refused.** The service answers 400 to any parameter but
  `role`, so the config refuses it at load time instead of at the phase.

## The network

Read only, nothing changed:

- `docker/compose/docker-compose.agents.yml` puts `agent-cuenta1`,
  `agent-cuenta2` and their dind sidecars on `ia_harness_net`. That network
  is external, created by `docker-compose.yml`.
- `board-service` in `docker-compose.yml` is on `ia_harness_net`.
- `scripts/configure.sh` generates agent services on `ia_harness_net`.
- The Coolify compose has `board-service` on `ia_harness_net` too.

So a phase reaches `board-service:8792` by name, and compose needs no
change.

## Pending

- **`--strict-mcp-config`.** It is not passed, so a project's own
  `.mcp.json` in its clone still loads beside the board. Passing it would
  keep a phase to the board alone, and would also drop any server a project
  relies on. This is left to the user.
- **The learnings fingerprint.** `harness_fingerprint` hashes the configured
  `allowed_tools`, not the per-role board names. Those names are fixed in
  code, so they do not change between runs of one version.
- **The write tools** for the arquitecto come with step 5. They need only a
  new entry in `ROLE_TOOLS`, and the config and the names follow from it.

## Ruled out

- A config file per phase.
- A committed `.mcp.json` for the phases.
- A config for every role.
- A second copy of the role table.
- An editable URL from the console.
- A URL with a query of its own.
