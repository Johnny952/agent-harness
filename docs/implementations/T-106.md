# T-106 — the board service's verdict route

Step 9 of ADR 142's split. The guards and their order are ADR 151's, as in
T-102; the worker's `command_verdict` handler, which runs the queued verdict,
is T-104.

## What was built

- `board_service/app.py`: `POST /api/tasks/<task_id>/command-requests/<n>/verdict`,
  through the same `_action` helper as start and cancel. Its body is
  `{"project", "verdict", "comment"?, "prefix"?}`; it creates a
  `command_verdict` with `params` `{"n", "verdict", "comment", "prefix"}`,
  actor `operator`, and answers 201 with the record.
- `tests/board_service/test_verdict_route.py`: the 201 with the record in
  `pending/`, 503 with no token, 401 for a missing or wrong bearer, 403 for an
  Origin, 400 for a bad `n`, a bad body, an extra key, a query string and a
  body that is not an object, 409 for a second verdict, and an unwritable
  queue. It reuses `test_actions_routes.py`'s fixtures, so the state dir and
  the hive are under `tmp_path`.

## Choices where ADR 142 left room

- The route does not check that request `n` exists or is still open. The
  board service stays a creator, as the cancel route does not look for its
  target (ADR 151, 3). The block can change between the queueing and the
  claim, so a check at the door would race. `run_command_request` already
  refuses every such case on claim (the task not blocked, `n` out of range, a
  block that already has its verdict), and the worker ends the action failed
  with that reason (T-104). A check here would copy `_filed_block` and
  `_pick_request` outside the dispatcher.
- `n` comes from the path as a string and must match `[1-9][0-9]*`, so a
  leading zero, a sign or a decimal is 400, not a silent re-spelling.
- Unknown body keys are 400, as for start; `n`, `note` and `params` are among
  them, so a body cannot override the path or the record's own fields.
- `params` always carries all four keys, with `comment` and `prefix` null
  when absent, so the record reads the same whatever the client sent.
- The 409 is `actions.create`'s per-task one: a second pending or claimed
  `command_verdict` for the same project and task is refused whatever its
  `n`, since any `n` on one task is the same block and a block takes one
  verdict (ADR 119).
- No new ADR: every choice above follows ADR 142, ADR 151 or ADR 119.

## Ruled out

- Flask's `<int:n>` converter: a bad `n` would be 404 from routing, not 400,
  and it would come before the token check.
- Reading the envelope or the task file to validate `n` (see above).
- Reusing `test_app.py`'s `cfg` fixture: its `state_dir` is the real
  `/data/dispatcher_state`.
