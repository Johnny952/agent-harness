# T-133-S2 — the console's *Resolve conflict* button

Decision: `docs/decisions.md` ADR 288, on ADR 285's route. Mirrors
`docs/implementations/T-129.md`.

## What was built

- `front/src/lib/api/forward.ts`: `TASK_RESOLVE_CONFLICT` and an `actionRoutes`
  entry (`action: "resolve_conflict"`). `resolveBody(bytes)` accepts only
  `project` (slug-shaped, else 400) and the upstream body is rebuilt as
  `{project}`; no project and no `CONSOLE_PROJECT` is a 503. Prose counts moved:
  seventeen board pairs, ten with the bearer, twenty-four board writes.
- `types.ts`, `client.ts`, `queries.ts`: `ResolveConflictBody`,
  `resolveConflict` (the 201 is the bare `ActionRecord`, so the toast reads
  `res.id`), `resolveConflictMutation` with approve's refetches.
- `review.ts`: `resolveConflictRefusal(task)`, null only on `conflict` with
  `merged === false`. `approveOutcomes` became `reviewOutcomes`, also keeping
  the dispatcher's comments opening `resolve conflict,`.
- `approvals.tsx`: the button, drawn on the Conflict lane only, after *request
  changes*. Off on a refusal, any pending mutation, or a verdict queued at this
  tip; its title is the reason. The shared `queuedAt` kind gained
  `resolve_conflict`. The typed text is neither required nor cleared. The panel
  sentence points at the button and keeps the CLI line.

## Why this way

It posts `{project}` only: the route takes nothing else (ADR 285), so the
forward refuses other fields rather than forwarding them. Sharing `queuedAt`
makes every review-ending button wait for the tip to move.

## Tests

`forward.test.ts` (forward, bearer, rebuilt body, 400s, 503s, GET 404/PATCH 405),
`review.test.ts`, `-approvals.review.test.tsx` (absent on Awaiting review, body,
merged and queued titles, 409 and 400 toasts, outcome comment).

## Not done

The button lives in the verdict form, so it is not drawn when a conflict task's
diff fails to load (ADR 288 Consequences).
