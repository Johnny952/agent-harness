# T-051 — taking an account is atomic across processes

Design: `docs/decisions.md` ADR 71. This note is only how it was built.

## What

- `dispatcher/state_machine.py`: `LOCK_NAME` (`.accounts.lock`), `_locked`
  (new fd + `flock(LOCK_EX)` per acquisition, never unlinked, not reentrant),
  `claim`, and `set_state(..., only_from=, forget_rate_limit=) -> bool`. Every
  read-modify-write (`set_state`, `record_rate_limit`, `clear_rate_limit`,
  `record_probe`) runs under `_locked`. Readers take no lock: files are
  replaced with `os.replace`, so a read sees a whole document.
- `dispatcher/dispatcher.py` `dispatch_phase`: `claim` right after the pick,
  before `check_quota_ok`; a lost claim moves on like a failed probe; a probe
  that raises puts the account back to IDLE; the old post-probe BUSY write is
  gone. `check_quota_ok` already parks the account on both False paths.
- `_recheck_cooling_accounts` clears the refusal and sets IDLE in one
  conditional write (`only_from` PRE_COOLDOWN/COOLING_DOWN), so a claim made
  during its probe survives. `reap_stale_busy_accounts` writes only from BUSY.

## Why this way

Claim-before-probe shrinks the race to the lock hold rather than the probe's
seconds. The lock is per claim, not per run, so two accounts still run in
parallel; it is never held while `claude` runs.

## Ruled out

A global single-instance lock (serialises runs); a lock held through the
probe (blocks other claimants for seconds); a lock-free `O_EXCL` marker per
account (stale markers after a crash).

## Tests

`tests/dispatcher/test_account_claim.py`: claim/only_from/forget semantics,
every writer waits on the lock, barrier-forced race (one account and two),
parallel phases with the lock free, probe parks / raises, recheck vs claim.
`tests/dispatcher/test_operator.py` account-report test now expects the lock
file in `state_dir`.
