# T-177-S1 — escalated_model editable through the overrides

Decision: `docs/decisions.md` ADR 441. Server half of debt T-175-D1.

## What

- `dispatcher/config.py`: new override kind `nullable_model` (`_check_override_value`
  accepts None or a non-blank string, else `must be a non-empty model ID or null`);
  `_read_overrides` exempts that kind from the null refusal; the `escalated_model`
  row of `CONFIG_KEYS` is now `_editable("nullable_model", ...)`; the
  `ConfigKey.kind` comment lists the kind.
- `config.example.yaml`: the `escalated_model` comment says the console can set it.
- Tests: `tests/dispatcher/test_config.py` (null beats config.yaml, an ID loads,
  `""`/`"  "`/`3` refused naming the file, null for other keys still refused,
  class counts 24/21/3), `tests/config_writer/test_app.py` (PUT null is 200).

## Why this way

A null override means off and a reset (deleting the key) means config.yaml. The
merge already reads a None `escalated_model` as None, and the writer validates
through `load_config`, so `config_writer/app.py` needed no change.

## Ruled out

- Editing ADR 75: ADR 441 narrows it for this kind only.
- Front work: its unknown-kind fallback still offers Reset only; debt T-175-D1
  stays open for the front half.
- The writer's change log records a PUT null as `new: null`, like a reset; only
  `op` (`set` vs `reset`) tells them apart.
