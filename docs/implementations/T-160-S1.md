# T-160-S1 — a drop needs a reason

Contract: `docs/decisions.md` ADR 366.

## What was built

- `dispatcher/context_transfer.py`: `TaskFile.dropped_reason` and
  `dropped_by`, read with `fm.get` and serialized after `project` only when set,
  like `debt_id`.
- `dispatcher/tasks.py`: `_drop_problems` (the one rule: a non-blank string
  reason within `MAX_COMMENT_CHARS`, `by` a role), `mark_dropped(task, reason,
  by)` (in place, no lock, no write; refuses a status outside `ACCEPT_FROM`),
  `accept(..., reason, by)` checking both up front, before any lock, and
  routing the single and the epic drop (each moved child, then the parent)
  through `mark_dropped`. `field_problems` names a bad value.
- `board_service/app.py`: `backlog_accept` passes `by=role`; the schema gains
  `reason`; `board_list` rows and `board_get`'s `item` serve both fields.
- `observability/api/app.py`: the task row serves both fields.

## Why this way

`by` is not in the schema, so an HTTP or MCP body naming it is refused as an
unknown argument and a caller cannot pass for another role. A retry on a card
already dropped is still the no-op, and keeps the first reason, but must itself
carry a reason: the check runs before the card is read.

## Ruled out

See ADR 366: a separate cancel tool, a locking `mark_dropped`, `by` from the body.

## Tests

`tests/dispatcher/test_board_writes.py` (refusals, fields, epic children, retry,
`mark_dropped`, `field_problems`), `tests/board_service/test_writes.py` (MCP and

assertions updated.
