# T-015 — the board's `rows` is memoised

What this task changed, why this shape, and what it deliberately did not do. The
decision is [`docs/decisions.md`](../decisions.md) **ADR 40**, which narrows
**ADR 39**'s ten-warning tally; this file does not restate its argument. The
change is one line of code plus its comment.

## What was built

In [`front/src/routes/index.tsx`](../../front/src/routes/index.tsx), `BoardPage`
read its task rows as `const rows = tasks.data?.data ?? []`. That is now

```tsx
const rows = useMemo(() => tasks.data?.data ?? [], [tasks.data]);
```

with a five-line comment above it saying why, pointing at ADR 40. `useMemo` was
already imported for `debtByTask`. Nothing else in the file moved: `filtered`,
`byStatus`, `unplaced`, the `n of m` count span and the empty state all still
read `rows`, and no state, branch or markup changed. The screen renders what it
rendered before.

The dependency is `tasks.data`, not `tasks.data?.data`. `debtByTask`,
immediately above, already reads `debt.data?.data ?? []` against `[debt.data]`
and draws no warning, so the file carries its own proof that the parent path
satisfies `react-hooks/exhaustive-deps`. React Query holds `data` identical
between renders, so the memo recomputes when the read answers and not otherwise.

## Why a memo that reads as redundant

`useMemo(() => tasks.data?.data ?? [], [tasks.data])` looks like ceremony around
a default, and that is the one plausible way it gets deleted by someone who did
not mean to undo a decision. It exists for the array's *identity*, not for the
cost of `??`: `?? []` yields a fresh array on every render for as long as the
read has not answered, `rows` is the first dependency of the `filtered`
`useMemo`, and [`useNow`](../../front/src/hooks/use-console.ts) re-renders this
screen every 2000 ms whether or not anything was read. So the filter ran on
every tick instead of when the query, the search box or the account filter
changed. Deleting the memo restores both the warning and the recompute. The
reason is on the line in the file as well as in ADR 40 for exactly that reason.

## What was ruled out

- **Inlining the default into `filtered`.** `rows` has three other readers on
  this screen — the count span, the `rows.length === 0` empty state, and
  `unplaced`, whose rows become the per-task warnings — and inlining would give
  each of them its own copy of the default.
- **Memoising `unplaced` and `byStatus` while in there.** `unplaced` is a
  `rows.filter` on every render and `byStatus` is called eight times per render,
  but neither is a hook dependency, so neither is warned about and neither
  destabilises anything. Both are a filter over a handful of tasks. This is not
  debt — it is a non-problem, named here so the next reader does not take it for
  something missed.
- **The nine `react-refresh/only-export-components` warnings.** Out of scope by
  the task text, and this file is one of the nine. Each is a module exporting a
  component beside a non-component — a question about that route's shape rather
  than a lint fix. They are declared as found debt in this task's handoff; see
  ADR 40's last-but-one paragraph for why
  [`docs/charter.md`](../charter.md) **C-10**'s promotion of the lint to a
  blocking gate stays untriggered.
- **A test.** A test of referential stability across renders asserts React, not
  this screen, and the render is identical either way.
  [`front/src/routes/-index.test.tsx`](../../front/src/routes/-index.test.tsx)
  mounts `TaskCard` and never mounts `BoardPage`. The test gate's
  `tests-in-diff` check (ADR 31) **did** fire on this change, as ADR 40 expected
  it to, and was answered rather than satisfied: the change produces no DOM
  difference, so there is nothing for a test in that file's idiom — mount, read
  `textContent` — to assert. Observing it would take a `BoardPage` mount, a
  query client, a two-route tree, three mocked reads and a render-counting spy,
  and what that pins is that `useMemo` returns the same reference, which is
  React's promise and not this screen's.

## Verification, and who does it

**No phase of this task ran any of the four commands.** `bun` is not on a
phase's allowlist and a fresh worktree has no `node_modules` (it is git-ignored,
so `install:` is the test gate's step, not a phase's) — both walls are written up
in `/data/.hive/learnings/inbox/T-015-bun-is-refused-in-a-phase.md`, and the
arquitecto hit them before the implementador did. The designed observation point
is the dispatcher's test gate between implementador and revisor, which runs
exactly the `install:`, `test:` and `lint:` entries of
[`docs/README.md`](../README.md)'s frontmatter — ADR 39.

Green, for this task, means:

| command | green |
| --- | --- |
| `bun run typecheck` | exit 0 |
| `bun run test` | exit 0 |
| `bun run lint` | exit 0, **nine** warnings, every one `react-refresh/only-export-components`, no `react-hooks/exhaustive-deps` |

What a reader of that output should check, which no phase could: **ADR 40
paraphrases the eslint message rather than quoting it**, because the message was
not observable where the ADR was written. If the verbatim warning differs in
substance from the paraphrase in ADR 40's *Context*, correct the ADR in place —
it is this cycle's own unmerged entry, which
[`docs/learnings/an-adr-your-own-cycle-appended-is-not-yet-append-only.md`](../learnings/an-adr-your-own-cycle-appended-is-not-yet-append-only.md)
allows.

The nine-warning count is also already asserted in prose, in ADR 40's
*Consequences* and in [`docs/README.md`](../README.md) *Stack*. Both were written
by the arquitecto before the code edit existed, so for one phase they claimed
something the tree did not do yet. They are true as of this file. If the code
edit is ever reverted, those two sentences are the ones that go with it.
