# T-128 — the *request changes* verdict

Design: `docs/decisions.md` ADR 272 (on ADR 258, 264, 267, 270);
`docs/plans/review.md` step 6. Board service and dispatcher; no front, no new
CLI verb.

## What was built

- **Route** (`board_service/app.py`): `POST /api/tasks/<id>/request-changes`,
  approve's route with the kind swapped; both go through `_review_action`.
  Same bearer, Origin, query, body (`project`, `commit`, `text`) and status
  codes. On an `awaiting_review`, unmerged task it writes the
  `request_changes` verdict line and queues a `request_changes` action; it
  starts nothing. `conflict` is refused naming *resolve conflict*. `/verdict`
  and the `review_verdict` tool refuse `request_changes` and name the route.
- **Verdict** (`dispatcher/tasks.py`): `request_changes` joins
  `VERDICT_KINDS_BUILT`. `review_comments` gathers the request's text and the
  same author's comments on that commit since their previous approve or
  request; `reopen_for_changes` moves the task back to `pending`.
- **Action** (`dispatcher/actions.py`): a `request_changes` kind, project
  serial key, spends quota, `requeue_unless_started`, one per task, and one
  approve or request per task at a time (409 naming the other).
- **Worker** (`dispatcher/worker.py`): `_request_changes` rechecks the task,
  reopens it and runs `core.run_task_cycle` unauthorized under the held
  project lock, with `changes_requested` set; the result carries the commit,
  outcome and any blocked reason. Cancel kills a running one, like approve.
- **Cycle** (`dispatcher/dispatcher.py`): `CycleContext.changes_requested`
  and `changes_requested_note` (the commit and every comment, in order, with
  file and line when set) reach the arquitecto's prompt below the Goal and
  Done when; later roles do not get it. The writer worktree reuses the
  task's branch, so the new commits stack on the reviewed tip.
- **Docs**: ADR 272; `docs/plans/review.md` status, *What exists today*, step
  6, step 7 and the open question on which roles rerun.

## Why this way

- Mirroring approve keeps one path, one auth model and one queue rule for both
  verdicts (ADR 272, 1-3).
- Every role reruns from the arquitecto: the docs leave no lighter path, and
  the note in the arquitecto's prompt is the only new input (ADR 272, 4-5).
- The task ends in `awaiting_review` at a new tip, and approve checks the
  verdict's commit, so an earlier approval cannot carry over (ADR 272, 6).

## Open

- A resume from mapping or command (ADR 119) does not carry the note.
- The arquitecto may split the task; round numbering may restart.
- A legacy unmerged `done` task is refused, unlike approve.
