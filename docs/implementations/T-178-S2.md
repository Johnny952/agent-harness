# T-178-S2 — epics in `GET /api/roadmap`

Contract: `docs/decisions.md` ADR 447.

## What was done

- `observability/api/app.py`, `roadmap` view: each task file is kept as a
  `_RoadmapEntry` (row, plan, merged, month, epic, is_epic, split_into,
  title, order key). Ids that have a file but no row (unreadable, another
  project, past the cap) go in an `absent` map with the reason.
- `_roadmap_epics`: pure. Nests sub-tasks by the epic's `split_into`, builds
  epic rows, and emits every warning (no sub-tasks, `epic` naming a missing
  or unlisting epic, plan differing from the epic's, bad `split_into`, a task
  listed twice). It returns `_Placed` items for `_roadmap`.
- `_roadmap`: plan names are normalised (`docs/plans/x.md` is `x.md`);
  backlog epics (`proposed`/`deferred`) go last in their list in board order,
  into a future plan row, a second future row for a `building`/past plan, or
  `no_plan.now`.
- Docstrings, the `MAX_ROADMAP_TASKS` comment and the item 4 note in
  `docs/plans/roadmap-view.md`; six tests in `tests/observability/test_roadmap.py`.

## Why this way

- Warnings in one pure helper, so the route stays a loop and a 500 has no
  place to come from.
- An epic's `merged_at` is the latest sub-task's by parsed datetime (strings
  compare wrong across offsets); null when any does not parse.

## Ruled out

- A separate `epics` key (ADR 447, Ruled out).
- A sub-task that is itself an epic is not nested (warning, left flat): the
  ADR does not define nested epics.
