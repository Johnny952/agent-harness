# T-031 — the split backstop, switched on

This task builds task 4 of `docs/plans/task-split.md` section 8, *How the
implementation is itself split*: the arquitecto's schema offers `split`, a
cycle files a valid one and stops before the implementador, and an epic is
not dispatched. The decision is `docs/decisions.md` ADR 60. T-025, T-029 and
T-030 built the three inert tasks before it.

The sections down to *Tests* are the arquitecto's design. The implementador
corrects them where the code turns out different and lists those corrections
under *Where the build differs from the design*.

No fact was different. Five things the card does not say, each of which
shapes the build:

1. **A sub-task's description must parse as a task description.**
   `tasks.file_split` runs `parse_description` on every entry and raises
   `SplitError` on one without `## Goal` and `## Done when`. Neither the
   plan's section 6 paragraph nor `_SPLIT_PROPERTY`'s description tells the
   arquitecto that, so every split would have blocked. The `_ARQUITECTO`
   paragraph below says it.
2. **The plan's section 6 paragraph names no card.** "Adapted to ADR 59"
   removes nothing from it; the adaptation is item 1.
3. **`run-phase` on an epic would lose its status.** `tasks.handoff` writes
   `pending` over whatever is there. So the refusal goes in `open_cycle`,
   which both verbs pass through, not in `run_task_cycle` alone.
4. **A re-file does not repair a parent.** `file_split` writes the parent
   only while its `split_into` is not this split's. A parent whose `epic`
   status was overwritten after a filing stays overwritten. That is why a
   parent whose lock is live is refused.
5. **`_file_split` takes a `CycleContext`, and `file-split` has no cycle.**
   The verb builds one without `open_cycle`; see below.

## The schema

`_ROLE_EXTRAS["arquitecto"]` becomes `_SPLIT_PROPERTY`. The comment above
`_SPLIT_PROPERTY` says it is "in no role's extras yet" and is corrected in
the same edit; nothing else in `dispatcher/handoff.py` changes. The
arquitecto's schema measures under the 4096-byte cap
(`docs/learnings/offering-split-to-a-role-is-one-red-test-and-a-measured-fit.md`);
`test_schema_stays_small_enough_to_send_on_every_call` holds it.

## The epic refusal, in `open_cycle`

In the block that already reads the task file for the dependency gate, and
before the gate's own reasons:

- If `task.status == "epic"`: one error line,
  `task <id> is an epic, split into <ids>: run its sub-tasks, not the epic`,
  and return None. `<ids>` is `split_into` joined by `, `, each through
  `str`, or `no sub-tasks` when it is empty or not a list.

That is before the supplied description is written, before any account is
picked and before any lock. `run_task_cycle` returns BLOCKED straight from
`ctx is None`, so `_mark_blocked` cannot fire and the file keeps its bytes.
`run-phase` is refused the same way and exits 1.

## `CycleOutcome.SPLIT` and `_file_split`

`CycleOutcome` gains `SPLIT = "split"`; its docstring says four outcomes.

`_file_split(ctx: CycleContext, subtasks: list[handoff.SubTask]) ->
CycleOutcome`, beside `_mark_blocked`. It reads `ctx.cfg`, `ctx.task_id` and
`ctx.task_file` only. It writes nothing unless it files, and marks nothing:

1. `problems = handoff.split_problems(subtasks)`.
2. Read the parent's task file. `FileNotFoundError` adds nothing here:
   `file_split` reports it. Otherwise:
   - status `done` or `epic`: `task <id> is <status>; only a pending,
     in_progress or blocked task can be split`;
   - `tasks._lock_is_live(parent, cfg.heartbeat_ttl_seconds)`: `task <id> is
     locked by <owner>; file the split once that run has ended`. The helper
     is private to `dispatcher/tasks.py` and is called by name on purpose,
     as that module calls `context_transfer`'s; no helper is added.
3. Any problem: one warning, `task <id>: the split cannot be filed:
   <problems joined by "; ">`, and return BLOCKED without calling
   `file_split`.
4. `tasks.file_split(cfg.hive_tasks_dir, ctx.task_id, subtasks)`. A
   `tasks.SplitError` is the same warning with `exc.problems`, and BLOCKED.
   That is where a description that will not parse, a task inside an epic
   and a sub-task file that disagrees are reported. No other exception is
   caught.
5. One info line, `task <id> is now an epic: <ids>; run them in that order`,
   and return SPLIT.

In `run_task_cycle`, right after the arquitecto's block branch:

```python
subtasks = handoff.split_of(arquitecto.handoff)
if subtasks:
    outcome = _file_split(ctx, subtasks)
    return blocked() if outcome is CycleOutcome.BLOCKED else outcome
```

So a split that could not be filed is marked `blocked` by the cycle, under
T-030's rule, and one that was filed is left `epic`. The parent is `pending`
with no owner at that point, because the arquitecto's `tasks.handoff` has
run. The existing `finally: close_cycle(ctx, completed=False)` does the
cleanup.

## `file_saved_split`, for the `file-split` verb

`file_saved_split(cfg, task_id, slug) -> CycleOutcome`, public, in
`dispatcher/dispatcher.py`. It runs no model, opens no cycle and closes
none, so nothing is reaped, reconciled or marked:

1. `context_transfer.read_handoff(hive, task_id, "arquitecto")`. None is an
   error line naming `context_transfer.handoff_path(...)`, and BLOCKED.
2. `handoff.blocked(payload)`: an error line saying the arquitecto blocked
   and a block wins over a split, and BLOCKED.
3. `handoff.split_of(payload)` empty: an error line, `task <id>: its
   arquitecto handoff has no split`, and BLOCKED.
4. Build a `CycleContext` directly: `description` from
   `tasks.read_description` or `""`, `task_file` from `task_file_path`,
   `scratch_dir` from `context_transfer.scratch_dir`, `harness` from
   `learnings.harness_fingerprint` as `open_cycle` computes it. Return
   `_file_split(ctx, subtasks)`.

## The CLI

- `EXIT_SPLIT = 3`, with a comment giving the plan's reasons: not 0, not 1,
  not 2 (argparse), not 75.
- `run-task`: on `CycleOutcome.SPLIT`, print `task <id> is now an epic:
  <ids>; run them in that order` to **stdout** and exit `EXIT_SPLIT`. The ids
  are the task file's `split_into`, read in the CLI; a file that will not
  read prints the line with `its sub-tasks` in place of the ids, and never a
  traceback.
- `run-phase`: after the `phase <role> finished` line, when the role is
  `arquitecto` and its handoff is not blocked and `handoff.split_of` is not
  empty, print:

  ```
  phase arquitecto proposes splitting task <id> into <n> sub-tasks; nothing was filed:
    1. <title> (<surface>)
    2. <title> (<surface>) — after 1
  run `dispatch file-split --task-id <id> --project <slug>` to file them
  ```

  The numbered lines are `handoff._split(result.handoff)`, the helper
  `render` uses, indented two spaces. If `handoff.split_problems` returns
  anything, one more line on stderr: `file-split would refuse it:
  <problems>`. The exit code stays 0: the phase finished.
- `file-split --task-id <id> --project <slug>`, both required:
  `_require_migrated`, then `file_saved_split`. SPLIT prints the same epic
  line as `run-task` and exits 0, because the verb did what it was asked.
  BLOCKED prints `task <id>: the split was not filed; the log above says
  why` to stderr and exits `EXIT_BLOCKED`.

## The arquitecto's paragraph

Appended to `_ARQUITECTO` after the block paragraph, as its own paragraph:

> If the plan would change more than one surface — one api route with its
> tests and ADR, one screen, one region of a screen, or one module's contract
> — do not plan it. Return a split instead: in `split`, two to four sub-tasks
> in the order they run, each one surface, each with a description complete
> enough to be its own task. That description is filed as the sub-task's own
> task description, so write it in the sections yours has: `## Goal` and
> `## Done when` are required, `## Surface`, `## Steps` and `## Out of scope`
> optional, and nothing goes before the first heading. Say in it what it
> builds, what it reads from an earlier sub-task and when it is done. In
> `after`, name the earlier entries that must be merged before it starts. The
> contract one surface hands the next — a route's row shape, a function's
> signature — is fixed by the sub-task that serves it, so put the server
> first. A split writes nothing to the repo: no ADR, no doc. Leave `changed`
> empty and `status` complete. A task that is already part of an epic cannot
> be split again; if it still spans surfaces, block it and say which. Split
> for size, not for difficulty: a single surface that is hard is still one
> task. With nothing to split, `split` is an empty list.

A sub-task's arquitecto knows it is inside an epic from the line
`file_split` puts under its *Goal*: `Part of epic <parent>. Surface: …`.

## Ruled out

- **The refusal in `run_task_cycle` only.** `run-phase` would still turn an
  epic `pending` (item 3 above).
- **`file-split` through `open_cycle`.** It would reap locks, reconcile
  learnings and need `close_cycle`, which calls into a container, for a verb
  that writes at most five files.
- **`file-split` exiting 3.** Exit 3 on `run-task` says the task did not
  ship. On `file-split` the filing is the success.
- **Marking the task `blocked` from `file-split` or `run-phase`.** T-030:
  only a cycle that took the lock marks.
- **Changing `_SPLIT_PROPERTY`'s descriptions** to name the two headings.
  The card keeps `dispatcher/handoff.py` to the one line, and the paragraph
  carries it.
- **Checking the parent's status inside `tasks.file_split`.** The card puts
  the rule in `_file_split`, and it is unconfirmed (`docs/business.md`).
- **Editing the root `README.md`.** It is `docs/debt/T-028-D2.md`, widened.

## Where the build differs from the design

The build follows the design. The implementador re-read every symbol in the
table above before editing and found none different. What it added or
settled where the design was silent:

- **Three small helpers the design did not name.** `_split_into` in
  `dispatcher/dispatcher.py` renders an epic's sub-task ids for
  `open_cycle`'s refusal line. In `dispatcher/cli.py`, `_epic_line` builds
  the line `run-task` and `file-split` both print, and
  `_print_proposed_split` is `run-phase`'s proposal output. No helper was
  added to `dispatcher/tasks.py`; only its module docstring changed, which
  said nothing calls `file_split`.
- **`tasks.file_split` is called only when nothing is wrong yet.** The
  design's steps 3 and 4 read that way; the consequence is that a split
  with a `split_problems` finding *and* a description that will not parse
  reports only the first kind. One refusal either way, nothing written.
- **`in_progress` with no live heartbeat is fileable**, and has its own
  test. That is the state `reap_expired_locks` leaves a dead run in, which
  is the recovery `file-split` exists for.
- **The epic refusal comes after the description checks in `open_cycle`.**
  It sits in the block that already reads the task file, as designed. So an
  epic with no stored description, run with none supplied, is refused as
  "has no description", not as an epic. Either way nothing is dispatched
  and nothing written; the CLI refuses that case itself before it gets
  there.
- **`_print_proposed_split` says nothing for a blocked arquitecto**, as the
  design says, and also nothing when the phase answered in prose (no
  handoff to read).
- **One test beyond the list**: a cycle whose arquitecto returns an empty
  `split` goes on to the implementador and finishes. Now that the field is
  required, that is the ordinary cycle.
- **The card says T-028 built task 1; the plan and this doc say T-025.**
  `docs/plans/task-split.md`'s *Status* names T-025 for the handoff shape.
  Nothing was changed for it.

## What a later task should know

- `run-task` has four exits: 0 finished, 75 held, 1 blocked, 3 split. On 3
  the task file says `status: epic` and `split_into` lists the sub-tasks in
  run order; nothing runs them.
- `file-split` reads whatever arquitecto handoff was saved last for the
  task. It refuses a `done` or `epic` parent, so filing twice is refused,
  not repeated.
- A task that is `epic` cannot be opened by `run-task` or `run-phase`. To
  split it again: delete the sub-task files and their descriptions, and set
  the status back by hand.
- A split whose entries are all non-objects reads as no split
  (`handoff.split_of` drops them), so that cycle goes on to the
  implementador. The CLI's schema validation is what keeps it from
  happening.
- `docs/debt/README.md`'s `T-028-D2` row is the auditor's to widen; the
  entry's file already names exit 3, `file-split` and the `run-phase` line.
