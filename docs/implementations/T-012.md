# T-012 — the console's share of tier 1, and the bound on the task body

What this task built, why it is shaped this way, and what it deliberately did not
reach. The spec is `docs/plans/front.md` *What changes, in the console* and
*Parity, and what it retires*, over ADR 14–21; the five decisions this task made
itself are `docs/decisions.md` ADR 22–26 and this file does not restate them —
read those for the *why*, this file is the *what*.

> **Written in two phases.** The arquitecto committed the api half, ADR 22–26,
> the `docs/ui.md` entries and the `T-011-D1` resolution, and wrote the console
> half below as the specification it handed the implementador —
> `/data/.hive/tasks/T-012/console-plan.md` is the file-by-file version. The
> implementador deletes this paragraph when the console half is on the branch, and
> corrects anything below it that came out differently. Until then, read *What was
> built — the console half* as what was decided, not as what is in the tree.

**This task does not reach parity and does not claim it.** Parity is the four
Jinja screens rendered with no fixture behind any query they make, and two of
those four query routes that do not exist: the Board screen and the task detail
screen both want phases, and the detail screen wants learnings. `/api/phases` and
`/api/learnings` are tier 2. So `observability/board/` stays, with its compose
service and its tests, and C-8 keeps it the tie-breaking reference. What the
unwired regions do instead is ADR 19's rule and `docs/ui.md` *A region with no
route says which route, and when*: they name the route and the tier on screen, so
an operator can always tell a quiet harness from an unwired console.

## What was built — the api half

One bound, on one field, on one route. `MAX_BODY_BYTES = 128 * 1024` in
`observability/api/app.py`, applied by `_bounded_body` inside the
`/api/tasks/<task_id>` view's existing guard, keeping the **newest** end of the
running record and naming the truncation in `warnings`. That closes
`docs/debt/T-011-D1.md`, which was the one thing this service answered with no
cap and which named this task as its owner — the console task that renders the
detail screen is the only thing that knows how much of the record the screen
shows.

`docs/decisions.md` ADR 23 is the decision, including why the cap rather than the
`?body=` parameter the entry also offered, and why the newest end rather than the
earliest. Five tests in `tests/observability/test_api.py` pin it: a body under the
cap is whole and silent, a body over it keeps its newest end and says so, a
truncated body starts at a whole line, it carries no replacement character when
the byte slice lands inside a multibyte character, and `/api/tasks` reports
nothing at all — the field is still the detail route's alone and ADR 21 is not
loosened.

Nothing else on the api moved. No new route, no new parameter, no contract change
on `_reject_unknown_parameters`, and the parametrized envelope test over all five
routes and its bearer twin are untouched and green.

## What was built — the console half

Five function bodies in `front/src/lib/api/client.ts`, the server-side forward
they call through, and the field-level consequences on five screens.

**The reads.** `listTasks`, `getTask`, `listAccounts`, `listEvents` and
`listDebt` go through one boundary function — ADR 7's "one boundary function per
call", inherited — which checks `application/json` before `.json()` because Flask
answers its own 404 and 405 in HTML, treats a non-200 as `{"error": …}` with no
`warnings` key, and checks shallowly that a 200 is `{data, warnings}`. They
resolve to `ApiResult<T>`, which is ADR 25: `data` unwrapped, warnings riding
beside it, `queries.ts` unchanged.

**The forward.** ADR 24. A closed, GET-only interception in
`front/src/server.ts` over a whitelist of five paths — not a proxy — reading
`API_BASE_URL`, `API_TOKEN` and `CONSOLE_PROJECT` from
`front/src/lib/api/server-env.ts`, which throws at import when the token is
missing, so a console with no token refuses to boot rather than falling through
to unauthenticated requests. Every browser fetch is same-origin, so
`observability/api/` needs no CORS and goes on not knowing a browser exists; the
CSRF middleware in `front/src/start.ts` is untouched and its comment stays true.

**The three environment names**, with no `VITE_` prefix on any of them, because
Vite inlines every `import.meta.env.VITE_*` into the client bundle:

| Name | Default | Missing |
|---|---|---|
| `API_BASE_URL` | `http://api:8789` — the compose network name, the same default the Jinja board takes | the default; a console on the host points it at `127.0.0.1:8789` |
| `API_TOKEN` | none | **the console does not start.** The module that reads it throws at import, and `server.ts` imports it |
| `CONSOLE_PROJECT` | none | `?project=` is omitted and the api picks, which is right for a harness with one checkout and a self-describing 400 for the other kind — ADR 9's shape |

`CONSOLE_PROJECT` takes its own name rather than reusing the board's
`BOARD_PROJECT`, because that variable belongs to a service C-8 retires and two
services may legitimately be pointed at two checkouts. The same three names are in
`front/AGENTS.md` and in `front/README.md` *Running it*, which is the list an
operator starting this service actually reads —
`docs/learnings/an-env-key-only-an-adr-names-is-invisible.md` is why they are not
left in an ADR alone. There is no `docker/compose/.env.example` in this repo to
add them to, and a compose service for the console is a separate task: this one
ships source.

**The tail's cursor moves forward.** `db.list_events` ends in `ORDER BY id DESC`
and `tail.tsx` keeps an ascending array whose next cursor is `events.at(-1)?.id`.
Wired together unchanged, `at(-1)` reads the *oldest* id of the batch, the cursor
walks backwards and the tail re-fetches the same window forever while looking
like it works. `listEvents` reverses each batch inside `client.ts` and nothing in
`tail.tsx` changed for it. The skip that `since` plus `limit` imply — more events
between polls than `limit` allows and the older ones in that window are gone — is
left exactly as the route documents it, not papered over. ADR 22, which is also
where the decision the plan asked for is recorded: the console consumes what the
collector already has and re-terminates nothing.

**Warnings render.** Every screen that lists rows shows the warnings it was
given, from every query it made, in one `Banner` above the content.
`docs/ui.md` *A degraded backend is a banner, not a blank screen* now says
concretely what that looks like, so ADR 16's criterion is checkable against a
file. `tail.tsx` was the worst case — it collapsed every failure into one `error`
string and swallowed warnings outright — and it keeps `error` for failures while
warnings get their own banner.

## Three visible regressions against the Lovable mock, all deliberate

In one sentence, because they are the same decision three times — a screen that
renders a field nothing records is a fixture wearing a column: the Debt screen
loses its severity partition and partitions on `resolved` instead (open first,
resolved below), the Pool screen's usage gauge loses its number and renders
through `Absent` (ADR 18: nothing persists `usage_pct`, and the same gauge
reading nothing is the same picture with none of the meaning), and the Board
screen loses its five role lanes and its gate filter (ADR 26: a task file's
status carries no role, so the split waits on `/api/phases`, and the screen says
so instead of standing five columns empty).

The fourth field-level consequence is not a regression, just a rename the console
does not get to make: there is no `queued` in this harness. The served word is
`pending` and the Board's first column takes it.

## What ships unexecuted, and why

**The console half ships with no test run and no typecheck.**
`front/package.json` has no `test` script, there are no `*.test.*` or `*.spec.*`
files and no vitest config anywhere under `front/`, and `front/node_modules` does
not exist — installing it is out of scope for this task. So the `tests-in-diff`
gate falls silent on the Python changes alone, and that silence is not TypeScript
coverage: `python3 -m pytest` is green over the whole suite, and it proves the
api's bound and nothing about the forward, the five reads or the five screens.

That gap is filed as found debt by this task rather than left implied: the
console's code has no runner, no typecheck in the loop and no gate that would
catch a wiring mistake in it.

The end-to-end check a human runs is `docs/ROADMAP.md` **V0.6c**, beside V0.6b's
board check, with no results row because nothing ran. The four things it settles
are the four this task cannot: the token is absent from the built client bundle,
the forward answers against the real api, the warnings appear where the api sends
them, and the tail's ids go up.

## What was not done, and is not debt

- `/api/phases` and `/api/learnings`, in any form. Tier 2, and the regions that
  want them say so.
- Deleting `observability/board/`. C-8 keeps it until parity, which this task
  does not reach.
- A compose service, a Dockerfile or any other answer to how the console is run.
- `front/src/lib/api/queries.ts`. ADR 16 is explicit that the keys and the
  intervals stay; what a `queryFn` resolves to is what moved.
- The inert `Release` button on the Pool screen and the Loading-per-region
  question, both bound by `docs/plans/front.md` to later screen-level tasks and
  both left exactly as they were found. `docs/ui.md` *Not decided here* still
  lists them.
- The five fixture functions that backed the five wired reads are updated to the
  served shapes rather than deleted, and the four that back routes which do not
  exist gain no `warnings`. ADR 25 says why.
