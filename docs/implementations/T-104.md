# T-104 — the worker's `command_verdict` handler (ADR 142 split step 8)

## What was built

- `dispatcher/worker.py`: `_command_verdict`, registered in `HANDLERS`
  beside `start` and `cancel` (ADR 148, 1). The loop now claims a pending
  `command_verdict` under its serial key `project:<slug>`, the key `start`
  has, so a verdict and a start on one project never run together and either
  waits `project` for the other; two projects still run side by side.
- `VERDICT_NOT_CANCELLABLE`, the reason a cancel on a running verdict gives.
- `tests/dispatcher/test_worker.py`, with `run_command_request` faked
  (`Verdict`, beside `Cycle`). The T-100 test that `command_verdict` stays
  pending became `test_turn_stays_pending_untouched`.

This supersedes, for `command_verdict` only, T-100's "`command_verdict` and
`turn` are left pending, untouched"; `turn` still is (split item 10).

## The handler

It writes `started_at`, then calls
`command_run.run_command_request(cfg, task_id, project, n, verdict, comment,
by=actor, prefix=prefix)` with the record's `params` and `actor`
(ADR 142, 8). The end:

- the call returns: `done`, `result` `{n, verdict, outcome, blocked_reason}`,
  `outcome` the `CycleOutcome`'s value and `blocked_reason` the task's when
  the outcome is `blocked` (ADR 142, 5, the same as a start's);
- `VerdictRefused`: `failed`, `error` the refusal's reason on one line.
  Nothing ran or was recorded;
- any other exception: `failed`, `Type: message`, through the loop's guard
  as for a start; the serial key is freed either way.

Recovery is `actions.recover`'s, unchanged: a claimed verdict ends
`interrupted` with the error naming `dispatch command-resume`, never run
again (ADR 142, 7).

## Choices where ADR 142 left room

- *The account wait.* `KINDS` marks `command_verdict` as spending quota, so
  the claim's account check is now keyed on `Kind.spends_quota` rather than
  on `kind == "start"`: a verdict with no account open waits `account`,
  paced as a start's (ADR 148, 5). ADR 142, 7 names the check for `start`
  only; a verdict resumes a phase, so running it with every account closed
  would record it, run the command and then hold the resume for
  `command-resume`. The check asks for any open account, while the resume
  runs on the phase's own account; `run_command_request` handles that one
  being closed, as before.
- *Cancel.* A pending verdict is cancelled as any pending action is. A
  running one is not (ADR 142, 7): the cancel ends `failed` naming the
  reason, and the verdict runs on. Before, it failed with the generic
  "is a running command_verdict; it cannot be cancelled".
- `started_at` is written before the call, the first point that can change
  state outside the queue. Recovery interrupts a claimed verdict either way.
- The handler has no `may_start_phase` hook: `run_command_request` takes
  none. A SIGTERM waits for the whole verdict, resume and cycle to end,
  bounded by compose's stop grace like a start's phase in flight; a kill
  leaves it claimed, and recovery interrupts it.

Nothing in the board service creates a verdict yet (split item 9).
