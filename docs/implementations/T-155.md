# T-155 — The dispatcher always merges the base before an implementador

Decisions: `docs/decisions.md` ADR 339 (base merge in every path, conflict kept
in progress, marker guard, fallback, leftover merge) and ADR 340 (denylist rule
`base-merge`).

## What was done

- `dispatcher/dispatcher.py` `_cycle_from_arquitecto`: the base merge
  (`merge_base_at_write_window`) and `stale_plan_note` run whether or not there
  is a scheduler; a scheduler only gates `enter_write_window`. Every caller of
  `run_task_cycle` (worker request_changes rerun, ungrouped start, CLI
  `run-task`) therefore merges, with no change in those callers.
- Conflict kept in progress: `merge_base_at_write_window` calls
  `_keep_conflict_in_progress`, which redoes the merge in the writers' checkout
  with `docker_exec.merge_base_into_writer` (ADR 277) and returns
  `BaseMove(in_progress=True)`. `_unfinished_merge_note` ("The base merge is
  yours to finish") names the paths and says to edit, run no git. Where the
  merge cannot be kept (checkout dirty, off the tip, git would not start) the
  old abort-and-tell `BaseMove` is returned (ADR 339, 5).
- Round-commit guard: `docker_exec.conflicted_with_markers` (reuses
  `_MARKER_RE`); `dispatch_phase` skips the commit and sets
  `DispatchResult.unresolved_merge`; `_cycle_rounds` appends a task note, hands
  the next round the conflict note (whatever its number) and goes round again
  before the gates' verdict and the revisor. A blocked handoff is not sent back.
  The commit itself is unchanged: `git add -A` + `git commit` with `MERGE_HEAD`
  set is the merge commit with both parents.
- Leftover merge: `docker_exec.abort_writer_merge`, called by
  `_abort_leftover_merge` when a cycle opens (after `update_project_branch`).
- Resume: `command_run._resume` merges the base before resuming an
  implementador, unless a merge is already in progress (`_merge_pending`: that
  one is the resumed session's own), and appends the note to the resume prompt.
- Denylist: `command_targets._base_merge` (rule `base-merge`, first in
  `DENYLIST`) refuses `git merge|rebase|pull` whatever the options; the
  reason says the dispatcher owns the base merge. `_REMOTE_IS_NOT_YOURS` tells
  the arquitecto and implementador never to plan or file one.

## Tests

- `tests/dispatcher/test_base_merge_paths.py`: the real `run_task_cycle` with
  the worker's request_changes rerun, ungrouped start and CLI `run-task`: the
  merge precedes the implementador.
- `test_premerge.py` (real git): conflict left in progress, resolved by an edit,
  round commit has parents `[tip, base]` and no marker; marker left -> guard
  names the file and nothing moves; dirty writer -> aborted fallback;
  leftover abort.
- `test_dispatcher.py`: `dispatch_phase` skips the commit on markers.
  `test_parallel_queue.py`: serial cycle merges (inverted old test), conflict
  note, round-back on `unresolved_merge`. `test_command_targets.py` /
  `test_command_requests.py`: `git merge main` etc. denied with the note, cycle
  goes on to the revisor.
- `fake_git` (test_dispatcher.py) stubs `_abort_leftover_merge`,
  `merge_base_at_write_window` and `command_run._merge_pending`: tests that
  count the cycle's git calls would otherwise see the new ones.

## Ruled out

- Teaching the callers (worker, CLI) to build a scheduler: the merge does not
  need one, and a fake scheduler would open a write window nobody asked for.
- A new git merge routine: ADR 277's `merge_base_into_writer` already leaves a
  merge in progress with the right refusals.
- Aborting-and-telling as the default: the implementador cannot merge either.

## Not run

- The front commands (`bun run typecheck`, `test`, `lint`): `front/` is
  untouched and `tsc` is not installed in this worktree.
