# T-105-S2: the Ready card's *Start development*

Contract: `docs/decisions.md` ADR 160 (on ADR 157, the forward). This note
records what was built and the states chosen.

## What was built

- `front/src/lib/api/types.ts`: `ActionRecord`, `ActionQueue`, `StartTaskBody`.
- `front/src/lib/api/client.ts`: `getActionQueue` (`GET /api/actions?limit=1`,
  `readEnvelope`) and `startTask` (`POST /api/tasks/<id>/start`, `readBare`,
  body exactly `{note}`).
- `front/src/lib/api/queries.ts`: `actionQueueQuery` under key
  `["action-queue"]` and `startTaskMutation`, which invalidates
  `["action-queue"]` and `["tasks"]` on settle.
- `front/src/routes/index.tsx`: `BoardPage` reads the queue and builds a
  task-id map of pending/claimed `start` records; `TaskCard` takes a `footer`;
  `StartControl` is the footer on Ready cards only.
- `front/src/routes/-index.test.tsx`: the new describe *Start development on a
  Ready card*; both existing `board()` helpers now serve `/api/actions`.

## The states of a Ready card

| Queue read | Start record for this task | Card shows |
|---|---|---|
| loading | n/a | nothing (no flash of a button) |
| answered | none (another task's start, or another kind, does not count) | *Start development* |
| answered | pending | *Queued*, plus ", waiting for an account" / "for the project" / ": <value>" from `waiting` |
| answered | claimed | *Running* (claimed wins over pending) |
| failed | unknown | the button, and a banner line saying `/api/actions` did not answer |

Waiting cards get no button. Refusals (a second start, a stopped task) are
`toast.error` with the service's message; the dialog and note stay open.

## Choices

- The button sits in a `footer` outside the card's `<Link>`: a button inside an
  anchor also navigates. The outer `<div>` carries the border and padding; the
  anchor still holds the id, so tests that find `closest("a")` keep working.
- Dialog, not alert-dialog: the note is a form field. Cancel closes it; success
  closes it and clears the note; a refusal keeps both.
- The note is optional: `commentProblem` runs only when `note.trim()` is
  non-empty, since it refuses blank text. A non-blank note is sent as typed; a
  blank one is sent as `null`.
- Key `["action-queue"]`, not `["actions"]`, which is the `/queue` draft's mock.
- `limit=1` on the read: the Board needs `pending` and `claimed`, served whole.
- No cost, pool, slot or limit text anywhere.

## Ruled out

- Reusing `listActions`/`actionsQuery`: mock shape, different consumer.
- Matching the start by project: the record's `project` is not compared, so two
  consoles on one hive would see each other's starts (ADR 160 consequences).

## Not done

- Worker heartbeat / stale state is not shown (the read serves it).
- No cost or limit: none exists yet (`params.limit` is null). Charter C-12
  (Amended) wants a limit shown before confirming; that is not met until
  board-service step 9.
- Waiting's disabled button, *Cancel* and the `/queue` screen (step 7), *Start
  epic*.
