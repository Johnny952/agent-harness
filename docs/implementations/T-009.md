# T-009 — the read API, Phase 1 of the board plan

What this task built, why it is shaped this way, and what it did not build.
The spec is `docs/plans/board.md` "Phase 1 — a read API in Python" and is
unchanged by this task. The decisions a later task could undo without knowing
they were decisions are `docs/decisions.md` ADR 3–5; this file is the build log
and does not restate them.

## What was built

One new service, one extracted module, and three readers given a path-based way
in. Nothing writes anywhere.

- `observability/api/`: `app.py` with `create_app(config_path, db_path,
  username, password_hash)` — the dashboard's shape — five `GET`s, the
  `{"data", "warnings"}` envelope, and the query-parameter rejection; a
  `Dockerfile` on the dashboard's model that also `COPY dispatcher/`, `EXPOSE
  8789`, entrypoint `python -m observability.api.app`; and `__init__.py`.
- `observability/auth.py`: `check_auth` and `requires_auth(username,
  password_hash, realm)`, lifted out of `observability/dashboard/app.py`'s
  `create_app`. The dashboard imports them and passes its own realm.
- `dispatcher/debt.py`: a public `index_rows(text) -> list[dict]` over the same
  private `_rows`/`_column` pair, plus `_RESOLVED_RE`. `index_fingerprints` and
  `card_ids` now read through it, so the index still has one row parser.
  `read_index` is untouched.
- `dispatcher/vibe_kanban_client.py`: `LocalBoardClient.unreadable()`, over a
  private `_scan()` that `_cards()` now shares — one pass over the directory
  behind both answers rather than two ideas of "readable".
- `observability/collector/db.py`: `connect_read_only(db_path)`
  (`file:<path>?mode=ro`, `uri=True`) and `list_events(…, since=None,
  read_only=False)`. The `WHERE` is built from the clauses present; `if
  source_app:` is kept verbatim, so the collector's and the dashboard's calls
  are byte-identical reads.
- `docker/compose/docker-compose.yml`: the `api` service as the plan's
  "Configuration" writes it — every mount `:ro`, no docker socket, root,
  `127.0.0.1:8789`.
- Tests: `tests/observability/test_api.py` (the five endpoints against a
  `tmp_path` standing in for the four mounts), `unreadable()` and `index_rows`
  cases in `tests/dispatcher/`, `since`/`read_only` cases in
  `tests/observability/test_collector.py`, the dashboard's realm pinned in
  `tests/observability/test_dashboard.py`, and a compose invariant that the
  `api` service never grows a socket or a writable mount.

`dispatcher/dispatcher.py`, the dashboard's rendering, `config.example.yaml`
and `docs/plans/board.md` are untouched, as "Out of scope for Phase 1"
requires.

## Why this way

**The envelope is checked in one place per route, not per read.** Every 200 goes
through `_envelope(data, warnings)` and every non-200 through `_error(message,
status)`, so a route cannot answer a bare array by accident. Warnings name
files, never states: a reader deciding whether to retry needs the path.

**The board is built in the API, not taken from `dispatcher/cli.py`.**
`_read_cards` constructs `LocalBoardClient` from the config because this service
is the one caller that has to know which implementation it got — `unreadable()`
is deliberately outside the shared seam (ADR 4), and the parity test in
`tests/dispatcher/test_vibe_kanban_client.py` names it as the single exception
so the next local-only method still has to argue for itself.

**`_is_bare_task_id` is the second lock, not the first.** Werkzeug's default
converter declines a `/` before the view runs (probed, then deleted: `..%2F…` is
a router 404), so the guard is what keeps a later `<path:task_id>` from turning
the route into a file reader. It is unit-tested directly for that reason.

**An empty parameter value reads as absent.** The plan writes
`/api/events?limit=&source_app=&since=` out as a URL, so that request has to be
legal; anything else non-integer is a 400 rather than a silent fall back to the
default.

**`_UNREADABLE` includes `yaml.YAMLError`.** It is not a `ValueError`, and
`context_transfer.read_task_file` raises it for frontmatter that does not scan
— which is exactly the hand-edited file this endpoint exists to report.
Measured: dropping it makes `test_a_task_file_whose_frontmatter_does_not_scan…`
raise `ParserError` out of the request.

**The two ways `/api/events` comes back empty say different things.**
`_no_events_warning` tells a cold start (`no events database yet`) from a
database that is there and will not open, because sqlite's own message —
`unable to open database file` — describes neither, and the second one is a
mount to argue with rather than something to wait out. See below for why that
case is expected rather than hypothetical.

## The events volume is `:ro` and the collector writes WAL

This is the one thing in the phase that measurement contradicted, and it is
carried as debt rather than fixed, because the `:ro` mount is the spec.

`observability/collector/db.py` sets `PRAGMA journal_mode=WAL`, which is stored
in the database file, and the collector opens and closes a connection per
insert — so the `-wal`/`-shm` pair is checkpointed away and usually absent. A
throwaway probe under `tests/observability/` (deleted) listed the directory
during a `connect_read_only` read of a cleanly-closed database:

```
after_write=['events.db'] during_read=['events.db', 'events.db-shm', 'events.db-wal'] rows=(1,) journal_mode=wal
```

A WAL reader needs the shared-memory file and creates it when no writer holds
one. `mode=ro` stops sqlite creating the *database*; it does not make the open
free of writes. On `observability_data:/events:ro` those creates cannot happen,
so `/api/events` is expected to answer `[]` plus a warning against the real
stack while the dashboard — same volume, mounted read-write — shows the same
events fine. Debt **T-009-D4** below; the shared trap is
`/data/.hive/learnings/inbox/T-009-a-read-only-sqlite-open-creates-wal-sidecars.md`.

That prediction was checked against the running stack on 2026-09-26 and held
exactly: the collector counted 2974 rows in the same file the api saw over
`/events`, and the api answered `[]` plus the warning. T-009-D4 was fixed the
same day — the mount is now `observability_data:/events` with no options in both
compose files, nothing in `observability/api/app.py` changed, and `/events` is
named in `API_WRITABLE_MOUNTS` so every other mount is still asserted `:ro`.
`docs/ROADMAP.md`'s results log carries the row.

## What was ruled out

- **`immutable=1` as a fallback after `mode=ro` fails.** It would make
  `/api/events` work on a `:ro` mount by telling sqlite the file cannot change,
  which against a live collector is how a reader gets undefined results instead
  of an empty list. An empty list with a warning is the honest answer.
- **Mounting the events volume read-write and simply never calling
  `init_db`.** That is the fix for T-009-D4 and it is a change to the plan's
  own "Configuration" block, which this phase was handed verbatim; a phase does
  not get to relax the mount that makes handing a web process root-owned state
  defensible.
- **Reading cards through `VibeKanbanClient` when `vibe_kanban` is
  configured.** ADR 3: an MCP subprocess per request, in an image with no node,
  inside a request that must never 500.
- **A second frontmatter, account-state or debt-table parser under
  `observability/`.** `index_rows` exists precisely so there is not one:
  `read_index` reaches a project's index through `docker exec` and the row
  parsing behind it was private, which is the only reason a path-based caller
  had no way in.
- **Putting the endpoints in the dashboard.** Phase 2 deletes it, so they would
  move twice, and it would widen what one auth bug reaches from the events
  table to the task files and `dispatcher_state/`.
- **A cap on `limit`.** Policy this phase was not given and cannot configure —
  no new keys. Debt T-009-D2.
- **A `docs/ROADMAP.md` verification row.** A row there would claim the by-hand
  `curl` check, which no phase may run against the live stack. The root
  `README.md` was a different case and was corrected in round 2 — see below.
  (The check was run by hand on 2026-09-26, out of cycle, and the row exists now:
  `docs/ROADMAP.md`, results log, last entry. It reports the auth sequence, every
  route, and the three things only a live stack could settle — T-009-D4
  confirmed and fixed, T-009-D3 reproduced over HTTP and left open, and the first
  unconfirmed rule in `docs/business.md` confirmed by the API's own error text.)

## Round 2 — what review changed

Five findings (`/data/.hive/tasks/T-009/revisor-round-1.md`, F1–F5). One was a
contract violation in the code; the rest were documents this change falsified
and one deploy path it skipped.

**F1 — parsed is not shaped.** `_UNREADABLE` covered a missing delimiter, a
scan failure and a missing key, and missed the third way a task file fails:
frontmatter that scans cleanly into something that is not a mapping.
`---\nTODO write this up\n---` is a `str`, a list of bullets is a `list`, and
`read_task_file`'s `fm["task_id"]` then raises `TypeError` — not a `ValueError`,
so the envelope's own rule broke on exactly the hand-edited file it exists to
report. Same shape one layer over: a `dispatcher_state/<account>.json` holding a
JSON array survives `json.loads` and then fails in `get_state`'s `data["state"]`
(`TypeError`) or `get_current_task`'s `data.get` (`AttributeError`). `TypeError`
joined `_UNREADABLE`, `TypeError` and `AttributeError` the `accounts` view's
tuple, and two tests pin both — each written first and each seen as a 500.
Widened in the API only: the readers in `dispatcher/` keep their narrow
contracts, because a caller that wants a crash there should still get one.

**F2 — `docs/learnings/the-kanban-seam-is-a-closed-surface.md` had gone false.**
It said the parity test refuses a local-only public method categorically, and
named "a Phase 1 reader method" as an example of what fails — which is this
task's `unreadable()`, now passing. Corrected to the rule the tests actually
hold: `VibeKanbanClient`'s names plus whatever `LOCAL_BOARD_ONLY` names, each
entry owing an ADR and the standing condition that `dispatcher/dispatcher.py`
never calls it. The evidence section now also records that the old assertion
compared against the *union* of both clients' names, so it had never failed a
superset at all.

**F3 — `docker-compose.coolify.yml` had no `api` service.** That file is the
documented one-resource deploy path, so the read API existed only for operators
running the split files, and Phase 2 would have been built against a service
that deploy path never starts. The service is mirrored there beside `dashboard`
with the same build stanza, port, mounts and `depends_on` (the bind-mount
sources are the same relative paths in both files), and
`test_the_read_api_gets_no_socket_and_only_the_events_volume_is_writable` now
parametrizes over both, as the dispatcher-profile test already did. Every mount
was `:ro` when this task shipped and the test was named for that; the events
volume became the one exception when T-009-D4 was fixed out of cycle on
2026-09-26, which is where the rename comes from.

**F4 — four wrong sentences in the root `README.md`.** Not omissions: the stack
paragraph said `up -d` brings up three persistent services, the layout block and
the Coolify enumeration both listed two things in `observability/`, and known
gap 6 attributed the development server and the unsalted digest to the collector
and dashboard alone. All four now count and name the read API, and gap 6 says
which of the three that shared digest guards the most — this one, which serves
the task files and root-owned `dispatcher_state/` rather than an events table.
A sentence naming `/api/*` on `127.0.0.1:8789` and pointing at ADR 3–5 was added
where the observability stack is introduced. Still no ROADMAP row, for the
reason above.

**F5 — ADR 5 promised a JSON error body Flask does not honour.** True of every
response this module constructs and not of the two Flask raises for itself:
`POST /api/tasks` answers 405 and `GET /api/nope` answers 404, both
`text/html`. The bullet is narrowed to "every non-200 this module returns" and
now says what the other two are; `test_flasks_own_404_and_405_are_html_not_this_envelope`
pins it, so a later task that registers `errorhandler`s to make the promise
unconditional fails there and updates the ADR with it. Narrowed rather than
handled, on the reasoning the finding gave: an envelope over a typo'd path makes
a routing mistake look like an endpoint's answer.

## Round 3 — what review changed

Three findings (`/data/.hive/tasks/T-009/revisor-round-2.md`, F6–F8). Two were
the same rule broken twice — a read that answers 500 — and one was the index row
round 2's doc fix left behind.

**F6 — an integer parameter SQLite cannot bind was a 500.** `_int_parameter`
accepted anything `int()` accepted and `db.list_events` bound it into `LIMIT ?`
and `WHERE id > ?`. SQLite integers are signed 64-bit, so `?since=2**63` raised
`OverflowError: Python int too large to convert to SQLite INTEGER` — not a
`sqlite3.Error`, not an `OSError`, not a `ValueError`, so none of the events
view's `except` clauses saw it. The module's own rule failed on a query string,
with no file involved at all, and Phase 3's tail is the caller most likely to
send a lost cursor. Validating one of these is two checks: `int()` parsed the
text, *and* the result fits. `_SQLITE_INT_MIN`/`_SQLITE_INT_MAX` bound it and the
answer is a 400 like every other bad parameter — a caught `OverflowError` would
have reported a database that could not be read when the database was never the
problem. The test is parametrized over both parameters and pins both ends:
`9223372036854775807` is a 200 and `9223372036854775808` a 400, so it cannot pass
by rejecting every large number. ADR 5's 400 list carries the case, saying why it
is not the `limit` cap this phase declared as debt.

**F7 — a `local_board.dir` that is a regular file was a 500.**
`LocalBoardClient._scan` catches `FileNotFoundError` only, so `os.listdir` on a
file raised `NotADirectoryError` out of `board.unreadable()` before `list_issues`
was reached, and `/api/tasks` and `/api/tasks/<id>` both 500'd — from the one
function whose docstring is about reporting a board it could not read. Fixed with
`except OSError` around both board calls in `_read_cards`, answering no cards and
one warning naming the directory. `_scan`'s own `except` was deliberately left
alone: for the dispatcher a broken board that reads as empty is worse than an
exception, because `create_issue` would then mint cards nobody can list. That
asymmetry — never-500 on the API side, raise on the dispatcher side — is now in
ADR 5 beside the other warning cases, since it is a warning Phase 2 can receive.

**F8 — the corrected learning left its index row behind.**
`docs/learnings/README.md`'s "What it says" cell still carried the categorical
claim round 2 removed from the file body, still marked `confirmed`, and that
column is what a phase scans *instead of* opening the file. One cell now states
the rule the tests hold, `LOCAL_BOARD_ONLY` and its condition included. Status
stays `confirmed`: the entry is true, only its summary had gone stale.

## Round 4 — what review changed

Three findings (`/data/.hive/tasks/T-009/revisor-round-3.md`, F9–F11) and no
round 4 phase to apply them: the dispatcher hit `max_revision_rounds: 3` and
blocked the task with the third review unaddressed. They were applied here by
hand, on the branch, out of cycle, and only the auditor phase was dispatched
over the result. All three are the same mistake in three places, and the single
cause is that each `try` ended after the *parse* instead of after the *use* — so
a frontmatter value of the wrong shape raised where it was used, outside every
`except` in the module, and the module's one rule is that no read answers 500.

**F9 — a frontmatter value of the wrong type was a 500.**
`context_transfer.read_task_file` hands back `fm.get("kanban_issue_id")` as
whatever YAML built there, and `_task` uses it as a dict key: `cards.get(…)`. A
`kanban_issue_id` written as a mapping or a sequence is unhashable, so the lookup
raised `TypeError: unhashable type: 'dict'` — or `'list'` on the single-task
route — one line past the end of the guard. Both views now shape the row inside
the `try`. The input is exactly what this API exists to survive: a task file some
phase wrote by hand.

**F11 — a value YAML builds and JSON cannot was a 500.** The same seam one step
later. `owner: !!set {a: null}` parses, shapes, and then raises `TypeError:
Object of type set is not JSON serializable` inside `jsonify` — past every
`except` in the module, because the raise happens while the response is being
written and not inside the view. The row is now serialised inside the same guard
as F9: one line, `app.json.dumps(row)`. It is `app.json.dumps` and deliberately
not `json.dumps`. Flask's provider renders a `datetime.date` as an HTTP date
string where the stdlib refuses it, and `owner: 2026-09-26` answers 200 today;
pre-checking with the stdlib would have turned a working read into a warning. A
test asserts that date is still a 200 with an empty `warnings`, so narrowing the
dumper later fails loudly instead of regressing quietly.

F11 could have been filed as debt instead — the revisor allowed either one, not
both. It is closed because the guard that closes F9 had to exist anyway and the
check costs one line inside it. The only genuinely new decision is which dumper,
and that is now pinned by a test.

**F10 — a board whose cards will not sort against each other was a 500.**
`LocalBoardClient._read_path` validates that a card is a mapping with a string
`issue_id` and leaves every other field as whatever was on disk; `_scan` then
sorts on `created_at`. Two cards whose `created_at` are of different types
compare a `str` against an `int`: `TypeError: '<' not supported between
instances of 'str' and 'int'`, which round 3's `except OSError` in `_read_cards`
does not catch. Widened to `except (OSError, TypeError)`, and the warning
shortened to "unreadable board" because the directory is no longer the only
thing that can be wrong with it. `_scan` and `_read_path` were left alone on
purpose, for the reason F7 gives: that is a `dispatcher/` contract this service
has no business changing, and never-500 belongs on this side of the seam.

**The claim is now bounded where it is made.** ADR 5 gained a bullet stating
what never-500 covers and what it does not: the guard is per task row, so
`/api/accounts`, `/api/events` and `/api/debt` are not serialisation-checked —
they shape their own rows out of `str` and `int` and have no frontmatter that
could carry a `set` — and a later endpoint returning anything a parser built
inherits the obligation, not the guarantee. The module docstring's never-500
bullet now cites that ADR rather than stating the claim flat.
