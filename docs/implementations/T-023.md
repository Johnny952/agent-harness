# T-023 — a cycle held for lack of an account exits 75, not 0

`run-task` exited 0 however its cycle ended. A cycle that stopped because no
account could take its next phase looked, to a script or to an operator who
only read the exit code, like one that had shipped. That happened twice on
2026-10-09 (`docs/plans/token-economy.md` P7). This task gives the cycle a
typed ending, maps it to an exit code in the CLI, does the same for
`run-phase`, and records the code as `docs/decisions.md` ADR 52. Scope:
`dispatcher/dispatcher.py`, `dispatcher/cli.py`, their tests, `README.md`,
`docs/decisions.md`, P7 in `docs/plans/token-economy.md`, this file.

## Verified first-hand, not taken from the plan

| Claim | Where | Verdict |
|---|---|---|
| A cycle that stops for lack of an account exits `rc=0` | `dispatcher/cli.py:main`, the `run-task` branch, ignores what `run_task_cycle` returns; `dispatcher/dispatcher.py:run_task_cycle` returns None on every path | true |
| It is one ending among several that all exit 0 | `run_task_cycle` | true, and wider than P7 says: every blocked ending exited 0 too (table below) |
| The CLI already uses 1 for errors | `cli.py:main` (`merge-task`, `run-phase`, `release-account`) and `cli.py:_run_learnings` | true; argparse's `parser.error` adds 2 |
| "No account" is a single condition | `dispatcher.py:dispatch_phase` | true: every account tried, every one cooling, and every one held back by `check_quota_ok` all reach the same `"no accounts available"` return |
| It is distinguishable from other failures as it stood | `DispatchResult` | differs: it carries `account=""`, which a failure from anywhere else can share, so an explicit field was needed |
| It happened twice on 2026-10-09 | — | not checkable from the code; taken as the operator's record |

Also found, not in the plan:

- `run-phase` already exited 1 for a phase that did not land, so it treated a
  phase that never got an account the same as one that crashed.
- `run_phase` logs "did not finish, so the cycle stops here" for both, and
  the comment above it noted that the run "ends at exit 0".

## Every way `run_task_cycle` ends

| Ending | Class | Exit before | Exit now |
|---|---|---|---|
| `open_cycle` returns None (no description; the CLI rejects it first) | blocked | 0 | 1 |
| `update_project_branch` reports `blocking` (the branch diverged from its remote) | blocked | 0 | 1 |
| The optional map bounced off another owner's lock (`ctx.foreign_lock`) | blocked | 0 | 1 |
| The arquitecto, an implementador, a revisor or the auditor returned None because no account took it | **held** | 0 | **75** |
| The same phases returned None because they failed, or hit a foreign lock | blocked | 0 | 1 |
| The arquitecto's handoff is `blocked` | blocked | 0 | 1 |
| The revisor read declarations as blocks (`debt.blocking`), which breaks the loop unapproved | blocked | 0 | 1 |
| The rounds ran out without an approval, including every round gated | blocked | 0 | 1 |
| The auditor closed the task, merged or not | finished | 0 | 0 |

The mapper finding no account is not a hold. It is `fatal=False`, and the
task runs on without it, so the run ends however its later phases end.

## What was built

**The outcome.** `dispatcher.py:CycleOutcome` is an enum: `FINISHED`, `HELD`,
`BLOCKED`. `run_task_cycle` returns one on every path. It used to return
None. No caller in the package read that None (`dispatcher/operator.py` names
the function only in comments), and the CLI was the one to change.

**The signal.** `DispatchResult.no_account` is set only by `dispatch_phase`'s
no-account return. `run_phase` copies it to `CycleContext.held` when a phase
the task depends on stops on it, next to where `foreign_lock` is set for the
same reason: the phase knows, and the cycle reads it. Each stop after a phase
that returned None goes through a local `stopped()`. The card is blocked the
same as before.

**The codes.** `cli.py:EXIT_HELD = 75` and `EXIT_BLOCKED = 1`. 75 is
sysexits.h's `EX_TEMPFAIL`, "try again later". 1 would merge held into
blocked, and 2 is argparse's. Each nonzero exit prints one line to stderr
saying which it was. The reasoning is ADR 52.

**`run-phase`.** The change is the same and just as small.
`run_single_phase` returns the unsuccessful result, with `no_account` set,
instead of None, and the CLI exits 75 on it. It still returns None for a
phase that failed, so `result is None` keeps meaning exit 1. Its
`close_cycle(completed=...)` reads its own local, which stays None on that
path, so the entries a `--final` carried are still orphaned.

**The tests.**
- `tests/dispatcher/test_cli.py` covers `run-task`: finished exits 0, held
  exits 75 (and not 1), blocked exits 1. It also covers `run-phase` held
  exiting 75. `_capture_cycle` now returns an outcome, and
  `_capture_single_phase`'s default is a real successful `DispatchResult`
  rather than `object()`.
- `tests/dispatcher/test_dispatcher.py` checks that:
  - the cycle is `FINISHED` on the approving path;
  - it is `HELD` when no account takes any one of the four phases, with the
    card blocked;
  - it is `BLOCKED` on a phase that failed by itself, on rounds run out, and
    on no description;
  - the map finding no account leaves the cycle `FINISHED`;
  - `run_single_phase` hands back the held result.
- An existing `dispatch_phase` test now also asserts `no_account`.

**The docs.** `README.md` *5. Run a task* has the exit-code table, and its
`run-phase` paragraph names the two codes. P7 has a "Built by T-023"
paragraph, and the plan's Status line says P7 is built.

## What was ruled out

- **Raising from `dispatch_phase` or `run_phase`.** Every stop already
  returns through `close_cycle`'s `finally`. An exception would have to be
  caught at the CLI and kept away from the mapper, which is not fatal. An
  exit code means something only in the CLI.
- **Reading `account == ""` as the signal.** The test fakes, and any failure
  that is not the pool's, use it too.
- **Holding the card in a status of its own.** That is a board and console
  change outside this task. The card stays blocked, so only the exit code and
  the log tell held from blocked.

## What is left

- **Blocked now exits 1 where it exited 0.** Only held was required to
  change. Blocked uses the same mapping and the same code `run-phase` already
  used, so it was taken here, but it is a behaviour change. Nothing in the
  repo reads `run-task`'s exit code. A wrapper outside it that treated any
  nonzero exit as a crash will now see one for every blocked task.
- **A refused merge after a finished cycle still exits 0.** The task is done
  and `merge-task` reports merges. A script that relies on `merge_on_done`
  cannot tell from `run-task`'s code that the merge was refused. It reads the
  log, or runs `merge-task` itself.
- **The board does not tell held from blocked.** Both block the card.
- **The token-economy Status line** is also where T-022 (P1–P3) records its
  own status, so a merge of the two will touch the same sentence.
- `docs/README.md` lists the CLI's verbs without `run-phase` and `status`.
  That predates this task and was not changed.
