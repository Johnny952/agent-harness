# T-080 — The board service, reads only (board-service step 4)

Decisions: `docs/decisions.md` ADR 124 and ADR 125. ADR 124 settles where
the board's write side lives: a root-level package and a service of its own.
The git credential and both pushes stay on the dispatcher. ADR 125 covers
the transport (stateless MCP over HTTP from the service's own handler), the
role check, and what `board_list` and `board_get` serve.

## What was built

- `board_service/__init__.py` and `board_service/app.py` (new):
  - `create_app(config_path)` loads the config once with
    `dispatcher.config.load_config` and reads `hive_tasks_dir`.
    `main(environ)` takes `CONFIG_PATH`, default `/app/config.yaml`, and
    exits 2 when the file is not there. `PORT` is 8792.
  - `POST /mcp?role=<role>` is JSON-RPC 2.0, one message per POST. It
    answers `initialize`, `ping`, `tools/list` and `tools/call`.
    Notifications get 202. `GET` and `DELETE` on `/mcp` get 405. Any
    `Origin` gets 403. `GET /health` answers `{"ok": true}`.
  - `KNOWN_ROLES` is `PHASE_ROLES` plus `operator`. `ROLE_TOOLS` is
    section 6's read rows: operator and arquitecto get both tools, and
    every other role gets none. The role is checked again on each
    `tools/call`.
  - `board_list(hive, place, status, epic, text)` and
    `board_get(hive, task_id)` are plain functions, read through
    `context_transfer` and `tasks`. A tool failure is an `isError` result.
  - It writes nothing, anywhere.
- `board_service/Dockerfile` (new): `python:3.11-slim`. It copies
  `pyproject.toml`, `dispatcher/` and `board_service/`, then
  `EXPOSE 8792` and runs `python -m board_service.app`. `dispatcher/`
  imports nothing outside itself; this was checked by importing the
  service from a copy that has only those two packages.
- `pyproject.toml`: `board_service*` added to `include`.
- `tests/board_service/__init__.py` and `tests/board_service/test_app.py`
  (new, 51 tests). They cover:
  - the handshake: every known version echoed, and the newest offered
    for an unknown one, with no session header;
  - notifications, `ping`, an unknown method, 405 on GET and DELETE, the
    Origin refusal, a body that is not JSON, a batch, and `/health`;
  - the role check:
    - a missing, unknown or wrongly cased role is 400, and so is an extra
      query parameter;
    - operator and arquitecto see both tools;
    - every other phase role sees none and is refused both calls;
    - an unknown tool is refused;
  - `board_list`:
    - its rows;
    - the title from the frontmatter, from the Goal, cut, and `null`;
    - each filter alone and combined;
    - bad and unknown arguments;
    - unreadable, unmigrated and `task_id`-less files as warnings;
    - the clamp, and a missing hive;
  - `board_get`:
    - the frontmatter, the description, and the comment count, with blank
      lines skipped and 0 when the file is absent;
    - YAML dates as text, and `place` from the status;
    - a missing task, a path id, a draft id and the drafts directory;
    - a missing `task_id`, and an unmigrated file;
  - no writes:
    - a snapshot of the tree (mode, size, mtime) is unchanged by every
      kind of call;
    - both tools work over a hive whose directories are 0555;
  - `main` without a config, `main` from the environment, and the
    Dockerfile and `pyproject.toml` lines.
- Docs: ADR 124 and ADR 125, and this file.

## Why this way

- **A package of its own, not the api.** The api writes nothing, and that
  is what lets it be reachable at all (`front.md` *Tier 3*). Step 5 puts
  writes on this process, so it starts as its own package and service, as
  ADR 75 did for the config writer.
- **The credential stays out.** ADR 78 already says what the pushes use. A
  service with no key, token or checkout cannot push, whatever reaches it.
- **A hand-rolled transport.** The `mcp` package is in `.venv` but is not
  one of the project's dependencies, and adding it is a network install.
  The stateless JSON form of streamable HTTP is small: a handshake, a list
  and a call. It also needs no session state, so a restart costs a client
  nothing.
- **An unknown role is 400, not an empty list.** A misspelt `?role=` in a
  `--mcp-config` would otherwise look like a role that has no tools.
- **A title from the Goal.** No task file has a title yet. Without one, a
  list of ids tells a model nothing. A frontmatter `title` wins once
  step 5 writes one.
- **The comment count is a line count.** Nothing writes `comments.jsonl`
  yet. A count is what section 6 serves, and counting does not break on a
  damaged line.

## The compose entry

For `docker/compose/docker-compose.yml`, after `config-writer`. It is not
applied.

```yaml
  # The board service (docs/decisions.md ADR 124 and ADR 125): the board's
  # MCP server, and from board-service step 5 its write side. It reads the
  # hive through dispatcher/tasks.py. For now every mount is :ro, and the
  # hive becomes writable with step 5's first write. No docker socket, no
  # .data, no projects, no git credential: the pushes stay on the
  # dispatcher. It is on ia_harness_net for the phases and on console_net
  # for the console. It publishes on loopback only, for the operator's
  # Claude Code session on the host.
  board-service:
    build:
      context: ../..
      dockerfile: board_service/Dockerfile
    restart: unless-stopped
    ports:
      - "127.0.0.1:8792:8792"
    volumes:
      - ../../.hive:/data/.hive:ro
      - ../../config.yaml:/app/config.yaml:ro
      - ../../config.d:/app/config.d:ro
    networks:
      - ia_harness_net
      - console_net
```

Two notes on it:

- **The port.** The plan has the service publish no port beyond the
  console's proxy. The operator's session runs on the host, though, and
  reaches a container only through a published port. Loopback-only is
  config-writer's precedent. If the user would rather keep the plan's
  wording, drop `ports` and leave the operator's session to step 7's
  route.
- **Step 4 needs only one network.** The phases' `--mcp-config` arrives
  in step 7 and the console's writes in step 5. Both are listed now so the
  entry does not change shape later. Either one can wait.

## The operator's session

Not applied. The project's `.mcp.json` would hold this:

```json
{
  "mcpServers": {
    "board": {
      "type": "http",
      "url": "http://127.0.0.1:8792/mcp?role=operator"
    }
  }
}
```

The operator's `.claude/settings.local.json` would enable it:

```json
{
  "enabledMcpjsonServers": ["board"]
}
```

Or the same server can be added for the operator alone, with no file in
the repo:
`claude mcp add --transport http --scope local board "http://127.0.0.1:8792/mcp?role=operator"`.
A committed `.mcp.json` would also be read by the clones under
`.data/projects/`. Those are phases, and each phase must get its own role
through `--mcp-config` (step 7), not `operator`. So the local scope is the
safer of the two until step 7 lands.

## Ruled out

- The `mcp` package as a dependency, and a session id.
- The writes, or any part of them, in the api.
- A git credential or a push in the service.
- A signal from the service to the dispatcher.
- An empty tool list for an unknown role.
- Parsing `comments.jsonl` to count it.
