# T-172 — waitress for the board service and the config writer, and its log line

Decisions are `docs/decisions.md` ADR 420; this records how it was built.

## What

- `board_service/app.py`: `HOST`, `THREADS = 8`; `serve` builds the app, starts
  the push notifier, calls `_log_waitress()`, then imports waitress lazily as
  `waitress_serve` (the module's own function is `serve`).
- `config_writer/app.py`: `HOST`, `THREADS = 4`, a new `run(environ=None)`;
  `__main__` calls it.
- `observability/collector/server.py`, `observability/api/app.py`: `run` calls
  `_log_waitress()` before serving.
- `_log_waitress()` sets the `waitress` logger to INFO and, if it has no
  handler, adds a stderr `StreamHandler` with `BASIC_FORMAT`. It is called from
  the entry point, never at import.
- `tests/conftest.py`: an autouse fixture restores the `waitress` logger's level
  and handlers after every test, so a handler bound to a closed capture stream
  is never inherited.
- Tests per service: serve kwargs, refusal with `sys.modules["waitress"] = None`,
  and a logging pin (INFO start line and queue WARNING reach stderr, root logger
  untouched).
- Docs: ADR 420, `T-171-D1` resolution row and log paragraph, README bullet,
  `docs/README.md` dependency line.

## Why this way

- Four copies of the helper, not a shared module: no module ships in all four
  images (ADR 420).
- Logger configured on `waitress` itself, not `logging.basicConfig`: pytest puts
  handlers on the root logger, so `basicConfig` is a no-op under test and would
  alter importers' logging in production.
- The `T-171-D1` row is rewritten in place as resolved, as T-008-D1 is: a second
  row with the same id fails `test_this_repositorys_own_index_has_no_repeated_entry`.

## Not done

Redeploying containers, compose and Dockerfiles (out of scope). The real waitress
was not run: the agent venv has none, so every test uses a `sys.modules` stand-in.
