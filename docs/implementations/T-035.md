# T-035 — a test pins the task page header's description

This task resolves `docs/debt/T-034-D1.md`: the task page gets its first
test file, `front/src/routes/-tasks.test.tsx`, which mounts the page and
reads its header for a task with no description, a task with one, and a
card the api could not read; and
`front/src/components/console/primitives.test.tsx` gets one `PageHeader`
case with a node as `subtitle`. No production file changes. The one edit
outside the two test files is a fourth, optional argument on `renderRoute`
in `front/src/test/render-route.tsx`, which the card's *Surface* admits as
a helper the new test needs. No ADR is written: `docs/decisions.md` is
outside this card, so what a later task could undo is under *Decisions*.

The sections down to *Verification the implementador owes* are the
arquitecto's design. The implementador corrects them where the tree turns
out different and lists those corrections under *Where the build differs
from the design*.

Nothing was different. One thing the card does not say, and it decides the
design:

**`renderRoute` cannot mount a route with a parameter as it stands.** It
takes one `path` and uses it twice: as the `path` of the route it builds
and as the memory history's first entry. Every screen mounted so far has a
path with no parameter (`/`, `/debt`, `/learnings`, `/tail`), where the two
are the same string. The task page calls `Route.useParams()` for `taskId`.
Given `/tasks/T-101`, the harness's route has no parameter, so the page
reads no `taskId` and asks for `/api/tasks/undefined`. Given
`/tasks/$taskId`, the location is that literal text and the id is
`$taskId`. So the card's "mounts `/tasks/<id>` through `renderRoute` … the
way `-index.test.tsx` and `-debt.test.tsx` do" needs the route's path and
the location handed apart. See *Decisions*, 1.

## Every read the page makes

Read off `TaskDetailPage`, `AppShell` in
`front/src/components/console/app-shell.tsx`, and each child the page
renders, then off `front/src/lib/api/client.ts` for the path.

| Read | Who asks | Path on the wire | Served by the test |
|---|---|---|---|
| `taskQuery(taskId)`, `getTask` | `TaskDetailPage` | `/api/tasks/T-101` | yes: the task under test, or `data: null` |
| `debtQuery`, `listDebt` | `TaskDetailPage` | `/api/debt` | yes, `[]` |
| `phasesQuery(taskId)`, `listPhases` | `TaskDetailPage` | `/api/phases?task_id=T-101` | yes, `[]`, keyed `/api/phases`: `stubApi` matches the pathname |
| `learningsQuery`, `listLearnings` | `TaskDetailPage` | `/api/learnings` | yes, `[]` |
| `actionBackendQuery`, `pingActionBackend` | `AppShell` | none: a fixture behind a 120 ms timer, no `fetch` | nothing to serve |
| `threadsQuery`, `tasksQuery` | `ChatPanel` | `/api/tasks` for the second | not asked: `AppShell` mounts `ChatPanel` only once the chat is opened, and the test never opens it |

Why the three secondary reads are served though no assertion reads them:
an unserved path answers 404, and the page draws an `ErrorState` in that
region ("/api/phases did not answer", "The debt index did not answer",
"The learnings tree did not answer"). The header would still be right, but
the test would be passing over a page that reports three broken reads, and
the harness's own rule is that a missing stub is a failure to notice. With
`[]` each region draws its empty sentence.

No path the page asks for is left unserved. `Markdown`, `PhaseList`,
`PhasePill`, `InPhaseTable`, `LearningStatus`, `HeartbeatDot` and
`RefreshedAt` make no read; `useNow` and `RefreshedAt` only set timers,
which `cleanup` clears with the unmount.

## Decisions

1. **`renderRoute` takes an optional fourth argument, `at`: the location
   to open the route on, defaulting to `path`.** `path` stays the route's
   own path, so the task page is mounted as
   `renderRoute(Route, "/tasks/$taskId", served, "/tasks/T-101")`. The
   five existing calls pass three arguments and get what they got. The
   alternatives were worse: a second helper would copy the stub and the
   router, and passing `/tasks/$taskId` as the location makes the id the
   text `$taskId`. A later task that folds `at` back into `path` breaks
   the task page's test and no other.
2. **The header is found by its heading, not by a class.** The test takes
   the level-1 heading named `T-101` and reads the block it sits in, which
   is what `PageHeader` draws: the title and the subtitle under it. That
   is how the test says "in the header" without naming a class.
3. **The test waits on the page's own text before reading the header.**
   The `<h1>` is drawn before the read lands, with no subtitle, so reading
   the header at once would pass the string case's negative for the wrong
   reason. Each case first awaits a text only its state draws: *task body*
   for a task that was read, the empty state's title for `data: null`.
4. **A third case covers the card the api could not read.** `subtitle` has
   three arms and `docs/implementations/T-034.md` *Decisions*, 3 is the
   third: no claim about a description for a task nothing has read. An
   edit to `t?.description ?? <Absent … />` would break it and the two
   cases the card asks for would both still pass.
5. **The fixture is annotated `TaskDetail`.** The served body is `unknown`
   to `renderRoute`, so without the annotation a later narrowing of `Task`
   would leave this literal stale and nothing would say so
   (`docs/learnings/narrowing-a-served-type-is-also-a-fixture-edit.md`).

### `front/src/routes/-tasks.test.tsx` (new)

```tsx
/**
 * The task page's header, read off the mounted route. `TaskDetailPage` builds
 * the subtitle itself and hands it to no component of its own, so there is
 * nothing to export and render alone: the page is mounted with `renderRoute`
 * and the header is read where the operator reads it. Three arms, one test
 * each: a task with no `description.md` says *no description*, a task with a
 * description shows it, and a card the api could not read claims neither.
 * `docs/debt/T-034-D1.md`.
 *
 * The page asks for four paths and all four are served, because one left out
 * answers 404 and the page draws that region's error state:
 * `docs/implementations/T-035.md` *Every read the page makes*.
 *
 * The `-` on the filename is load-bearing; see `-index.test.tsx`'s header.
 */
import { afterEach, describe, expect, it } from "vitest";
import { cleanup, screen } from "@testing-library/react";
import { Route } from "./tasks.$taskId";
import { renderRoute } from "@/test/render-route";
import type { TaskDetail } from "@/lib/api/types";

// `vitest.config.ts` sets `globals: false`, so the library's own cleanup hook
// never runs, and every render would stack in one document.
afterEach(cleanup);

const DESCRIPTION = "the pool screen says which account holds a lock";

/**
 * A task nobody holds, with nothing below the header that could repeat the
 * description: no dependencies, an empty body.
 */
const TASK: TaskDetail = {
  task_id: "T-101",
  status: "pending",
  owner: null,
  depends_on: [],
  heartbeat: null,
  description: DESCRIPTION,
  resolved_debt: [],
  lock_expired: null,
  body: "",
};

/** The page at `/tasks/T-101`, with `data` as what the api answered for it. */
async function taskPage(data: TaskDetail | null, warnings: string[] = []) {
  await renderRoute(
    Route,
    "/tasks/$taskId",
    {
      "/api/tasks/T-101": { data, warnings },
      "/api/debt": { data: [] },
      "/api/phases": { data: [] },
      "/api/learnings": { data: [] },
    },
    "/tasks/T-101",
  );
}

/** The block the page's title sits in: the task id and the subtitle under it. */
function header(): HTMLElement {
  return screen.getByRole("heading", { level: 1, name: "T-101" }).parentElement as HTMLElement;
}

describe("the task page's header for a task with no description", () => {
  it("says so under the task id", async () => {
    await taskPage({ ...TASK, description: null });
    // The title is drawn before the read lands; this is drawn after it.
    await screen.findByText("task body");
    expect(header().textContent).toContain("no description");
    expect(header().textContent).not.toContain("null");
  });
});

describe("the task page's header for a task with a description", () => {
  it("shows the description and does not call it absent", async () => {
    await taskPage(TASK);
    await screen.findByText("task body");
    expect(header().textContent).toContain(DESCRIPTION);
    expect(screen.queryByText("no description")).toBeNull();
  });
});

describe("the task page's header for a card the api could not read", () => {
  it("claims nothing about a description", async () => {
    await taskPage(null, ["T-101: the task file could not be parsed"]);
    await screen.findByText("T-101 exists and could not be read");
    expect(header().textContent).toBe("T-101");
    expect(screen.queryByText("no description")).toBeNull();
  });
});
```

The `header` return line is 95 columns, under prettier's 100. Without the `Absent` arm the first
test finds a header that reads `T-101` alone.

## Where the build differs from the design

Nowhere in the code: the three edits under *The edits* are in the tree as
written there. The implementador re-read `renderRoute`, `TaskDetailPage`,
`PageHeader`, `Absent`, `EmptyState`, `TaskDetail` and the four client
functions before editing, and each claim the design rests on held:

- `PageHeader` puts the `<h1>` and the subtitle's `<p>` in one inner
  `<div>`, with `right` in a sibling, so the heading's parent holds the
  title and the subtitle and nothing else. `RefreshedAt` is outside it.
- `AppShell` in `front/src/components/console/app-shell.tsx` draws no
  `<h1>`, so the level-1 heading named `T-101` is the page's.
- *task body* is an `<h2>` drawn only once a task was read, and
  `EmptyState` puts its title alone in a `<p>`, so both awaited texts match
  whole elements.
- *no description* appears in no other text the page draws for these
  fixtures; the debt region's sentence starts *No debt declared*.
