# T-073 — target resolution, the denylist and `accounts[].dind` (command-requests step 3)

Decisions: `docs/decisions.md` ADR 118 (the optional `dind` key, the pure
resolver and its never-targets, the compose working-dir label for the
project's services, the denylist's rules and where they run, `denylist_problems`
exported for step 4, `--permission-prompt-tool` deferred with the CLI version
found).

## What was built

- `dispatcher/config.py`: `AccountConfig.dind` (default `None`), validated in
  `_build_config` as absent or a non-empty string.
- `config.example.yaml`: `dind: dind-cuenta1` and `dind: dind-cuenta2`, with a
  comment. The host's `config.yaml` is untracked and needs the key by hand.
- `dispatcher/command_targets.py` (new): `writer_worktree`; `resolve`, pure,
  answering `(resolved, None)` or `(None, reason)`; `_never_target` and
  `HARNESS_SERVICES`; the `DENYLIST` of named `Rule`s (`remote-git`,
  `docker-socket`, `credential-path`, `privilege`, `shell-command`,
  `cwd-outside-worktree`) and `denylist_problems`; `check`, which moves a
  refused request to the refused list and adds `resolved` to the rest;
  `project_services`, the pure parser of `docker ps` label output; and
  `running_services`, the one docker reader, answering `None` on any failure.
- `dispatcher/dispatcher.py`: `_checked_command_requests` (ADR 117's check,
  then `command_targets.check` on the phase's account and writer worktree),
  computed once in `run_phase`, kept on `DispatchResult.command_requests`,
  recorded in the envelope, and read by `_filed_command_requests`.
- Tests: `tests/dispatcher/test_command_targets.py` — each kind resolved; the
  cwd joined and normalized; escapes by `..` after the join, a sibling
  sharing the prefix, and absolute paths; no dind; a service running, not
  running and the list unavailable; never another account's container, a
  harness container or a harness-named service; the label parser and the
  reader stubbed to succeed, fail and time out; each denylist rule refusing
  and naming itself, with near misses passing (`git status`, `git -C push
  status`, `git remote -v`, `docker compose up` in the dind, `cat
  README.env.md`, `id_rsa.pub`, `bash script.sh`, `python -c`); every broken
  rule named; `check` reading the services once and only for a service; and
  the filing path through `run_task_cycle` (a denylisted or unresolved
  request lands in refused and does not block, an accepted one carries
  `resolved` and blocks). `tests/dispatcher/test_config.py`: `dind` read,
  absent and invalid. `tests/dispatcher/test_command_requests.py`: the
  envelope's accepted entry carries `resolved`, and the mapping test's
  account has a dind.
- Docs: ADR 118; *Built* notes under decisions 3 and 7 and a dated note under
  decision 8 in `docs/plans/command-requests.md`.

## Why this way

- The resolver and the denylist are pure and take the running services as an
  argument, so the filing check and step 4 apply the same verdict and no test
  reaches docker.
- The project's services are found by the compose working-dir label under
  the project's dir, not the project-name label, which compose derives from a
  basename every worktree shares (`work`).
- The services are read lazily and at most once, so a cycle with no service
  request never calls docker.
- The verdict is computed once in `run_phase` and reused, so the envelope and
  the block decision cannot disagree.
- `sh -c` is refused outright: its command is one string no argv rule reads.

## Pending

- `_run_gates` still reads only the step-2 check: a request refused at this
  step still skips the gates.
- The rendered handoff's *Command requests* section shows the step-2 verdict,
  not this step's.
- The dind does not mount `/data/projects`; step 4 decides how a `dind` or
  `service` command reaches the worktree.
- `board` and `board-service` in `HARNESS_SERVICES` are a guess until the
  board service exists.
- Other interpreters' `-c` (`python -c`, `node -e`) pass the denylist.
- The host `config.yaml` needs `dind: dind-cuenta1` on cuenta1.
- `--permission-prompt-tool` against Claude Code 2.1.296 is unchecked.

## Ruled out

- Guessing the dind's name from the account's or the container's name.
- Accepting a service request when the service list cannot be read.
- Refusing docker for the `dind` and `service` kinds, which exist for it.
- Matching credential paths by substring.

## Review fix

The gates' skip in `_run_gates` still read only step 2's verdict, so a request
step 3 refused skipped the gates while the cycle went on to the revisor. Both
places now call `_command_request_lists`, which runs step 2 and step 3 on one
handoff; `_run_gates` takes the phase's account name to do it. Tested by
`test_the_gates_run_when_step_3_refuses_every_request`.
