# T-178-S1 — optional `plan` field on tasks and epics

Decision: `docs/decisions.md` ADR 450.

## What was done
- `dispatcher/context_transfer.py`: `TaskFile.plan`, read from and written to
  frontmatter only when not None.
- `dispatcher/tasks.py`: `_PLAN_PATH`, `is_plan_path`, `_plan_problems`;
  `propose` and `edit_task` take `plan`; `_proposed` and the missing-child
  rebuild in `_propose_again` carry it. An epic's plan goes on the epic and
  every child.
- `board_service/app.py`: `plan` in the `backlog_propose` (top level only) and
  `task_edit` input schemas. `dispatcher/board_mcp.py` needed no change (it
  lists tool names only).
- Tests: `tests/dispatcher/test_board_writes.py`, `tests/board_service/test_writes.py`.
- Docs: `docs/plans/board-service.md` tool table, `docs/plans/roadmap-view.md`
  item 2, `docs/README.md` row.

## Why this way
- The value is checked with `re.fullmatch` (a `$` anchor admits a trailing
  newline) and `..` is refused; only a file directly under `docs/plans/`.
- `task_edit` clears with `""` because the service drops a null argument
  before the writer sees it.
- No existence check: the project's checkout is not reachable from the board
  service.
- `plan` is not in `field_problems`, so existing files with other values still read.

## Ruled out
- A per-task `plan` inside an epic's task entries: the epic's plan goes on its tasks.
- Comparing `plan` on a repeated proposal: like `tags`, a repeat changes nothing.

## Known gap
`/api/roadmap` matches bare names, so `docs/plans/x.md` values land in
`no_plan` until the sibling api task strips the prefix.
