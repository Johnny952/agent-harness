# T-153-D1 — No backup before the automatic approve or `dispatch merge-task`

**Origin:** introduced, by T-153; declared by its arquitecto and implementador.
**Status:** resolved 2026-10-23 by T-157 — `backup` shares the caller's own
held project lock (`shared=`), and the automatic approve and
`dispatch merge-task` now take a copy before their merge
(`docs/decisions.md` ADR 345).
**Ruling:** accepted by T-153's revisor.
**Card:** none — nothing mirrors a row (`docs/decisions.md` ADR 59).
**Impact:** risk.

## What

Since T-153 the worker's `approve` handler passes `dispatcher.approve_reviewed`
a `before_merge` that takes one copy of the hive and `<state_dir>` before the
merge (`docs/decisions.md` ADR 342). The other two ways a task branch merges —
the automatic approve (ADR 77, `docs/plans/autonomy.md`) and
`dispatch merge-task` — take none.

## Where it bites

A task that changes the automatic approve merge or `dispatch merge-task`, or
that lets `dispatcher/backup.py` `backup` wait for, or share, a held project
lock.

## Why it stayed

Both merges run inside or beside a cycle that holds a project lock, and
`backup` takes every project lock without waiting (ADR 327, 5), so a copy
there would be refused every time (ADR 342, *Consequences*).

## Cost of leaving it

Those merges have only the nightly host-crontab copy behind them, which may be
up to a day old, or missing if that night's run was refused with exit 75.

## Fix

Give `backup` a lock-aware or waiting mode, then pass `backup.before_merge` at
those two merges as the worker's `_approve` does; ADR 342 *Consequences* names
the gap.
