# T-026-D1 — the unmigrated-hive refusal is enforced at each entry point, not inside the task-file writer

**Origin:** introduced, declared by T-026's implementador in round 1 and
restated in round 2 after the revisor's F4 asked for the *where* without a
`merge-task` example (`close_resolved_debt` only reads).
**Ruling:** accepted by the revisor in both rounds: every writer reachable
today is guarded, traced in round 1, and the structural fix belongs to the
second half of step 1 of `docs/plans/board-service.md`.
**Card:** none — this harness has no board configured, the first reason given
in [`README.md`](README.md)'s closing paragraphs.

## What

Since T-026 `dispatcher/context_transfer.py` neither reads nor writes the
`description` frontmatter key, and every one of its task-file writers is read,
mutate, `write_task_file`
([dropping-a-key-from-read-task-file-deletes-it-on-the-next-write](../learnings/dropping-a-key-from-read-task-file-deletes-it-on-the-next-write.md)).
So a write to a task file that still has the key deletes that task's
description, silently.

What stops it is a check made by the callers, not by the writer:
`tasks.unmigrated_ids` is called in `dispatcher/dispatcher.py`'s `open_cycle`
before `reap_expired_locks`, and by `dispatcher/cli.py`'s `_require_migrated`
at the top of `run-task`, `run-phase` and `release-account`. Any one
unmigrated file refuses the whole hive, because the reaper rewrites other
tasks' files.

## Where it bites

A future verb or library caller reaches a `context_transfer` writer
(`acquire_lock`, `refresh_heartbeat`, `handoff`, `set_kanban_issue_id`,
`set_resolved_debt`, `release_stale_lock`) without going through `open_cycle`,
`run-task`, `run-phase` or `release-account`.

Not today's other verbs: `merge-task`, `cleanup-task`, `status` and the api
write no task file, which the revisor traced. Not a hive that has been
migrated and has had no legacy file added since.

## Why it stays

The card says `context_transfer` no longer reads the key, so the stronger
form, raising inside `read_task_file`, would have had that module reading it
again. Moving the dispatcher's writes onto `dispatcher/tasks.py` was put out
of scope by the card as the next task, and that is where a writer that can
refuse exists.

## Cost of leaving it

A write through an unguarded path on an unmigrated hive deletes a task's
description and the operator loses the ask. Bounded by the window: once
`dispatch migrate` has run and nothing writes the key any more, there is
nothing left to delete.

## Fix

`docs/plans/board-service.md`, *How it would be built*, step 1, "The
dispatcher's own writes move onto the module": make the module's writer
refuse an unmigrated file, then drop the four enumerated checks.
