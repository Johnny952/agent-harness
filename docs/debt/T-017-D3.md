# T-017-D3 — the tail's no-match arm unmounts the scroller while `scrollTop` outlives it

**Origin:** introduced, declared by T-017's implementador in round 2, in
`front/src/routes/tail.tsx` — the arm that task added. Found by its revisor in
round 1 and called non-blocking there.
**Status:** resolved 2026-10-10 by the operator, out of cycle, by the first
of the two repairs the *Fix* below offers (see *How it was resolved*).
**Ruling:** accepted by the revisor in round 2, as transient
and self-healing, with the same stale `scrollTop` predating the arm, and with
the fix being scroll behaviour rather than the empty-state wording this task was
held to.
**Card:** none — this harness has no board configured, the first reason given in
[`README.md`](README.md)'s closing paragraphs.

## What

`front/src/routes/tail.tsx` virtualises its rows off component state:
`scrollTop` and `viewportH` are `useState` on `TailPage`, `start` is
`Math.floor(scrollTop / ROW_H) - 10` clamped at zero, and the inner div is
`transform: translateY(${start * ROW_H}px)`. `scrollTop` is only ever written by
the scroller's own `onScroll`.

The no-match arm added by this task sits in the same ternary as the scroller, so
rendering it **unmounts** the scrolling div. The state does not unmount with it.
Scroll down, pause, then narrow a filter until nothing matches: the arm renders,
and when the filter is cleared the div remounts with a DOM `scrollTop` of 0
while the state still holds the old offset. `start` therefore points into the
middle of the buffer and the rows are translated below the viewport until the
next scroll event corrects `scrollTop`.

Two things bound it. The `useEffect` on `[filtered.length, paused]` sets
`el.scrollTop = el.scrollHeight` whenever the screen is **not** paused, which
fires on the remount and repairs the state through `onScroll` — so only the
paused path is reachable. And the stale state is not new: before this arm, a
filter that matched nothing collapsed the inner div to height 0 with the same
`scrollTop` left standing. What the arm changed is that the div now goes away
entirely, which is the case the scroll-to-bottom effect cannot reach while
paused.

## Where it bites

A task changing `front/src/routes/tail.tsx`'s `scrollTop` or `viewportH` state,
its `start`/`end` window arithmetic, or the `useEffect` on
`[filtered.length, paused]`. Also any screen that is given a virtual scroller
behind a bare-state arm in the same ternary — the state that survives the
unmount is the trap, not the tail specifically.

Not a task editing `TailNoMatch`'s copy, and not one adding a no-match arm to a
screen whose rows are not virtualised: `learnings.tsx` and `debt.tsx` render
their rows in full and have no scroll state to go stale.

## Why it stays

It is transient and self-healing — one scroll event, or one unpaused poll,
repairs it — and the fix is scroll behaviour rather than empty-state wording,
which is the single surface T-017 was told to keep to. The same stale
`scrollTop` existed before the arm, so taking it here would be fixing a
pre-existing scroller bug inside a copy change.

The honest obstacle is the test. Both repairs below need a test that can observe
the rendered window, and the plain-`render`-the-exported-component idiom these
three test files use cannot: the window is `TailPage`'s state and reaching it
means mounting the route, which is `T-017-D1`.

## Cost of leaving it

Filter to nothing while paused, then clear the filter: the tail reads blank
until the operator scrolls. That is on the screen whose silent-blank defect this
very arm exists to end, so the cost is the appearance of the symptom the change
was about, in a narrower path.

Nobody has reported it and nobody has walked it: `docs/ROADMAP.md` **V0.6f** is
`NOT RUN`, and the only state the suite observes is which component renders.

## Fix

Either reset the window when there is nothing to show — `setScrollTop(0)` in an
effect on `filtered.length === 0` — or key the scroller on
`filtered.length === 0` so the state is rebuilt with it. The first is smaller
and says what it means; the second also covers any future state added to the
scroller, at the cost of discarding the position on every filter change rather
than only on the empty one.

Whichever is taken, the window has to be observable to be pinned, so this entry
is cheapest done alongside `T-017-D1`'s route-render helper — and resolving it
without a test is worth saying out loud rather than leaving implied.

## How it was resolved

The first repair, as written: an effect on `[filtered.length]` in
`front/src/routes/tail.tsx` that calls `setScrollTop(0)` when `filtered.length`
is `0`. Every arm that replaces the scroller — Empty, Error and No match — has
nothing filtered, so the reset runs exactly when the div goes away, and the next
div mounts with state and DOM both at the top. The position is kept on every
filter change that still matches something.

The keyed remount was not taken, and as written it would not have worked here:
`scrollTop` and `viewportH` are `TailPage`'s state, not the scroller's, so a
`key` on the div rebuilds the div — which the ternary already does — and leaves
the state standing. Keying only helps once the scroller is its own component
holding its own state, which is a larger change than this entry and the reason
its "also covers any future state" holds only after that extraction.

The test is in `front/src/routes/-tail.test.tsx`, on `T-017-D1`'s
`renderRoute`: 300 events served, the scroller's `scrollTop`, `clientHeight` and
`scrollHeight` stubbed on the instance with `Object.defineProperty` — jsdom has
no layout and reads all three as 0 — and a `scroll` fired at row 200, which
pauses the screen through its own `onScroll`. A payload filter that matches
nothing draws No match; clearing it remounts a new div at jsdom's `scrollTop`
0, and the test asserts the first event is on the page, the window's
`translateY` is `0px`, and the screen is still paused. With the effect removed
it fails at the first of those, unable to find the first event's row, and it
passes with it. The suite is 88 tests, all green.
