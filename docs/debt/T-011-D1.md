# T-011-D1 — nothing bounds the `body` served on `/api/tasks/<task_id>`

**Origin:** introduced by T-011, in `observability/api/app.py`, the
`/api/tasks/<task_id>` view.
**Status:** **resolved 2026-10-01 by T-012** — see *Resolved* at the end of this
file. **Ruling:** accepted by the revisor in round 1 — a cap needs a rule for
which end of a truncated record survives and how the caller is told, which is a
`warnings` contract change under `docs/decisions.md` ADR 5 and a decision this
task was never given.

## What

`/api/tasks/<task_id>` serves `context_transfer.TaskFile.body` whole, and
`dispatcher/handoff.py`'s `handoff()` only ever appends to it: every phase of
every round adds its summary and nothing removes anything. So the size of that
response is the whole history of the task id, and it grows for as long as the id
lives. Measured in this repository on 2026-10-01, `.hive/tasks/*.md` is 211 KB
over ten cards and the largest single card is 55 KB.

`/api/accounts`, `/api/events` and `/api/debt` all have a bound — ADR 11's
`MAX_EVENT_LIMIT` and `MAX_WARNINGS`, or the size of the pool. This field is the
one thing the service answers that has none.

## Where it bites

A card under `.hive/tasks/` past a few hundred KB, or a client that polls the
detail route rather than reading it once per screen view. Both are reachable:
the console's task-detail screen is tier 1 of `docs/plans/front.md`, and nothing
in the api tells a caller the field is unbounded.

Not the list route. `docs/decisions.md` ADR 21 keeps `body` off `/api/tasks`
precisely so the request a screen repeats every few seconds does not carry every
card's history, and
`tests/observability/test_api.py:test_one_task_by_id_carries_the_running_body_and_the_list_route_does_not`
fails if that is undone. So this entry is about one request per screen view, not
about a poll — unless a client makes it one.

## Why it stays

ADR 17 admits the body whole and ADR 21 only decided which route serves it. A
cap is a decision nobody has made, and it is not a line in a view: truncating a
running record needs a rule for which end survives — the latest phase is what a
reader wants, the earliest is what the file starts with — and a rule for how the
caller is told it got less than the whole, which under ADR 5 means a `warnings`
contract and under ADR 11 means a named constant with a test. T-011 was given
six fields to serve, not a size policy to invent.

## Cost of leaving it

One detail response carries a task's whole history, with no warning and no
parameter to ask for less, and it is the largest thing this service answers. A
secondary cost, named by the revisor and not worth fixing on its own:
`row["body"]` is assigned before the guard's `app.json.dumps(row)`, so the field
is serialised twice per request — sub-millisecond today, and the placement is the
module's rule rather than an oversight.

## Fix

Either half, as an ADR narrowing ADR 21:

- `MAX_BODY_BYTES`, truncating and naming the truncation in `warnings`, on the
  model `MAX_EVENT_LIMIT` already set under ADR 11 — which also fixes where the
  constant lives and what the warning reads like.
- A `?body=` parameter, so the caller asks. Note that
  `_reject_unknown_parameters` means adding one is a contract change on that
  route and not only a new branch.

It belongs with the console task that renders the task-detail screen, which is
the only thing that knows how much of the record that screen shows. Detail on the
placement and on why the field is on this route at all:
`docs/implementations/T-011.md` *Declared debt — nothing bounds the body on the
detail route*, and `docs/decisions.md` ADR 21.

## Resolved

By T-012, the console task that renders the detail screen, as the entry above
asked. `docs/decisions.md` ADR 23 is the decision; this is what it came to.

**The first half of the fix, not the second.** `MAX_BODY_BYTES = 128 * 1024` in
`observability/api/app.py`, applied by `_bounded_body` on the detail route and
nowhere else. The **newest** end of the record survives: `handoff()` appends, so
the last phase to run is at the end of the file and that is what a detail screen
is open for, while the operator's own ask travels separately and whole on
`description`. The truncation names the file, the real size and the cap in
`warnings`, on the model `MAX_EVENT_LIMIT` set under ADR 11.

The `?body=` parameter was not taken, and the reason is in ADR 23 rather than
here in one line: a parameter is an escape hatch and not a bound, so the cost
this entry measured — the largest thing the service answers, with no warning and
no cap — survives it, and it would have bought a `_reject_unknown_parameters`
contract change for nothing. It stays available **on top of** the cap for a later
task that wants the earliest end or a page through the record.

**The secondary cost is bounded, not moved.** `row["body"]` is still assigned
before the guard's `app.json.dumps(row)`, so the field is still serialised twice
per request; what is serialised twice is now at most `MAX_BODY_BYTES`. The
placement is ADR 21's rule — the guard wraps the use of a parsed value — and
moving the assignment to save the second pass would trade that rule for a
sub-millisecond saving on a request a screen makes once per view.

**What pins it**, in `tests/observability/test_api.py`: a body under the cap is
served whole and silent; a body over it keeps its newest end, drops the oldest
and names itself in `warnings`; a truncated body starts at a whole line; it
carries no U+FFFD when the byte slice lands inside a multibyte character; and
`/api/tasks` reports nothing at all, because the field is still the detail
route's alone.

**Not deleted, because a fix can be reverted.** Two things would reopen this
entry: raising or removing `MAX_BODY_BYTES` without a superseding ADR, and moving
the `body` assignment into `_task`, which the ADR 21 test catches first.
