# T-016-D1 — a filter matching nothing renders the empty-index empty state

**Origin:** found, declared by T-016's arquitecto and again by its implementador
as one entry, in `front/src/routes/learnings.tsx` — the screen that task wired,
which is what makes it eligible for a `found` row. `front/src/routes/debt.tsx`
has the same shape and predates this task.
**Status:** open. **Ruling:** accepted by the revisor in round 1 and re-affirmed
in rounds 2 and 3, on the grounds that the fix is a `docs/ui.md` entry binding
every filtered screen in the console, which is wider than a task told to edit
that file only if a vocabulary entry changes.
**Card:** none — this harness has no board configured, the first reason given in
[`README.md`](README.md)'s closing paragraphs.

## What

Both wired screens with a filter box test the *filtered* list for emptiness and
then render the empty state written for an empty collection:

```
front/src/routes/learnings.tsx   rows = (learnings.data?.data ?? []).filter(…q…)
                                 rows.length === 0 ?  <EmptyState
                                   title="No phase has written a learning entry"
front/src/routes/debt.tsx        rows = (debt.data?.data ?? []).filter(…q…)
                                 rows.length === 0 ?  <EmptyState
```

So an operator who types `obserability` into the Learnings filter is told that
no phase has ever written a learning entry, and one who mistypes a slug in the
Debt filter is told the project has filed no debt. Both statements are about the
harness; the true statement is about the three characters they just typed.

The screens are otherwise careful about exactly this distinction — the learnings
screen's own comment cites `docs/ui.md` *Absent, empty and broken are three
different things* on the line above the empty state, and the error state beside
it is at pains to say "unknown rather than empty". The filter is the one input
that can make the careful sentence false.

## Where it bites

A task adding or changing a filter on a wired console screen, or writing the
filter-empty wording entry in `docs/ui.md`. Both shipped instances are
`front/src/routes/learnings.tsx` and `front/src/routes/debt.tsx`, and the second
one is pre-existing.

Not a task that only reads either screen, and not one adding a filter to a
screen still backed by a fixture: a fixture is never empty, so the state is
unreachable there until the screen is wired.

## Why it stays

The fix is not the twenty lines on the screen T-016 wired. It is a vocabulary
decision in `docs/ui.md`, which says what each empty state means and is the file
every console screen is written against — and once that entry exists it binds
both shipped screens and every filtered screen after them. T-016's task text
permits editing `docs/ui.md` only "if a vocabulary entry changes", and this is a
new entry rather than a change to one; `docs/decisions.md` **ADR 42**'s closing
paragraph declares it on that reasoning rather than half-fixing the one screen,
which would leave the console with two answers to the same question.

Fixing `learnings.tsx` alone would also be the worse outcome of the two: the
pre-existing instance in `debt.tsx` would then be a divergence nobody had
decided, instead of a known row.

## Cost of leaving it

An operator reads a fact about their own filter as a fact about the harness.
`docs/ui.md` *Absent, empty and broken are three different things* forbids
exactly that of an empty state, so this is the console contradicting its own
vocabulary rather than a rough edge in it.

It is bounded: the operator typed the filter, the box is on screen with their
text still in it, and clearing it restores the table. Nothing is lost and no
decision is made on the strength of it. Nobody has reported it, and no phase has
seen either screen in a browser — `docs/ROADMAP.md` **V0.6e** is NOT RUN.

## Fix

One entry under `docs/ui.md` *Absent, empty and broken are three different
things*, distinguishing an empty collection from a filter that matched nothing,
and saying what the second one is allowed to claim — the shape the rest of that
section uses is a named state with the sentence it may and may not say. Then the
two shipped screens against it: split the `rows.length === 0` branch into the
unfiltered case (the collection is empty: the current wording stands) and the
filtered case (the query matched nothing: name the query, offer to clear it).

Do the `docs/ui.md` entry first. The screens are a transcription of it once it
exists, and writing them first is how the console ends up with two wordings.
