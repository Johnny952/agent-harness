# T-010-D1 — `debt.resolved()` still unwraps an entry id with one backtick per end

**Origin:** found by T-010, in `dispatcher/debt.py`, which it changed.
**Status:** open. **Ruling:** accepted by the revisor, round 1.

## What

`dispatcher/debt.py:resolved` reads the entry ids a handoff claims and unwraps
each with `str(item or "").strip().strip("`").strip()` — the same
one-backtick-per-end strip that `T-009-D3` has just replaced inside `_rows`.
`_rows` now goes through `dispatcher/debt.py:_unwrap_code`, which takes one
matched pair and nothing else; `resolved` was deliberately left on the old
rule, so the module now has two answers to "what does a backtick around this id
mean".

## Where it bites

A `resolved_debt` entry written with double backticks (`` ``T-009-D3`` ``) or
with a stray one at a single end, in a handoff payload or in a task file's
frontmatter — or a later task changing how ids are unwrapped anywhere in
`dispatcher/debt.py`, which now has to change two functions that disagree. It
does not bite a single-backticked or bare id, which is every id written so far.

## Why it stays

`T-009-D3`'s trigger was `/api/debt` rendering a cell to a human. `resolved`
feeds no screen: it is read by the dispatcher when it stamps a task file, and
its output is compared against ids that come out of the index through the *other*
unwrap. Moving both unwraps in one commit would have made the condition on the
`T-009-D3` fix — that no fingerprint moved — considerably harder to check, and
that condition was the whole point of the fix.

## Cost of leaving it

A paid fix filed as unresolved, because the id the handoff claimed does not
match the id the index holds. Narrow: it needs somebody to write an id with a
doubled or unbalanced backtick, and nothing has yet.

## Fix

Reuse `_unwrap_code` in `resolved` in place of `.strip("`")`, and add the
double-backtick case to `tests/dispatcher/test_debt.py` beside the cases
`T-009-D3` added. Re-run that file and confirm
`test_the_fingerprints_of_the_projects_own_index_did_not_move` still holds —
`resolved` does not feed `index_fingerprints`, so it should not move, and a
move means the two unwraps were coupled after all.
