# T-028-D3 — nothing writes `blocked` to a task file

**Resolved 2026-10-12 by T-030.** See *How it was resolved*; the sections
before it describe the tree as it was.

**Origin:** found, declared by T-028's arquitecto and by the implementador in
rounds 1 and 2.
**Ruling:** accepted by the revisor in both rounds: found and not introduced,
and the plan's sections 4 and 6 own the write, which changes lock behaviour.
**Card:** none — nothing mirrors a row (`docs/decisions.md` ADR 59).

## What

A cycle that stops blocked leaves a log line and an exit code and nothing
else. A task file's `status` is written by `tasks.acquire_lock`
(`in_progress`) and `tasks.handoff` (`done` or `pending`), and no code writes
`blocked`. Before T-028 the board card was the one place a blocked run was
recorded, on a harness that had a board; this one never did. T-028's card
assumed `_update_task_status` also wrote the task file. It did not, so
removing the seam removed that record and left none in its place.

## Where it bites

A task reading a task file's `status` to tell a blocked task from a pending
or `in_progress` one, such as the console's Blocked column, or one writing a
test that looks for `blocked` in a task file. Not a task that reads how a
cycle ended from `CycleOutcome` or the exit code.

## Why it stays

Writing `blocked` changes what a re-run and the lock reaper see, which the
removal did not ask for (`docs/implementations/T-028.md` *Ruled out*).

## Cost of leaving it

The board cannot show a blocked task from the task file alone; an operator
learns it from the log.

## Fix

`docs/plans/board-service.md` already decides it: section 4 (*Backlog and
board*) has a Blocked column that reads `blocked`, and section 6 (*The tools,
and who gets them*) leaves that status with the dispatcher, so the dispatcher
writes it to the frontmatter, beside the `phase` key of build step 6.
The writer exists since T-029, `tasks.mark_blocked` in `dispatcher/tasks.py`
(`docs/implementations/T-029.md`), and nothing calls it: this entry stays
open until the task that has the dispatcher call it on a blocked cycle.
Background:
[nothing-writes-blocked-to-a-task-file](../learnings/nothing-writes-blocked-to-a-task-file.md).

## How it was resolved

**Resolved 2026-10-12 by T-030** (`docs/implementations/T-030.md`, *Blocked:
which return points mark, and why*). `run_task_cycle` in
`dispatcher/dispatcher.py` calls `tasks.mark_blocked`, through
`_mark_blocked`, when it returns `CycleOutcome.BLOCKED` after a phase of the
run took the task's lock: a phase that failed, the arquitecto's block, the
rounds run out or the revisor's block, the auditor failing. A task file whose
cycle ended that way now reads `status: blocked` with no owner. It is not
written on a held cycle, on another owner's lock, when `open_cycle` refused
the task, when the project's branch diverged, when there is no task file, or
by `run-phase`: those leave the file as it was, so `blocked` in a task file
means a cycle ran and stopped, not every `EXIT_BLOCKED`.
