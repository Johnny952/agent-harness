# T-065-D1 — The whole-repo-writes-alone queue test is timing-flaky

**Origin:** found, declared by T-065's implementador in round 1.
**Status:** resolved 2026-10-19 by hand, out of cycle (see *How it was
resolved*).
**Ruling:** accepted by the revisor in round 1: `dispatcher/` and its tests are
outside the task's surface, and the failure passes on a rerun.
**Card:** none — nothing mirrors a row (`docs/decisions.md` ADR 59).

## What

`tests/dispatcher/test_parallel_queue.py` `test_a_whole_repo_task_writes_alone`
runs two fake cycles through `ScheduledCycle(cfg, hold=0.1)` and asserts their
windows do not overlap. It depends on wall-clock scheduling, and under the load
of the full suite it fails now and then:

```
>       assert windows["T-1"][1] < windows["T-2"][0]
E       assert 5 < 2
```

T-061's and T-062's auditors saw it, and T-065's implementador saw it fail
once and pass on the rerun (14 passed), on diffs with no `dispatcher/` change.

## Where it bites

A task whose `python3 -m pytest` gate fails on that test with `assert 5 < 2`
while its diff has no `dispatcher/` change, or a task editing that test file or
the scheduler it drives.

## Why it stayed

`dispatcher/` and its tests were outside T-065's surface, and the flake was
not diagnosed past "timing".

## Cost of leaving it

A spurious gate failure can cost a task a revision round, and every phase that
hits it spends turns re-running the suite.

## Fix

Make the test wait on events the fake cycles set (an event or barrier per
cycle) instead of `hold` timing, so the order it asserts is caused, not
likely. Until then, the rule in
`docs/learnings/the-whole-repo-writes-alone-test-flakes-under-load.md`.

## How it was resolved

The race was in the test, not in the scheduler. `_Scheduler.enter_write_window`
puts a task in line only once it asks: `_first_in_line` lets the queue order
decide between tasks *already waiting*, and a task that asks while nothing
overlapping is waiting or held takes its window at once. Both fake cycles run
their arquitecto concurrently, so whichever thread reached
`enter_write_window` first wrote first. When that was T-2, the log was
`T-1 arquitecto, T-2 arquitecto, T-2 enter, T-2 leave, T-1 enter, T-1 leave`:
T-1's window is (4, 5) and T-2's starts at 2, which is exactly `assert 5 < 2`.
The windows did not overlap — the whole-repo task did write alone — but the
assertion also demanded that T-1 write first, which nothing caused. That is
why "re-run the file" did not always clear it: no other test has to be running
for T-2's thread to win.

`ScheduledCycle` gained two hooks, `before_window` and `in_window`. The test is
parametrized over which task writes first: the second one asks for its window
only after a `threading.Event` says the first holds its own, and the first
leaves only once the second is seen in `_Scheduler._waiting` (polled every
5 ms against a 10 s deadline that fails the test with a message rather than
hanging). So the second task provably asked while the first was writing, in
both directions — the whole-repo task waiting on a narrow one and a narrow one
waiting on the whole-repo task. It asserts the same non-overlap as before plus
the scheduler's own `windows` record, `[first enter, first leave, second enter,
second leave]`. No `hold` sleep is left in it.

Checked by mutation: an `enter_write_window` that grants every window at once
fails both cases. 40 runs alone and 40 runs with every core busy all passed.

A second, unrelated flake turned up in the same file under that load:
`test_the_limit_is_read_live_across_cycles` failed 3 of 30 runs of the file
with every core busy (a third entry `blocked` or `limit_reached` where
`pending` was expected). It was left alone then and resolved the same day by
hand, out of cycle (next section).

## The limit-read-live flake

**Status:** resolved 2026-10-19 by hand, out of cycle.

The race was in the test, not in `dispatcher/queue.py`. Each fake cycle spends
100 before its window and 100 inside it, so the two spend 400, the limit. The
queue reads the limit live: when a slot frees, `_run_parallel`'s `spent_now()`
adds what the finished task spent to what the running one has written so far,
and starts the next task if that is under the limit. Nothing made the second
cycle finish its spending before the first one ended. When the first ended
while the second had written only its first 100, `spent_now()` read 300 and
T-3 started: either its `may_start_phase` then saw the 400 and it was held
(`limit_reached`), or it ran and its `arquitecto_barrier` of two, with no
partner left, broke after 5 s (`blocked`). Both are correct behaviour for a
live limit at 300; the assertion assumed 400 was already on the logs.

`ScheduledCycle` gained an `after_spend(task_id)` hook, run once the cycle has
written its last usage line and before it ends. The test passes a
`threading.Barrier(2)` there (10 s timeout, so a stall fails the test instead
of hanging): neither cycle ends until both have spent, so the first slot to
free is offered with 400 on the logs. The assertion is unchanged: queue
`limit_reached`, entries `merged, merged, pending`.

Reproduced at 2 of 30 runs with every core busy before the fix. Checked by
mutation: a `spent_now()` that counts a running task as 0 instead of reading
its log fails the test every run. 30 runs with every core busy all passed, and
the full suite passed (3333 passed, 10 skipped).
