# T-133-S2-D1 — *Resolve conflict* is not drawn when the conflict task's diff fails to load

**Origin:** introduced, by T-133-S2; flagged as a risk by its implementador, revisor and auditor, filed by the operator at merge.
**Status:** resolved 2026-10-22 by T-135 (*Resolve conflict* drawn alone on the Conflict lane when the diff does not load).
**Ruling:** accepted by the operator at merge.
**Card:** none — nothing mirrors a row (`docs/decisions.md` ADR 59).
**Impact:** risk.

## What

`front/src/routes/approvals.tsx` draws the *Resolve conflict* button inside
the verdict form, and the form is drawn only once the task's diff has loaded,
because approve needs the diff's tip. The resolve-conflict forward needs no
tip: its body is `{project}` alone (ADR 288). ADR 288's Consequences name the
gap.

## Where it bites

A task on the Conflict lane whose diff does not load, for example because the
branch is gone, the diff is too large, or the API fails. The console then has
no way to start a resolution, and the operator has to run
`resolve-conflict` from the CLI.

## Why it stayed

ADR 288 placed the button beside approve so the review screen keeps one form.
Moving it out of the form is a layout change that the task did not plan.

## Cost of leaving it

The case is rare, and a CLI fallback exists. The console just loses the one
action that needs no diff, in exactly the situation where the diff is
missing.

## Fix

Draw *Resolve conflict* on the Conflict lane outside the diff-gated verdict
form, or keep it drawn when the diff fails to load, since its body needs no
tip. Add a test in `front/src/routes/-approvals.review.test.tsx` where the
diff query fails and the button is still drawn.
