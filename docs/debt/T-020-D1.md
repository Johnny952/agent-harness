# T-020-D1 — nothing serves the paced weekly ceiling, so `/api/accounts` still offers `reserve_pct` as the primary's

**Origin:** introduced, declared by T-020's implementador in round 1 and again
in round 2, as one entry, in the surfaces its own change narrowed:
`observability/api/app.py`'s account row and `front/src/routes/pool.tsx`, two
files T-020's card named out of scope.
**Status:** resolved 2026-10-10 by the operator, out of cycle, in the two
halves the *Fix* below asks (see *How it was resolved*).
**Ruling:** accepted by the revisor in round 1 and re-affirmed in round 2,
which held that the trigger is a condition a later task can check against its
own work, and that `docs/decisions.md` **ADR 48** *Consequences* plus
`docs/implementations/T-020.md` *What is left* already record it where the next
reader of either surface lands.
**Card:** none — this harness has no board configured, the first reason given
in [`README.md`](README.md)'s closing paragraphs.
**Progress:** the server half landed under `docs/decisions.md` **ADR 49**:
`_quota_decision` persists every probe in the account's state file, and every
`/api/accounts` row serves it as `last_probe`, with the probe's own percentages
and both ceilings it was held to — for a paced primary, the week's paced value
with the reset and days-left it was computed from. The pool screen half
followed the same day, which closed the entry.

## What

`/api/accounts` serves `reserve_pct` on every row and the console's pool screen
labels it the primary's ceiling. Both were right when they were built:
`docs/decisions.md` **ADR 18** picked the three thresholds as the numbers a
console must show, and **ADR 20** reasoned the per-account shape from
`dispatcher/dispatcher.py:_threshold_for` being the one place a ceiling is
decided — so a consumer with both numbers and `is_primary` could work out which
one applied.

Since **ADR 48** the primary answers to two ceilings. `reserve_pct` is its
*session* ceiling, and its week's *fallback* for a probe whose reset will not
parse. The number its week actually parks on is `quota.week_ceiling`'s, paced
against the reset `/usage` reported, recomputed at every probe — and served
nowhere.

The pool screen is where that reads as a claim rather than a column.
`front/src/routes/pool.tsx` prints `primary · reserve {a.reserve_pct}%` on the
primary's row, picks a threshold sentence by `is_primary`, and carries a
comment citing `_threshold_for` as the reason it may.

## Where it bites

A task that changes `/api/accounts` — adding a field to the account row,
re-deciding what the route serves — and reads `reserve_pct` beside `is_primary`
as the pair that says what the primary parks on. Any `front/` screen that reads
`reserve_pct` for the same purpose, which today is `front/src/routes/pool.tsx`
in the three places above.

Not a task that only reads the ceiling from inside the dispatcher:
`dispatcher/operator.py:format_status` prints both of a paced primary's
ceilings, so the surface an operator reads without a browser is correct.

## Why it stays

`observability/` and `front/` are named out of scope by T-020's card, and the
honest fix is not a relabel. The paced ceiling is a property of **one probe**,
and ADR 18 leaves the probe's own numbers — `usage_pct`, the week's percentage
— unserved until something persists a probe: the api reads configuration and
the dispatcher's own state files, and a `/usage` result is in neither. So there
is no server-side home for the paced value to be served *from* yet, and a
screen cannot be made correct by editing the screen.

## Cost of leaving it

The console's pool screen labels the primary's week with a number that no
longer governs it, and in the direction that misleads most: an operator reading
`reserve 60%` on a Monday will not expect the harness to refuse fallback work
at 5% of the week, which is what the ramp does just after a reset
(ADR 48 *Consequences*).

Bounded three ways. `reserve_pct` is still exactly right for the primary's
session and is still what its week falls back to, so the number is not junk;
`status` in the CLI prints both ceilings and the days to the reset; and the park
log names the ceiling, the days left and the reset it read, so the reason an
account parked is recoverable from the log without the browser.

## Fix

One task that persists a probe and serves both halves — the probe's own
`week_pct` and the paced ceiling with the reset and days-left it was computed
from — then relabels the pool screen's primary row so the week's number and the
session's are two fields rather than one. ADR 18's unserved `usage_pct` is the
same missing record, so the two are cheapest taken together.

Until then, `reserve_pct` stays on the row: removing it would break the
session's ceiling and the fallback as well, and ADR 20's shape is not what
T-020 narrowed. The nearest proposal is `docs/plans/token-economy.md` **P5**,
which sends `ClaudeResult.raw`'s usage to the collector — a per-phase series
rather than the probe's own snapshot, so a task taking this row has to decide
whether the probe is persisted as well, and that decision is the ADR it owes.

## How it was resolved

In two halves, both by the operator on 2026-10-10 and out of cycle. The server
half is **ADR 49**, recorded under *Progress* above.

The screen half touched `front/src/` only. `front/src/routes/pool.tsx` now
reads `last_probe` before any configured number. It prints the probe's age
first, from `probed_at`, and marks it stale past `PROBE_STALE_S`, which is 30
minutes. Then it gives the session and the week as two rows, each with its own
ceiling. A paced week also shows the days to the reset. When `fallback_reason`
is set, the screen says the week fell back to the reserve and why. A worker
shows the same two rows against its threshold. With no probe recorded, the card
shows the configured numbers worded as configuration, and the primary's
`reserve_pct` is labelled as its session ceiling, never its week's. The parked
sentence names the window that crossed, using the probe's `>=`. The comment
that cited `_threshold_for` now cites `_quota_decision` and ADR 48/49.

`last_probe` is now non-optional in `front/src/lib/api/types.ts`, because ADR 49
serves it on every row. The mock fixtures carry a paced primary, a fallback
primary, a worker, a stale probe and an account with no probe.
`front/src/routes/-pool.test.tsx` covers each of those cases.
`reserve_pct` stays on the row, as the *Fix* asked.
