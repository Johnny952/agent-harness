# T-024-D1 — nothing reads the usage log, so P5's series accumulates with no aggregation, no route and no screen

**Origin:** introduced, declared by T-024's implementador in round 1 and again
in round 2, in the surface its own change created: the per-call usage log
`docs/decisions.md` **ADR 53** writes under
`<hive_tasks_dir>/<task_id>/usage/calls.jsonl`.
**Status:** resolved 2026-10-10 by the operator, out of cycle, under
`docs/decisions.md` **ADR 54** — the reader and the route, with the screen
filed apart as [`T-024-D3`](T-024-D3.md) (see *How it was resolved*).
**Ruling:** accepted by the revisor in both rounds. Round 1 held that T-024's
card put `front/` out of scope and asked only that choice (b) explain why the
api need not serve the record yet, which ADR 53 *Consequences* does; it
required the *Fix* below to stop naming `docs/plans/front.md`'s Tokens card,
which is a different object (see *Where it bites*). Round 2 re-checked that
correction and accepted the row as it now stands.
**Card:** none — this harness has no board configured, the first reason given
in [`README.md`](README.md)'s closing paragraphs.

## What

T-024 built the write half of `docs/plans/token-economy.md` **P5** and
deliberately none of the read half. One JSON object per line per `claude` call
the dispatcher made is appended to the task's own log, and nothing anywhere
opens it: no aggregation function, no route on `observability/api/`, no console
screen, and no median.

`/api/phases` is untouched and correct as it stands — that route lists
`handoffs/`, and the log is a sibling directory, so the new file reaches no
existing reader and breaks none. The point is the other direction: it reaches
no reader at all.

## Where it bites

A task asked for a measured phase cost, a spend view, a token median or a
budget expressed in what a phase actually consumed — including **P4** in
`docs/plans/token-economy.md`, which wants "the median ia-harness implementador
costs X% of a window" and whose own closing paragraph in that section now says
this log does not give it that.

Also any task that decides to serve the log, because it inherits two open
questions rather than one: which row shape, and which screen.

Not a task that only wants to know whether a phase's numbers were captured —
ADR 53 and `docs/implementations/T-024.md` both describe the line's seventeen
keys, and the file itself is readable with one `jq` over the task's scratch
directory.

## Why it stays

ADR 53 decides the *write* and declines, on purpose, to decide a reader's row
shape. The honest unit is not obvious and the choice is not free: a line is one
`claude` call, a phase is up to four of them on as many accounts as a failover
tries ([a-phase-is-not-one-claude-call](../learnings/a-phase-is-not-one-claude-call.md)),
and a task is several phases over several rounds. A route keyed on the wrong
one of those three is worse than no route, because it would be a number
somebody trusts.

Picking a shape now would also invent a screen's contract. No console screen
and no card anywhere in `docs/` owns a view of what a phase cost: the console's
Tokens screen and `docs/plans/front.md`'s Tokens task are a container's
*provider login*, a different object with the same word
([the-tokens-screen-is-logins-not-spend](../learnings/the-tokens-screen-is-logins-not-spend.md)).
So there is no consumer whose needs would settle the row, and T-024's card put
`front/` out of scope in either case.

## Cost of leaving it

The series accumulates unread. P5's whole purpose is to replace the operator's
one-off transcript read of T-016 with a measurement, and until something
aggregates these lines the project still has exactly one data point about what
a phase costs — so P4's surface proxy and P8's 5-point margin both stand on a
2026-10-09 transcript rather than on the log now being written beside every
task.

The first reader therefore pays twice: it has to design the row *and* discover
the log, which nothing but ADR 53 and this row points at.

Bounded two ways. The log is per task under `.hive/`, which
`dispatcher/cli.py`'s `cleanup-task` removes worktrees from and never the
scratch directory, so nothing written is being thrown away while this row is
open. And every line carries `raw_keys`, so the first real dispatched phase
answers on its own which keys the CLI actually printed — a question the write
half could not answer and the reader would otherwise inherit as a third
unknown.

## Fix

One task that picks a row shape over a **series** — per call, per phase or per
task, and says which and why, because the three disagree — serves it, and
proposes the screen that consumes it. No card owns a cost view yet, so that
task is writing the screen's first contract as well as the route's, which is
the work this entry defers rather than a detail of it.

It inherits one open question from ADR 53 and should resolve it first:
[`T-024-D2`](T-024-D2.md), whether a `--resume` result's `usage` is per call or
cumulative over the session. An aggregator that sums a phase's lines is wrong
if the answer is cumulative, so the sum cannot be written before that is known.

## How it was resolved

By the reader and the route, under `docs/decisions.md` **ADR 54**, and not by
the screen. The change is `docs/implementations/T-024-D1.md`.

`dispatcher/context_transfer.py:read_usage` is ADR 53's reader half as that
entry states it: a line that will not parse is skipped and counted, the last
line is trusted only when it ends in a newline, a log that does not exist reads
as empty, and every other `OSError` reaches the caller.
`GET /api/tasks/<task_id>/usage` serves the lines verbatim, one group per
attempt — a new group at every `call: "phase"` line or wherever
`(role, round, account)` changes — and adds only what holds under either answer
to [`T-024-D2`](T-024-D2.md): the call count, the kinds, the measured and
unmeasured counts, and the attempt's own `phase` line as `phase_call`.

The row shape this entry asked for is **per attempt**, and the reason is the
one *Why it stays* gives: per phase and per task are both sums, and a sum is
wrong if a resumed call's `usage` is cumulative. So D2 was not resolved first,
as *Fix* advised — it needs a live phase this resolution was not allowed to
run — and instead nothing is summed. ADR 54 says what changes once D2 is
answered: a per-attempt total, as a new key under a new ADR.

What *Fix* also asked, the screen that consumes the route, was not built. No
card owns a cost view and `front/` was out of this resolution's scope, so it is
[`T-024-D3`](T-024-D3.md) rather than a clause here. P4 still has no median:
the route serves one task's lines, and a budget is a reading across many.
