# T-008-D1 — No lock around `set_status`'s read-modify-write

**Origin:** introduced by T-008. **Status:** open. **Ruling:** accepted by the
revisor, rounds 1 and 2.

## What

`LocalBoardClient.set_status` reads the card, merges the new status and writes
the document back. The write itself is atomic, but the read-modify-write is not,
and there is no lock and no racing-writers test.

## Where it bites

Phase 4's action queue, or anything running two `dispatch` processes against one
`local_board.dir` and expecting both status moves to stick. One writer at a time
— today's dispatcher — never sees it.

## Why it stays

There is exactly one writer today, and because the file write is atomic a race
can lose a status but can never corrupt a card or produce a half-written
document. A lock file would be a mechanism with no user yet, and the test that
would prove it belongs with the concurrency Phase 4 introduces.

## Cost of leaving it

With concurrent writers, one card's status move is silently overwritten by the
other's. Nothing logs it: both writes succeed.

## Fix

`docs/plans/board.md` "Actions go through a queue, not a socket" already decides
the shape — make the Phase 1 API the only writer. The narrower alternative is an
`O_EXCL` lock file per card around the read-modify-write. Either way it needs the
racing-writers test this task did not write.

Reasoning behind the ruling: `docs/decisions.md` ADR 1 "Consequences".
