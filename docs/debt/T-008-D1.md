# T-008-D1 — No lock around `set_status`'s read-modify-write

**Origin:** introduced by T-008. **Status:** resolved 2026-09-28, out of cycle
— the narrow half, taken by hand because it is small and because a second
writer arrived before Phase 4 did (see *Fix*). **Ruling:** accepted by the
revisor, rounds 1 and 2.

## What

`LocalBoardClient.set_status` reads the card, merges the new status and writes
the document back. The write itself is atomic, but the read-modify-write is not,
and there is no lock and no racing-writers test.

## Where it bites

Phase 4's action queue, or anything running two `dispatch` processes against one
`local_board.dir` and expecting both status moves to stick. One writer at a time
— today's dispatcher — never sees it.

## Why it stays

There is exactly one writer today, and because the file write is atomic a race
can lose a status but can never corrupt a card or produce a half-written
document. A lock file would be a mechanism with no user yet, and the test that
would prove it belongs with the concurrency Phase 4 introduces.

## Cost of leaving it

With concurrent writers, one card's status move is silently overwritten by the
other's. Nothing logs it: both writes succeed.

## Fix

`docs/plans/board.md` "Actions go through a queue, not a socket" already decides
the shape — make the Phase 1 API the only writer. The narrower alternative is an
`O_EXCL` lock file per card around the read-modify-write. Either way it needs the
racing-writers test this task did not write.

Reasoning behind the ruling: `docs/decisions.md` ADR 1 "Consequences".

Done 2026-09-28, the narrow alternative and its test, not the architectural
one: `_card_lock` in `dispatcher/vibe_kanban_client.py` wraps `set_status`'s
read, merge and write in one critical section, and
`test_two_writers_on_one_card_do_not_read_the_same_document` proves the second
writer blocks and then reads the first writer's new status. Two departures
from what is written above, both deliberate:

  - **`flock`, not the `O_EXCL` create named in *Fix*.** Both serialise
    writers, but an `O_EXCL` lock outlives the process that took it, so a
    dispatcher killed mid-phase — the accident `run-phase` exists to
    repair — would leave a card nothing could move again. A worse board
    than the one this entry was written about. The kernel drops a flock when
    its holder dies, which keeps the worst case a writer that waited. The lock
    file is never unlinked, because unlinking is what makes flock racy.

  - **"There is exactly one writer today" stopped being true.** `run-phase`
    (T-010's repair path) is a second process reaching `_update_task_status`,
    and nothing stops it running beside a `run-task` cycle that is merely
    stuck rather than dead. The mechanism has a user; it did not have to wait
    for Phase 4.

What this does not do: make a lost update visible. `set_status` merges one
field, so even unlocked the interleaving A-read, B-read, A-write, B-write ends
at B's status — the losing write is the *card* A had read, not the status.
What the lock buys is the serialisation Phase 4's second mutator will need,
and the test that was owed. The architectural fix in *Fix* — the Phase 1 API
as the only writer — is untouched and still the right end state.
