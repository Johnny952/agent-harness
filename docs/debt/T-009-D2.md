# T-009-D2 — Nothing caps `/api/events?limit=`, or the length of `warnings`

**Origin:** introduced by T-009. **Status:** resolved 2026-09-28, out of cycle
— both halves, taken by hand because they are small and because the number
turned out not to need Phase 3 (see *Fix*). **Ruling:** accepted by the
revisor, rounds 1, 2 and 3.

## What

`observability/api/app.py` validates that `limit` and `since` are integers
SQLite can bind — `_int_parameter`, bounded by `_SQLITE_INT_MAX` — and then
passes `limit` through to `db.list_events` unchanged. There is no maximum, and
no cap on how many strings `warnings` may hold: one warning per unreadable task
file, per unreadable board card, unbounded by anything but the directory.

## Where it bites

A caller — or Phase 3's tail — sending a large-but-bindable `limit` (`2**62`
passes) at a long-lived events database, or a `local_board.dir` holding many
documents that will not parse. Phase 3 is where the number finally comes from,
because a tail window is the first thing that needs one.

## Why it stays

A cap is policy, and the only place to configure it would be a new
`config.yaml` key, which this task was explicitly forbidden. The range check
added in round 3 (F6) rejects an integer SQLite *cannot* bind; the revisor ruled
in rounds 2 and 3 that it does not resolve this entry. The endpoint is bound to
loopback and sits behind Basic auth, so the exposure is an operator's own
request, not an anonymous one.

## Cost of leaving it

One request can build an unbounded response in the `api` container's memory: the
rows are materialised into a list and then serialised whole by `jsonify`. A
board directory full of foreign documents does the same through `warnings` on
every `/api/tasks`.

## Fix

A module constant clamping `limit`, with the clamp itself reported in
`warnings` so a caller is told it got fewer rows than it asked for — the
envelope's own rule, `docs/decisions.md` ADR 5. Decide the number together with
Phase 3's tail window in `docs/plans/board.md`, "Phase 3", rather than picking
one here. A cap on `warnings` needs the same treatment and the same decision.

Done 2026-09-28, both halves and their tests, and the number decided without
waiting for Phase 3: `MAX_EVENT_LIMIT = 1000` clamps `limit` and appends a
warning naming what was asked for, what was answered and `?since=` as the way to
walk the rest; `MAX_WARNINGS = 100` caps the list in `_envelope`, the last slot
spent tallying what was left out. `docs/decisions.md` ADR 11 records the
reasoning. Two departures from what is written above, both deliberate:

  - **The number did not come from Phase 3's tail window.** *Where it bites*
    says "Phase 3 is where the number finally comes from, because a tail window
    is the first thing that needs one", and that turned out to be wrong: Phase
    3's tail is bounded by `since` (`id > last`), so its `limit` is a burst
    ceiling and not a page size, and the two numbers are unrelated. 1000 comes
    instead from the only client that exists — five times the board's
    `EVENTS_LIMIT = 200` — which means nothing in this harness is clamped today.
    Waiting for Phase 3 would have been waiting for an answer it does not hold.

  - **It is a clamp, not a rejection, and the range check stays in front of
    it.** *Why it stays* is right that the round-3 check does not resolve this
    entry, and the fix leaves that check exactly where it was: an integer
    SQLite cannot bind is still a 400, because it is malformed, and `since` is
    still bound straight into `WHERE id > ?` with nothing else guarding it. What
    is new sits after it and answers 200. The order is load-bearing — the
    shipped boundary test is parametrised over both parameters, and clamping
    first would have made `limit=2**63` a 200 for a genuinely unbindable value.

What this does not do: bound the response in bytes. A thousand rows whose
payloads are large is still a large answer, because the cap counts rows and
`warnings` counts strings, not either one's size. It also leaves the cap a
module constant rather than a `config.yaml` key, as *Why it stays* describes —
an operator who wants a different ceiling still edits source. Both are the right
trade at this size, and both are the place to look first if `api` ever runs out
of memory again.
