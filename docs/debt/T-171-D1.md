# T-171-D1 — The board service and the config writer still serve from Werkzeug's development server

**Origin:** found, by T-171; declared by its arquitecto and implementador.
**Ruling:** accepted by T-171's revisor.
**Card:** none — nothing mirrors a row (`docs/decisions.md` ADR 59).
**Impact:** risk.

## What

T-171 moved the collector and the read API onto waitress (`docs/decisions.md`
ADR 417). `board_service/app.py` (`app.run(host="0.0.0.0", port=PORT)` in
`serve`, which `__main__` calls) and `config_writer/app.py` (`main().run(host="0.0.0.0",
port=PORT)`) still run Flask's development server.

## Where it bites

A task that hardens `board_service` or `config_writer` for 24/7 use, or touches
the entry point of `board_service/app.py` (`serve`) or `config_writer/app.py`
(its `__main__`).

## Why it stayed

T-171's *Out of scope* kept both services on their current servers and asked
for this to be filed as debt.

## Cost of leaving it

Two always-up services run a server Flask says is not for production: no
production-grade request handling and no bound on the request queue.

## Fix

Apply ADR 417's pattern: a `run()` that builds the app, imports waitress
lazily and serves with a named `THREADS`; `__main__` calls `run()`, and tests
use a `sys.modules` stand-in for waitress
([the agent venv learning](../learnings/the-agent-venv-has-only-the-packages-its-dockerfile-names.md)).
The board service already has that entry point, `serve`, which starts the push
notifier's thread before serving; the fix swaps its `app.run` and keeps the
thread start.
