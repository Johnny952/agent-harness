# T-188-D1 — `tasks.unmet_dependencies` never counts an epic parent as met

**Origin:** found, by T-188; declared by its arquitecto and implementador.
**Ruling:** accepted by T-188's revisor.
**Card:** none — nothing mirrors a row (`docs/decisions.md` ADR 59).
**Impact:** risk.

## What

`dispatcher/tasks.py` `unmet_dependencies` counts a dependency met only when
its file has a `merged` block, and no path writes one on an epic parent
(`close_epic` sets `done` or `dropped`). T-188 re-points a queued dependent's
`depends_on` to the sub-task ids (`docs/decisions.md` ADR 495), so inside a
queue the wait clears; outside one it never does.

## Where it bites

Any task whose `depends_on` names a task with `status: epic`, started by
`run-task`, the worker or the Ready order rather than through a queue.

## Why it stayed

The gate is outside T-188's surface (`dispatcher/queue.py`); ADR 495
*Ruled out* names the change.

## Cost of leaving it

Such a task waits forever and `open_cycle` refuses it ("<id> is not merged");
the owner re-points its `depends_on` by hand.

## Fix

`unmet_dependencies` counts an epic parent met when every id in its
`split_into` is merged (`docs/decisions.md` ADR 495, *Ruled out*). Learning:
`docs/learnings/a-dependency-on-a-split-task-never-clears.md`.
