# T-009-D3 — `debt._rows` strips one backtick per cell end, not a matched pair

**Origin:** found by T-009, in `dispatcher/debt.py`, which it changed.
**Status:** **resolved 2026-09-27 by T-010**, the task that built Phase 2 and so
the first one to render these cells to a human. Confirmed against the running
stack 2026-09-26 before the fix — reproduced through `/api/debt`, not only read
off the code (see *What*). **Ruling:** accepted by the revisor, rounds 1, 2 and 3.

## How it was resolved

`dispatcher/debt.py:_unwrap_code` replaced the `cell.strip("`")` inside `_rows`:
it takes exactly one backtick off each end and only when both ends have one, so
a cell that merely opens or closes with inline code survives intact. Nothing
else in the module moved.

No fingerprint moved, which was the condition on the fix and is now a test
rather than a claim:
`tests/dispatcher/test_debt.py:test_the_fingerprints_of_the_projects_own_index_did_not_move`
parses `docs/debt/README.md` twice — once under the new rule and once with the
old strip monkeypatched back in — and asserts the fingerprint sets and the ids
are identical. It holds for a reason worth writing down: `fingerprint` replaces
punctuation with spaces and then strips, so a backtick at either end of a
**what** cell never reached the comparison in the first place. The visible
defect was always in the rendered cell, never in the dedupe.

One thing was deliberately left: `debt.resolved()` unwraps the entry ids a
handoff claims with the same one-backtick-per-end strip. It feeds no screen, and
moving two unwraps in one commit would have made the fingerprint check above
harder to read. It is declared as T-010's own debt.

## What

`dispatcher/debt.py:_rows` (through `_column`) strips a single backtick from
each end of a table cell so that an id written `` `T-008-D1` `` reads as
`T-008-D1`. It is not a matched-pair unwrap: a cell that merely *ends* in inline
code — "…in `_scan`" — loses its closing backtick and keeps the opening one, and
a cell wrapped in double backticks keeps one at each end.

Confirmed live on 2026-09-26 against `compose-api-1`, by the entry above it in
this same index: `GET /api/debt?project=ia-harness` returns the `T-009-D4` row
with its `where` cell ending `` …handing any later service
`observability_data:/…:ro `` — opening backtick kept, closing one eaten. Evidence:
`.data/verify/t009-api-verification.txt`. Nothing about the fix changes; what the
check settles is that the defect reaches a caller over HTTP, which is the Phase 2
exposure this entry predicts.

## Where it bites

Phase 2 rendering `/api/debt` from `index_rows`, or any task changing the cell
stripping in `_rows`. It does not bite a row whose cells are plain prose, which
is most of them.

## Why it stays

The same stripping is what unwraps the ids that feed `index_fingerprints`, and
fingerprints are how the dispatcher decides a declaration is already filed.
Changing the unwrap changes those strings, so a fix re-files debt that is already
on the board — which is a larger change than the defect, and not one Phase 1
was asked to make. Pre-existing: `index_rows` only exposed it, by giving a
caller the cells rather than the ids.

## Cost of leaving it

An unbalanced backtick in the Phase 2 UI, and a dedupe comparing a slightly
different string from the one the index holds.

## Fix

Strip a matched pair only, then re-run `tests/dispatcher/test_debt.py` to
confirm no fingerprint moved — that suite is what proves the `index_rows`,
`index_fingerprints` and `card_ids` trio still agree, since all three read
through `_rows`.
