# T-009-D3 — `debt._rows` strips one backtick per cell end, not a matched pair

**Origin:** found by T-009, in `dispatcher/debt.py`, which it changed.
**Status:** open. **Ruling:** accepted by the revisor, rounds 1, 2 and 3.

## What

`dispatcher/debt.py:_rows` (through `_column`) strips a single backtick from
each end of a table cell so that an id written `` `T-008-D1` `` reads as
`T-008-D1`. It is not a matched-pair unwrap: a cell that merely *ends* in inline
code — "…in `_scan`" — loses its closing backtick and keeps the opening one, and
a cell wrapped in double backticks keeps one at each end.

## Where it bites

Phase 2 rendering `/api/debt` from `index_rows`, or any task changing the cell
stripping in `_rows`. It does not bite a row whose cells are plain prose, which
is most of them.

## Why it stays

The same stripping is what unwraps the ids that feed `index_fingerprints`, and
fingerprints are how the dispatcher decides a declaration is already filed.
Changing the unwrap changes those strings, so a fix re-files debt that is already
on the board — which is a larger change than the defect, and not one Phase 1
was asked to make. Pre-existing: `index_rows` only exposed it, by giving a
caller the cells rather than the ids.

## Cost of leaving it

An unbalanced backtick in the Phase 2 UI, and a dedupe comparing a slightly
different string from the one the index holds.

## Fix

Strip a matched pair only, then re-run `tests/dispatcher/test_debt.py` to
confirm no fingerprint moved — that suite is what proves the `index_rows`,
`index_fingerprints` and `card_ids` trio still agree, since all three read
through `_rows`.
