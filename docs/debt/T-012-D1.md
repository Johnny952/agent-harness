# T-012-D1 — `merge-task` drops a task's project-scope inbox entries whether or not its auditor ever ran

**Origin:** found by the by-hand review of T-012, in
`dispatcher/learnings.py:drop_promoted` and its `merge-task` call site
`dispatcher/cli.py:476` — files that review did not touch, which is a
departure from *Declare `found` debt only for files your task touched* in the
README. It is filed anyway because the loss has already happened and this row
is the only record of it left anywhere.
**Status:** resolved 2026-10-05 by T-014, both halves (`docs/decisions.md` ADR
33 and ADR 34), and it had already fired once before either landed. Filed out
of cycle: T-012's run stopped for quota before its auditor, so nothing in cycle
declared it — no declaration, no ruling, no filing note and no card. The
operator gave it the first free id in T-012's sequence, the way the two
`T-010` rows were re-derived by hand.

## What

`drop_promoted(hive_dir, task_id)` deletes every unreviewed project-scope
entry in `.hive/learnings/inbox/` that belongs to a task whose branch has just
merged. Its own docstring states the premise and names the risk:

> They are in the project's `docs/learnings/` now, committed, so keeping them
> here would charge every later phase of every task for a row it can already
> read in the repo. The risk is the other way: an auditor that ran out of
> turns before filing one loses it here. That is why every deletion is logged
> by ref — the inbox is not the only copy, the merge commit is.

The premise holds at the automatic call site. `dispatcher/dispatcher.py:1822`
runs after `run_phase(ctx, "auditor", final=True, …)` returned and after the
task moved to `done`, so the role that promotes an entry into the project's
`docs/learnings/` has run and the merge commit really is the other copy.

It does not hold at the other call site. `dispatcher/cli.py:476` is
`merge-task`, the verb for landing a branch by hand, and the branch it is
handed is by definition one the cycle did not land — because the cycle died,
timed out, or ran out of quota at whatever phase it was in. It merges, and
then drops unconditionally. Nothing checks that an auditor ran, and the log
line it leaves is the entry's *ref* — a filename — not its text, so the "other
copy" that line points at is a file that was never written.

The inbox has no copy of its own to fall back on either: `.gitignore:6`
ignores `.hive/`, and the directory is root-owned, outside every worktree and
in no history.

## Where it bites

`dispatcher merge-task` on a branch whose cycle did not reach a completed
auditor phase — which is every hand-driven recovery this project has done:
T-010, T-011 and T-012 all landed that way. Also any later change to
`drop_promoted`, to either call site, or to which scope promotes where.

Harness-scope entries are not at risk and the table above should not be read
as saying they are: `drop_promoted` skips anything whose scope is not
`SCOPE_PROJECT`, and `docs/learnings/README.md` is explicit that a harness
trap waits in the inbox until a human promotes it. Project scope is exactly
the scope whose destination is in the repo, which is why it is the scope the
assumption is made about.

## What it already cost

T-012's cycle stopped for quota after the implementador's round 1; the
auditor never ran. `merge-task` landed the branch and deleted three entries:

- `T-012-a-task-files-status-has-no-role-in-it.md`
- `T-012-front-has-no-node-modules-and-a-generated-route-tree.md`
- `T-012-front-tsconfig-admits-no-node-globals.md`

`grep -rl "T-012" docs/learnings/` comes back empty, so none of the three was
promoted, and the files are gone. What each one *said* survives by luck rather
than by design — the first in `docs/decisions.md` ADR 26, the other two in ADR
24 and `front/README.md`, because the same facts had to be written down
somewhere a screen task would read. That is what makes this easy to miss: the
knowledge was not lost this time, only the entries, and the next cycle to be
recovered by hand may not have written its findings down twice.

## Why it stays

The fix is dispatcher work with a test in
`tests/dispatcher/test_learnings.py`, and the review that found it was reading
`front/` for two console findings; taking `dispatcher/learnings.py` on the
same pass would be a second, unrelated change landing with no cycle around it.

It is also not a one-line fix with an obvious shape. Both candidates below
change what `drop_promoted` promises, and that promise is the one thing
standing between the inbox and every later phase's prompt budget — the reason
the deletion exists at all. That trade is an implementador's to make with the
suite in front of it.

## Cost of leaving it

Every future hand-recovered cycle silently destroys whatever its implementador
and revisor filed, at the moment an operator does the most ordinary thing
available — landing work that is finished. Silently is the operative word: the
drop is logged, `merge-task` prints the count, and both read like
housekeeping, because in the automatic path that is exactly what they are.

## Fix

Two halves, independent, and the first is worth doing even if the second is
rejected.

**Stop deleting.** Move the entry to a sibling `dropped/` directory instead of
unlinking it. `read_inbox` and `read_harness` enumerate `inbox/` and
`harness/` by name through `read_dir`, so a third directory is invisible to
every prompt and the docstring's reason for the drop — prompt cost — is
satisfied in full. The loss stops being permanent for a cost of nothing.

**Stop dropping on a cycle that never promoted.** `drop_promoted` already has
`hive_dir` and `task_id`, and the task file's body carries one `## <role>`
section per phase that ran, so the evidence that the promoting role ran is one
local read away: no `## auditor` section, no drop, and `merge-task` prints
what it kept and why. This is a proxy, not the exact test — an auditor that
ran but ran out of turns before filing one entry is the case the docstring
already names, and only checking each ref against the merged tree answers
that. The proxy covers the whole-cycle case, which is the one that has fired,
and costs one file read rather than a second container round-trip.
