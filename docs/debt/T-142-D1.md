# T-142-D1 — `/api/learnings` `in_phase_table` answers for the unfiltered table, not per task

**Origin:** introduced, by T-142; declared by its arquitecto and implementador.
**Status:** open.
**Ruling:** accepted by T-142's revisor.
**Card:** none — nothing mirrors a row (`docs/decisions.md` ADR 59).
**Impact:** cost.

## What

Since T-142 a phase is handed `learnings.select(eligible(...), context)`
before the cap: the rows its task's paths or tags name, plus every harness
or reviewed row (`docs/decisions.md` ADR 315). `/api/learnings` in
`observability/api/app.py` still computes `in_phase_table` as
`learnings.handed(learnings.eligible(served, slug), harness)`, which is the
table a phase gets only when its task has no usable context or matches
nothing. A filtered phase is handed a subset of `eligible` that can include a
row this column marks `false` for the cap, and leaves out rows it marks
`true`.

## Where it bites

A task that adds a `?task=` parameter to `/api/learnings`, renders
`in_phase_table` on the task detail screen, or otherwise reads that column as
"this row reached this task's phases". Not a task reading the column as the
per-project, unfiltered answer, which is what it still is.

## Why it stayed

The route answers per project and has no task to select for. ADR 315
decision 5 states the divergence, which the task card allowed in place of
keeping the two equal.

## Cost of leaving it

An operator may read a row as not reaching a phase that a filtered phase is
in fact handed, or as reaching one that the filter left out.

## Fix

Add `?task=` to `/api/learnings` and compute the column as
`handed(select(eligible(...), task_context(...)))` for that task, keeping the
no-parameter answer as today's (`docs/decisions.md` ADR 315, decision 5).
