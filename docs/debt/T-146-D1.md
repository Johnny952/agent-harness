# T-146-D1 — Failed sign-ins are throttled per user only, not per address

**Origin:** introduced, by T-146; declared by its arquitecto and implementador.
**Status:** resolved 2026-10-23 by T-149.
**Ruling:** accepted by T-146's revisor.
**Card:** none — nothing mirrors a row (`docs/decisions.md` ADR 59).
**Impact:** risk.

## What

`board_service/signin.py` `install`'s `session_create` counts failures on the
user record (`failures`, `locked_until`): `MAX_FAILURES` wrong passwords or
codes lock that one name for `LOCK_SECONDS`. Nothing counts failures per
client address. An unknown name is answered as fast as a known one (it is
checked against `_dummy`) but is never counted at all.

## Where it bites

A task that makes the console forward `X-Forwarded-For` to `board_service`
(step 2 of `docs/plans/server-deployment.md` *How it would be built*), or that
exposes sign-in beyond `localhost`.

## Why it stayed

The browser never reaches the board service: the console's server half
forwards every call, so until step 2 relays `X-Forwarded-For` the service sees
only the console's address. A per-address limit now would lock every person
out at once on the first burst of failures.

## Cost of leaving it

Someone guessing across many user names from one address is slowed only per
name, so spraying one password over every name goes unthrottled. The audit log
records each attempt with `addr` and, once forwarded, `forwarded_for`.

## Fix

Add a per-`forwarded_for` failure counter beside the per-user one in
`board_service/signin.py` once step 2 sends the header, counting unknown names
too (`docs/decisions.md` ADR 324, *Consequences*).
